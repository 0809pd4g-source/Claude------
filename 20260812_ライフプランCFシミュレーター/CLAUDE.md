## このツールが何のためにあるか（個人版・最重要）

**依頼者ご夫妻が住宅購入の判断に納得と安心を得るためのツール。** FP相談で受け取った診断書に対し、配偶者が「この収入水準を維持できる自信がない」と感じたことが出発点。

**配偶者の不安は具体的に次の3点。** 「3つの心配に答える」タブ（初期表示）がこれに対応している。改修のときはこの3点に照らして優先順位を決める。

1. 年収が減っても月々の支払いに耐えられるか
2. 老後資金が十分に溜まるか
3. 0〜2歳の保育料など子育て支援は東京は潤沢だが他の首都圏はそうでない可能性があり、東京に買うべきか

配偶者の収入想定は **500万／550万／600万円**（依頼者から確認済み）。

したがって：

- **利用者自身が操作する**。開発者向けの道具ではない。ラベル・説明文・レイアウトは、FPや金融の知識がない人が読んで分かることを基準にする。
- **前提が崩れたときに何が起きるかを見せる**のが本質的な価値。参照PDFは「配偶者が884万円を維持する」前提でしか書かれていない。
- **都合の悪い結果も隠さない**。D（扶養内）以下では破綻することを明示している。同時に「ではどうすれば持つか」（必要な生活費の見直し額）も示す。
- 新機能を足すときは、まず「これは利用者の判断に役立つか」を問う。

### 汎用版だけの決めごと

- 選択肢（住宅プラン・収入シナリオ・昇給カーブ）は**金額を持たない**。
  プロフィールの「いまの年収」（`income.hBase` / `wBase`）に**割合**をかけて組み立てる。
  金額をハードコードすると、その世帯以外で使えなくなる。
- 既定値は**「仮の値」**。根拠のある推奨値ではないことを画面に明記する。
  相場の目安は出典つきの `BENCH` に任せ、既定値のコメントには書かない（二重管理を避ける）。
- 出産・育休の落ち込みは**お子さんの生年から自動で置く**（年齢を直書きしない）。
- 「すでに持ち家」は**取得年齢が現在の年齢より前**で表す。
  取得済みなら頭金・諸費用の資金整合は検査しない（もう終わった話なので）。
  正常な状態で警告を出さないよう、`info` レベル（緑の「こう解釈して計算しています」）を使う。

  （`.stack`。見出しを `data-label` に写し、CSSの `td::before` で出す）。
  **表の作り手側を触らないので、あとから表を足しても自動で効く。**
  **縦積みの対象は3〜16列。** 上限16は資産形成の16列に合わせたもので、
  **CF表の67列はここで自動的に外れる**（67列を積むと1項目66行になって読めない）。
  下限3は個人版V17の実機診断（3列の表が幅2,254pxまで伸びていた）による。
  **★同じことをする仕組みを2つ作らないこと。** 2026-08-24に、既にある
  `prepareStackTables` に気づかず `mobileCards()`（`.cardize`）を足してしまい、
  同じCSSと関数が2つ並ぶ状態になった（v2で一本化）。**着手前に必ず既存を探す。**
  **★幅の実測だけで縦積みを決めてはいけない。** 試したら対象が24表→4表に激減した。
  枠に収まっている表も、スマホではカード表示のほうが読める作りになっている。
  折り返しは `table.tbl:not(.stack)` の `th` / `td.lbl` / **`td.hint`** / `td .hint` / `td.txt` に許す
  （既定は nowrap。金額の列には掛けない＝「1,234／万円」と割れると桁を読み違える）。
  **`td.hint` と `td .hint` は別物。** セル自身が `.hint` のこともあり、
  子孫セレクタだけ書くと当たらない（V17→V19、v2で計3回同じ見落としをした）。
  **全12タブで横スクロール0を維持すること。** 表を足したら mobile 幅で測って確かめる。

- **狭い画面かどうかの判定は `isNarrowScreen()` 1本に統一してある。**
  中身は **CSSと同じ `matchMedia("(max-width:760px)")`**。
  **★`innerWidth <= 760` で別に判定しないこと。** CSSとJSで物差しが2本になり、
  2026-08-24に**同じ瞬間に `matchMedia().matches === true` なのに `innerWidth === 1067`**
  を返す状態が起きた。結果、**CSSは縦積みの見た目なのにJSが `.stack` を付けず**、
  プラン比較の3つの表が横のまま溢れていた。
  画面幅・向きが変わったら `onViewportChange()` が組み直す
  （これが無いと**スマホを回転しても次の操作まで横のまま**になる）。

- **スマホ表示の自己診断（`runMobileDiag`）を両方の版が持っている。**
  「計算の前提」ページの先頭。**全12ページを順に開いて測り、終わったら元のページに戻す。**
  1ページだけ測ると本命の表を見逃す（個人版V17でCF表を見逃した）。
  年次を横に並べた表（`data-wide="year"`＝`cfTable`／`eduTable`／`assetTable`）の中身は
  数えない。数えると1ページで2,600件超が並び**本当の崩れが埋もれる**。
  **★画面まわりを直したら、目視で判断せずこれを実行すること。**
  2026-08-24に、目視で「全12タブ横スクロール0」と判断した直後、
  この診断がプラン比較の3表の溢れを検出した。
  **汎用版 v2 は依頼者の端末（画面350px・表示倍率3）で全12ページ○・溢れ0件を確認済み。**
  この基準線を下げないこと。
  **★ただし診断が測れるのは幅だけ。** 「収まった」と「読める」は別で、
  縦積みになった32個の表の読みやすさは未確認のまま。
  **★はみ出しは `scrollWidth - clientWidth` で測ること。`innerWidth` と比べてはいけない。**
  端末エミュレーション下では、ページがはみ出すと `innerWidth` 自体が広がる
  （375のはずが613になった）ため、**差が常に0になり、はみ出しを絶対に検出できない**。
  2026-09-02のChatGPT版V89査読で、`scrollWidth - innerWidth` では0だった画面が
  `clientWidth` 基準では113pxはみ出していた。相手のQAハーネスも同じ式を使っている。
  **★監査・検証系の関数（`audit()` など）は測定の前に呼ばないこと。**
  同じV89で、`audit()` が経路を再描画して段組みクラスを落とし、
  包み側のスクロール枠だけ残すため、**監査を呼んだ後だけ**はみ出しが出ていた。
  監査が自分の壊した結果を自分の不合格として報告していた。
  同じ式の中で `audit()` を呼んだ自分の測り方も原因で、P1候補からP2へ格下げした。
  **測定行為が対象を壊しうる。呼ぶなら「呼ぶ前」と「呼んだ後」を別々に記録する。**
  **★「console 0件」は新規タブで測ること。**
  ブラウザペインのコンソールは再読込・遷移でも消えないため、
  前のページ（自分のv32検証時）の `SyntaxError` を査読対象の不具合だと誤認しかけた。

- **感応度分析（`renderSensitivity`）は既存の `SCENARIOS` を使い回している。**
  「基準」と「複合」を除いた分＋`SENS_EXTRA`（`SCENARIOS` に無い1変数の項目）。
  **同じ前提を2か所で定義しないこと。** 項目を足すときは、
  まず `SCENARIOS` に入れるべきかを考える（ストレステストにも出したいなら `SCENARIOS`）。
  `SENS_EXTRA` は `applies(P)` でその世帯・住まいに当てはまるものだけ出す。
- **「片方の版にあって片方にない」だけで欠陥と決めつけないこと。**
  2026-08-25に「個人版は狭い画面の判定が `innerWidth` のままで物差しが2本ある」と指摘したが、
  **個人版の `prepareStackTables` はそもそも画面幅を見ていなかった**（常に `.stack` を付け、
  CSSのメディアクエリだけに判定を任せる設計）。**設計が違うだけで欠陥ではなかった。**
  差分を直す前に、**両方の実装を読んで、なぜそうなっているかを確かめること。**

- **「入力欄が16px未満」だけで iOS の自動ズームを疑わないこと。**
  自動ズームは**テキスト入力（text/number/select等）でしか起きない**。
  チェックボックス・スライダー・ファイル選択が13.3pxでも問題ない。
  2026-08-24に、この区別をせずに誤診した。**測った数値の中身を見ること。**

## 凍結している判断（変えるときは理由を残す）

- 税・社会保険料は**制度どおり**に計算する。PDFは厚生年金の標準報酬月額の上限（月65万円）を
  適用しておらず保険料が過大なので、PDFに合わせ込まない。結果として資産は最大4.5%多く出る。
- 配偶者の33歳・35歳の収入（346万円・143万円）はPDFのCF表の実額を採用する。
  設定テーブル上は0万円だが、按分ルールが特定できないため実額を正とする。
- 就学段階は誕生年からの経過年（学年ベース）で判定する。満年齢ではない。
- **扶養控除は「学校を出るまで」で打ち切る**（`tax.depEndAge`。既定は教育の最終段階が終わる年）。
  v8まで上限がなく、子が何歳になっても控除が続いていた（v9で修正。PDFとの乖離も縮んだ）。
  本来の要件は「子の合計所得58万円以下」だが、このツールは子の収入を持たないため卒業で判定する。
- **寡婦控除は実装しない**（婚姻の経緯という、このツールが集めていない情報が必要なため）。
  該当する世帯では税額が実際より多めに出ることを画面に明記する。
- **住民税は前年の所得にかける**（`tax.residentPrevYear`。既定true）。
  退職した年・育休に入った年の負担がここで効く。
  **退職所得の住民税は分離課税で退職した年に特別徴収される**ので現年のまま。
  基準年（1年目）だけは前年の所得が分からないためその年の所得で計算する。
  ※この修正でPDFとの乖離が 6.4%→3.5〜4.1% に縮んだ（PDFも前年基準だった）。
- **育児休業給付金は非課税・社会保険料免除**（`tax.leaveTaxFree`。既定true）。
  **両方の版にある**（個人版はv15〜v26で失われていたのをv27で戻した）。
  ただし**個人版の収入テーブルには `leave` の印を付けていない**＝参照PDFのCF表の実額が
  給与なのか給付金なのかを断定できないため。**機構はあるが、この世帯には適用していない。**
  収入テーブルの行に `leave` の印を付けて判定する（`tableFlag`）。
  **免除されても将来の年金は納付扱い**なので `estimatePension` では収入として数える。
  出産した年は給与のまま（年の大半は働いている想定・安全側）。
- **国民健康保険は世帯単位**（`kokuhoHousehold`）。賦課限度額は世帯で効く。
  **「扶養」の概念がないので加入者全員に均等割がかかる（子どもも1人年6万円強）。**
  ただし親のどちらかが会社員なら子はその健保の被扶養者になるので対象外。
  減免（7割・5割・2割軽減）は未実装＝所得が低い年は多めに出る。
- **税の扱いを直したら、画面の「わかっている簡略化」も必ず直すこと。**
  直したのに説明が古いままだと、正しい計算を誤りだと読ませてしまう。
- その他支出は物価変動させない（PDFの挙動に合わせる）。
- 固定資産税等は物件価格×0.306%で自動計算する（①②から逆算した値）。修繕積立管理費は物価変動させない。
- 資産残高の乖離判定は**率ではなく絶対差**で見る。社会保険料の差は毎年ほぼ一定額なので、
  資産が小さいパターンほど率では大きく見えてしまい実態を表さない。

## ブラウザでの実機確認（2026-08-17に可能になった）

`file://` は開けないが、**HTTPで配信すればブラウザペインで開ける**。
画面まわりを変えたら、必ず実機で確認すること。

```
preview_start（name: "ライフプランCF"）→ http://localhost:7435/
```

設定は親コンテナの `.claude/launch.json`。

**なぜ必須か**：DOMスタブのスモークテストは `onclick` などのイベント属性を
解析しないため、**属性が壊れていても「異常なし」と出る**。
実際に `onclick="...${JSON.stringify(name)}..."` でHTML属性が途中で切れ、
グラフの凡例が押しても効かない状態が追補24から約2日間気づかれずに残っていた。

同種の見落としを防ぐため、スモークテストに**イベント属性の構文検査**を入れてある
（描画したHTMLから `onclick` 等を全部取り出して1つずつ構文解析する）。
**HTML属性の中にJS文字列を埋めるときは `jsAttr()` を使うこと。`JSON.stringify` は使わない**
（ダブルクォートを出すため属性が終わってしまう）。
