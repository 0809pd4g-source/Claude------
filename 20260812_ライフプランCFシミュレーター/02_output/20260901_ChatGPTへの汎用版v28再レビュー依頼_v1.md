## 2. P0-1｜擬制世帯主の前年所得

**再現しました。** `extraFor()` が当年の給与・年金だけで世帯主を作り、
`if(sal <= 0 && pen <= 0) return [];` で**当年0円なら世帯主が判定から消えて**いました。

v27で加入者側（`mem`）を `prevOf()` / `prevPensionOf()` に通したのに、
**同じループの中にある擬制世帯主を見落としていました。**

**受入ケース（そちらの指定どおり）**：H自営・前年国保所得0円／W会社員・世帯主・前年所得800万円確認済み／当年は給与も年金も0円

| | v27 | **v28** |
|---|---:|---:|
| 前年800万円を確認済み | 25,461.9円 | **84,873円** |
| 前年0円 | 25,461.9円 | 25,461.9円 |
| 差 | **0円**（前年所得が効いていない） | **59,411.1円** |

**そちらが期待値として書かれた 84,873円 と一致しました。**
壊れているときの 25,461.9円 も一致しています。
別々に実装したものが両方の数字で合ったので、同じ制度を同じように読めていると考えます。

対応：`prevHeadIncH/W`・`prevHeadPenH/W` を年をまたいで持ち越し、
加入者と**同じ入口**（`prevOf` / `prevPensionOf`）を通します。H/W対称です。
当年も前年も0円のときだけ空配列を返します。

## 3. P0-2｜トップレベル金額の意味範囲

**再現しました。** v27の範囲検査は `setNum()`（配列の中の欄）だけで、
`onMan()` を通るトップレベルの金額は素通りでした。

**「どれを守るか」を並べると必ず漏れる**ので、逆にしました。
**`onMan()` は金額の入口なので既定を0以上**とし、負を許すパスだけを
`NEGATIVE_MONEY_OK` に明記します（いまは空。足すときは画面にも意味を書く決まりにしました）。

| 操作 | v27 | **v28** |
|---|---|---|
| `onMan('house.price','-1000')` | −1,000万円が入る | **拒否・直前値のまま** |
| `house.selfFund` / `house.gift` | 受理 | **拒否** |
| `econ.deposit` / `econ.invest` | 受理 | **拒否** |
| `living.insurance` / `house.feeRegistration` | 受理 | **拒否** |

あわせて年齢の下限を **18歳**にしました（v27は0も−5も受理し、
見出しが「あなた-5歳〜100歳」になりました）。`meta.endAge` は19以上、
`econ.inflation` は−20〜20、`econ.investRate` は−50〜50、`house.rentGrowth` は−99.9〜50です。

## 8. P1-5｜ウィザードと準備度

**再現しました。これがいちばん痛い1件です。**
v26で「セットアップを一周したら段階3に届く」を受入条件にしたと書きましたが、
**測っていたのは賃貸の分岐だけ**でした。

| 分岐 | v27 | **v28** |
|---|---|---|
| 賃貸のまま | 段階3・10/10 | 段階3・10/10 |
| **これから購入** | **段階1・9/10**（足りない「いまの住居費」） | **段階3・9/9** |
| **すでに持ち家** | **段階1・9/10**（同上） | **段階3・9/9** |

しかも `checkWizardCoverage()` は**0件**を返していました。
`covers` の一覧を突き合わせるだけで、**分岐を見ず、欄が実際に描かれるかも見ていない**ためです。

対応は2つ。

1. **準備度を分岐で条件付ける**。`need` の3つ目に `applies(P)` を持たせました。
   - 賃貸・これから購入 → `house.rentNow` が要る／すでに持ち家 → 要らない
   - これから購入 → `house.price`・`house.loans.0.years` が要る
2. **購入の分岐にも「取得するまでの住居費」と家賃の上昇率を置きました**
   （取得年までは実際に家計から出ていくので、隠れた要求ではなく本当に必要な入力です）。
