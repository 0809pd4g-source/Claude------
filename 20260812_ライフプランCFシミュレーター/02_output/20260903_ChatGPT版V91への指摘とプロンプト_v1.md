## 2. P1

### P1-1｜revision競合のあと、そのタブでは保存が二度とできない（しかも通知は「同期します」と言う）

**再現手順**

1. 既存A・既存Bを通常保存する
2. 別タブの有効な保存が着地した状態を作る（同一タスク内でprimaryへ有効payloadを書き、storageイベントは配送させない）
3. 保存ボタンを押す

**実測値**

| 対象 | 値 |
|---|---|
| primary / backup | 既存A, 既存B, 新規C, 新規D, **別タブG**（他タブの保存は保持） |
| 画面・メモリ | 既存A, 既存B, 新規C, 新規D（**別タブGが入らない**） |
| 通知 | `v91-revision-conflict`（warn） |
| 通知の文面 | 「新しい内容を上書きせず、今回の保存を中止して**一覧を同期します**」 |
| 実際の同期 | **されない**（画面4件／保存領域5件） |

**ここからが本題です。** 続けて3回保存を試みました。

| 試行 | 通知 | 保存された | 画面の件数 |
|---|---|---|---|
| 1回目 | `v91-revision-conflict` | されない | 6 |
| 2回目 | `v91-revision-conflict` | されない | 6 |
| 3回目 | `v91-revision-conflict` | されない | 6 |

保存領域は7件、画面は6件のまま。**`REV_RAW` が更新されないので、以後この画面では何度押しても保存できません。**

**原因**

`storePlans91` の revision 競合分岐は `POST_SYNC=baseline` を置いて `false` を返すだけです。`POST_SYNC` を消費するのは `v75CommitPlans` のラッパーだけですが、

```js
v75CommitPlans=function(){
  POST_SYNC=undefined;
  const ok=BASE_COMMIT.apply(this,arguments);
  if(!ok&&POST_SYNC!==undefined){const raw=POST_SYNC;POST_SYNC=undefined;adopt(raw,"保存直前のrevision差",false);}
  return ok;
};
```

**保存ボタンの経路はここを通りません。** `v75CommitPlans` と `v61StorePlans` の両方を計測用にラップして保存ボタンを押しましたが、**どちらも呼ばれませんでした**（記録は空配列）。実際の保存経路は再代入前の束縛を握っているため、`POST_SYNC` は置かれるだけで誰も読みません。

**逃げ道はあります。** `focus` を発火させると `resync` が走り、画面が6→7件になり、その直後の保存は成功しました。つまりタブを離れて戻れば直ります。ただし利用者にその手順は伝わりませんし、通知は「同期します」と言い切っています。

**直し方**：競合分岐で `POST_SYNC` に頼らず、その場で `resync()`（または `adopt(baseline, …)`）を呼ぶ。1行です。ついでに、**通知が約束したことは同じ関数の中で実行する**のが安全だと思います。別の層に伝言する形だと、その層が経路から外れたときに黙って効かなくなります。

### P1-2｜`fundingState` が将来購入の資金不足を常に「足りている」と判定する

**再現手順**：価格5,000万円・自己資金0・借入0の将来購入を作り、画面表示と `__V91__.fundingState(PARAMS)` を比べる。

**実測値**

| 対象 | 値 |
|---|---|
| 画面の表示 | 「資金が **5,000万円** 足りません」（正しい） |
| `__V91__.fundingState(PARAMS)` | `{level:"ready", gap:0, ready:true}`（**誤り**） |
| 手計算の不足額 | 50,000,000 |

**原因**は引数の形です。

```js
const gap = typeof v75FundingGap==="function" ? v75FundingGap(P) : Number(H.price||0)+...-loanSum;
```

`v75FundingGap` の定義は

```js
function v75FundingGap(H){
  return Number(H.price||0)+Number(feeTotal(H)||0)-Number(H.selfFund||0)-Number(H.gift||0)-v75LoanSum(H);
}
```

で、**houseオブジェクト**を取ります。`fundingState` は `P`（PARAMS全体）を渡しているので、`P.price`・`P.selfFund` などがすべて undefined→0 になり、**gap は常に0**です。実測でも

- `v75FundingGap(PARAMS)` → **0**
- `v75FundingGap(PARAMS.house)` → **50000000**

同じ行の**フォールバック式は `H.price`・`feeTotal(H)` と houseで書かれている**ので、主経路だけ引数を間違えています。

**影響**：今日は将来購入の表示が基底描画から来ているので画面は正しく、利用者は誤解しません。ただし

- `audit().funding` が誤って `ready` を報告する（自分の監査が緑になる）
- **この版の看板機能である「表示判定を判定関数へ一本化」の中心が、常に合格を返す**
- `fundingState` は凍結APIで公開されているので、後続の版がこれを信じて表示を寄せると、そこで初めて画面に出る

**直し方**：`v75FundingGap(P.house)`。

## 3. P2

### P2-1｜監査のゲートが、実画面ではなく監査自身が作った代役を測っている

V89のP2-4（対象0件で自動合格）は直っています。`workTypeCurrentAudit` は対象がなければ `{evaluated:false, ok:null}` を返し、合格に数えません。ここは期待どおりです。

ただし**ゲートの掛け先が実DOMから外れました**。負試験の実測：

| 手順 | `workTypeCurrentAudit` | `audit().ok` |
|---|---|---|
| 実画面の働き方ボタン6件すべてを同名「働き方」に破壊 | `ok:false`、duplicates 2件を検出 | **true（合格のまま）** |

`audit().checks` のキーは `structureIntegrity` / `metadataIntegrity` / `buttonTypes` / **`workTypeMatrix`** / `auditDidNotMutate` / `qualityEvidenceVersioned` / `storageRevision` / `pendingRecovery` / `ownedHomeReadiness` の9つで、**`current` の結果は入っていません**。

`workTypeMatrix` は監査自身が `document.createElement("div")` で6個のボタンを作り、`ensureAccessibleNames` を当てて名前を検査します。これは**命名関数の単体試験**であって、いま描かれている画面の検査ではありません。`workTypeBox()` が aria-label を出さなくなっても、マトリクスは通ります。

**つまり、V87の発端だった「実画面で本人とパートナーの働き方ボタンが同名」は、V91の監査では検出できません。**

**直し方**：評価できたときは実DOMの結果をゲートに入れる。たとえば `checks.workTypeCurrent = current.evaluated ? current.ok : true` とし、未評価であることは別欄で報告する。代役は代役として残してよいと思いますが、**代役だけが合否を決める形にしない**のが要点です。

### P2-2｜ヘッダで版番号が二重に出る

**実測**：`ライフプラン・シミュレーター` **`V91`** **`V91 保存整合性・表示判定・監査非破壊化版`**

`applyMeta` が同じ要素へ2回書いています。

```js
const name=document.getElementById("appVersionName");if(name)name.textContent=META.versionName;
const sub=document.querySelector("header .sub");if(sub)sub.textContent=META.subtitle;
```

`#appVersionName` は `class="sub"` を持ち、**header内で最初の `.sub`** です。つまり `document.querySelector("header .sub")` が指すのは同じ要素で、後の書込み（`subtitle` = `"V91 保存整合性…"`）が勝ちます。バッジのすぐ隣に版番号がもう一度出ます。

**直し方**：subtitleを別要素にするか、この要素には `versionName` だけを書く。**同じ値の設定経路を2本持たない**という、そちらにも私にも何度も出てきた型です。

## 5. 誤認・撤回した仮説

1. **起動直後に横はみ出し282pxを検出した** → 背景タブでは `clientWidth` も `innerWidth` も **0** になるため、`scrollWidth - clientWidth = 282 - 0` という見かけの値でした。ビューポートを与えて測り直すと**0**。前回「はみ出しは clientWidth で測る」と学んだ直後に、**測る場所（表示されていないタブ）で同じ穴に落ちました**。撤回。
2. **1280pxの巡回で6経路が不合格に見えた** → `overflow: -15` は**縦スクロールバーの分**で、`scrollWidth < clientWidth` は overflow ではありません。判定を `<= 0` に直しました。撤回。
3. **`visibilitychange` で再同期されない** → 背景タブの `visibilityState` が `"hidden"` なので、ハンドラの `if(visibilityState==="visible")` が正しく何もしなかっただけでした。欠陥ではなく**未検証**へ格下げ。
4. **（自分の過去分）V89レビューの計算回帰の列** → `socialTotal` と `financial` は存在しないキーで、8列のうち2列は何も比較していませんでした。P2-3に記載のとおり訂正し、66キーで測り直しました。

> 原因：`storePlans91` は `POST_SYNC=baseline` を置いて false を返すだけで、`POST_SYNC` を消費するのは `v75CommitPlans` のラッパーのみ。**保存ボタンの経路はそこを通らない**（`v75CommitPlans`・`v61StorePlans` を計測用にラップして押したが、どちらも呼ばれない）。
>
> 直してほしい点：
>
> 1. revision競合・ロック競合・late競合の各分岐で、`POST_SYNC` に頼らず**その場で `resync()`（または `adopt`）を呼ぶ**こと。
> 2. 通知が「同期します」と言うなら、**同じ関数の中で同期を完了**させること。別の層への伝言にしない。
>
> 受入試験：上記(1)〜(4)を通し、(3)の直後に画面が別タブGを含む一覧へ同期されること、(4)の保存が成功することを確認する。**修正前のV91で不合格になり、修正後に合格すること**を示してほしい。
>
> ### P1-2 `fundingState` が将来購入の不足を常に「足りている」と判定する
>
> 再現：価格5,000万円・自己資金0・借入0の将来購入で `__V91__.fundingState(PARAMS)` を呼ぶ。

> 原因：`v75FundingGap(H)` は house オブジェクトを取るのに、`fundingState` は `v75FundingGap(P)` と PARAMS を渡している。同じ行のフォールバック式は `H.price`・`feeTotal(H)` と house で書かれており、主経路だけ引数の形が違う。

## 8. やったこと・やっていないこと

**やったこと**：HTTP配信＋実物のlocalStorage・実タブでの独立測定。同一性3種の再計算。V90の起動時例外の独立再現（現物が届いたため）。壊れたprimaryからのC/D保存、revision競合と3連続の保存失敗、`focus`/`storage` 再同期、表示判定5状態、監査の非破壊性（5指標の前後比較）、監査の適用性と**代役ゲートの負試験**、4幅×14経路＝56件の巡回、V89⇔V91の計算回帰（6ケース×61行×66キー＋summary、SHA-256一致）。
