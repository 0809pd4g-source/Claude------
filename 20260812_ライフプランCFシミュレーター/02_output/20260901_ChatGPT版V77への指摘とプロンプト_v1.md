### E. 資金不足のまま保存できること（設計判断として妥当）

> ★この確認で、**こちらのv27が同じ操作を弾いてしまうこと**に気づきました。

> 手入力の借入を保存できませんでした。**手入力の時点で自動連動を外す**よう直しています。

## 3. P1

### P1-1 「判断の準備が整ったか」の答えが2つあり、新しいほうが甘い

V77で追加した `decisionReady(topic)` は `PARAMS.meta.v61.confirmed` の**旗だけ**を見ます。
一方、既存の `v61Completion()` は旗に加えて**その旗の裏にある値が使えるか**まで見ます
（`housingDetailReady = !house.buy || (c.housing && price>0 && loans[0].years>0)`、
`childReady = 子の生年 > 0`）。

**再現手順**（ブラウザのコンソール、初期状態から）

```js
PARAMS.meta.v61.confirmed =
  {age:1,income:1,living:1,assets:1,retirement:1,housing:1,insurance:1,saving:1,assumptions:1,children:1};
PARAMS.house.buy = true;
PARAMS.house.price = 0;                                   // 物件価格 未入力
PARAMS.house.loans = [{name:'本人',amount:0,years:0,steps:[{y:1,rate:1}]}];  // 返済年数 0年
PARAMS.family.children = [{name:'子1', birthYear:0, plan:{}}];               // 生年 未入力
v61Completion();       // → stage 2, decisionReady:false, missing:{decision:['children','housingDetails']}
decisionReady('overall');   // → level:'ready'
decisionReady('housing');   // → level:'ready'
decisionReady('education'); // → level:'ready'
```

**実測**

| 判定 | 結果 |
|---|---|
| `v61Completion().stage` | **2**（家計の全体像を確認できます） |
| `v61Completion().missing.decision` | `['children','housingDetails']` |
| `decisionReady('overall')` | **`ready`** |
| `decisionReady('housing')` | **`ready`** |
| `decisionReady('education')` | **`ready`** |

物件価格0円・返済年数0年・子の生年0年のまま、新しいAPIは「判断の準備が整った」と答えます。
**依頼書 §E がこのAPIの妥当性を問うている以上、ここは配布前に揃えるべきだと考えます。**

**なぜ起きたか**：`V77_READY_TOPICS` は**確認済みキーの集合**だけで準備度を定義しており、
`v61Completion()` が持っていた**値の妥当性の条件2つ**（`housingDetailReady` / `childReady`）が
写されていません。

**修正案**

1. `v77DecisionReady()` の判定を `v61Completion()` から導出し、**準備度の定義を1か所にする**。
   `V77_READY_TOPICS` はテーマごとの「どのキーを見るか」だけを持ち、
   **値が使えるかの条件は共通の関数**に置く。
2. どうしても2本持つなら、**両者が一致することを回帰に入れる**
   （上の再現状態を含む数状態で `v61Completion().decisionReady === (decisionReady('overall').level==='ready')`）。
3. `missingRequired` に `housingDetails` / `childBirthYear` を返せるようにし、
   **画面と同じ言葉で不足を言う**。

> ★これは、こちらがv23で踏んだ形と同じです。「確認した」という旗を立てただけでは、
> **確認した時点の値が今も入っているか**は保証されません（`kokuhoConfirmedFingerprint` で直しました）。

### P1-2 家賃上昇率の欄が、見えるラベルと読み上げ名で別のものを指している

**実測**

| 項目 | 値 |
|---|---|
| 見えるラベル（`<label for="v77RentGrowthMode">`） | **「賃貸を続ける場合の家賃」** |
| 読み上げ名（`aria-label`） | **「家賃上昇率の設定方法」** |
| 読み上げ名が見えるラベルを含むか | **いいえ** |
| すぐ上の欄のラベル | 「取得前の住宅関連費（年）／家賃など」（単位：万円） |

問題は2つあります。

**(a) 見える文字が中身と違う。** ラベルは「家賃」＝**金額**を指しますが、この欄は**年率**の選択です。
しかも**すぐ上の欄が本物の家賃（万円）**なので、
「家賃を入れる欄が2つあり、片方は万円、もう片方はなぜか選択式」に見えます。
選択肢を開けば率だと分かりますが、**開くまで分かりません。**

**(b) `aria-label` が `<label>` を上書きする。** 読み上げ利用者には「家賃上昇率の設定方法」、
画面では「賃貸を続ける場合の家賃」。**同じ欄を2つの名前で呼んでいます。**
音声操作で「賃貸を続ける場合の家賃」と言っても、この欄には当たりません
（WCAG 2.5.3 Label in Name の考え方）。

**修正案**：見えるラベルを **「家賃の上昇率」**（または「賃貸を続ける場合の家賃の上昇率」）にし、
`aria-label` は**外す**（`<label for>` があるので不要）。単位が率であることをラベルで言い切る。

> ★依頼者が2026-08-31に「心配ごとが3つまで選べると書いてあるが2つしか見えない」と指摘した件と**同じ型**です。
> 自動検査は「名前がある／崩れていない」を測りますが、**その名前が中身と合っているか**は測りません。
> V76のときに「対応関係の正しさはレイアウト検査では見えない」と書いたのと同じ場所に、また出ています。

## 4. P2

### P2-1 版の名乗りが2つある

| 場所 | 文字列 |
|---|---|
| `<title>` | ライフプラン・シミュレーター｜**レスポンシブ・ビジュアル統一版 V77** |
| ヘッダーの副題 | **V77 数値入力・住宅試算安全性強化版** |

どちらもV77ですが、**版の名前が違います。** 利用者が「どの版か」を人に伝えるとき食い違います。

あわせて、`render()` の中に

```js
const ver = document.querySelector('header .sub'); if(ver) ver.textContent = 'V70 導線・文言総点検版';
```

が残っています。**いまは後段の層が上書きするので画面には出ません**（実測で副題は V77 のもの）。
つまり**現時点では利用者に影響しません**が、同じ描画の中で同じ要素に2回書いており、
**順序が変わった瞬間にV70と表示されます。** 版の表記は1か所の定数から参照してください。

### P2-2 年齢に負の値を入れられる

QAレポート §3.1 は「年齢・リタイア・子どもの人数／生年」に**範囲**検査を入れたと書いていますが、
実測では負の年齢が通ります。

```js
onNum('family.ageH','-5');
// → PARAMS.family.ageH === -5
// → ヘッダー「2026年基準 ／ あなた-5歳〜100歳」
// → 試算 106行（先頭 -5歳）
```

同様に、`meta.endAge` を現在年齢より小さくすると試算が2行になります（35歳→最終年齢10）。
生活費 −1,000万円・預金 −1億円も通ります。

**桁あふれは止まっているので実害は小さい**ですが、**レポートの記述と実装が食い違っています。**
記述を実装に合わせるか、実装をレポートに合わせるかのどちらかにしてください。

### P2-3 「テーマ別準備度」の `assumptions` を、案内が一度も聞かない

`V77_READY_TOPICS` はすべてのテーマで `assumptions`（長期前提）を `recommended` に入れており、
**`ready` に到達するには確認が要ります**（`level` は `missingRecommended` が空でないと `ready` にならない）。

一方、上部ガイドの3ステップは
「1 基本情報／2 資産・住まい／3 診断（確認画面）」で、**長期前提はどのステップにも入っていません。**
本文の対応表示は「住まいはステップ2、**長期前提は診断の精度を上げるために確認します**」と書いており、
**どこで確認するのかを言っていません。**

これはV76で指摘した件の**残り**です。V76では「ガイドどおりに入れても4段階目に到達しない」と書きました。
V77は文を足しましたが、**案内の中に長期前提の居場所がない**点は変わっていません。

**提案**：`V77_READY_TOPICS` の必要キーとガイドのステップを**機械で突き合わせる**。
こちらはv26で `WIZ_STEPS` に `covers` を持たせ、`checkWizardCoverage()` が
`READY_STEPS` の必要パスと照合して足りない項目を返すようにしました（現在0件）。
**案内と要求を別々に書いた瞬間からずれ始めるので、人が並べ直すとまた抜けます。**

## 5. 誤認・対応不要

- **資金不足のまま保存できること**（第2節E）は欠陥ではないと判断しました。
  依頼書 §B の「不足1円以内」は**ツールが借入を組み立てる経路**の条件で、
  利用者が手で決めた額に課すものではありません。画面の警告も出ています。
- **`render()` 内の `V70 導線・文言総点検版`** は、実測では画面に出ません（P2-1で保守上の指摘に留めました）。
  最初はP1に挙げかけましたが、**実際の副題を測って取り下げました。**

## 7. ChatGPT版へ戻す提案

1. **準備度の定義を1か所にする**（P1-1）。2本持つなら一致を回帰で縛る。
2. **案内のステップと、準備度が要求する項目を機械で突き合わせる**（P2-3）。
   `checkWizardCoverage()` 相当を持ち、**足りなければ検査が落ちる**ようにする。
3. **見えるラベルと読み上げ名を一致させる検査**（P1-2）。
   `aria-label` を持つ要素で、`<label for>` の文字が `aria-label` に含まれない件数を数える。
   V77では少なくとも1件あります。
4. **範囲検査の一覧を、レポートではなくコードの表として持つ**（P2-2）。
   項目→{min,max} の表を1か所に置き、レポートはその表を出力する。
   そうすれば「書いてあるのに効いていない」が起きません。
