## 3. P1

### P1-1｜事後検査が、事故の起きた経路（描画）を覆っていない

**V85のソース（17925〜17945行）が、この非対称をそのまま示しています。**

```js
const V85_BASE_RENDER = typeof render === 'function' ? render : null;
if(V85_BASE_RENDER){
  render = function(){
    const result = V85_BASE_RENDER.apply(this, arguments);
    v85ApplyVersionMeta();          // ★事故の原因コード系は描画のたびに走る
    return result;                  // ★完全性検査は無い
  };
}
const V85_BASE_SET_TAB = typeof setTab === 'function' ? setTab : null;
if(V85_BASE_SET_TAB){
  setTab = function(tab){
    const result = V85_BASE_SET_TAB.apply(this, arguments);
    const integrity = v85DomIntegrity();       // ★ここだけ検査する
    if(!integrity.ok) console.error('V85 DOM integrity failure after tab transition', tab, integrity);
    v85ApplyVersionMeta();
    return result;
  };
}
```

**再現手順と実測値**

1. 「詳細設定」を開く
2. `#nav` を外して、DOMが不完全な状態を作る
3. 画面の入力欄「このプランについて：計算基準年」に**実際に値を入れる**（`input`／`change` を発火）
4. 警告が出るかを見る

| 壊れた状態で行った操作 | `console.error` |
|---|---|
| **利用者の入力 → 再描画** | **0件** |
| `render()` を直接呼ぶ | **0件** |
| `setTab('cf')` | 1件（`V85 DOM integrity failure after tab transition cf {ok:false, hasNav:false, …}`） |

入力後も `#nav` は無いまま（＝**壊れた状態で描画が通った**）で、そのとき `domIntegrity()` は `{ok:false, hasNav:false}` を返す状態でした。**検査すれば分かるのに、その経路では呼ばれていません。**

**なぜこれが重要か**：V83の破壊は「版情報を適用する**描画ラッパー**」で起きました（そちらのQAレポート§7-1も「V82より後に追加された版情報ラッパーに入った」と書いています）。次に同型が入るとすれば、最も可能性が高いのは**同じ描画ラッパー**です。そこが無検査のままです。

**修正案**：`render` ラッパーにも同じ事後検査を入れてください。`v85ApplyVersionMeta()` の直後が自然です。

```js
render = function(){
  const result = V85_BASE_RENDER.apply(this, arguments);
  v85ApplyVersionMeta();
  const integrity = v85DomIntegrity();
  if(!integrity.ok) console.error('V85 DOM integrity failure after render', integrity);
  return result;
};
```

あわせて受入条件を「**タブ遷移後**にDOM完全性を保つ」から「**描画のたびに**DOM完全性を保つ」へ上げてください。負試験は「壊した状態で入力を1つ変える → 警告が鳴る」で書けます。

## 4. P2

### P2-1｜危険の前提条件がV85にも残っている（罠は外していない）

`data-app-version` は、V85でも **`<html>` に設定されています**（ソース上7箇所：15916・16224・17032・17464・17827・17907 ほか）。

つまり **V85でも** `querySelector('[data-app-version]')` と書けば `<html>` が返ります。§2.2 のとおり、私はそれを**V85のDOMで実際に再現できました**。

セレクタを3箇所（V83層・V84層・V85層）narrow したのは正しい対処ですが、**罠そのものは残っています**。次に誰かが版情報を探すコードを足したとき、同じ事故が起こり得ます。

**修正案**：どちらか一方を。

1. 版情報を `<html>` の属性に置くのをやめ、**表示専用の要素**（`#appVersion`）を1つ置いてそこだけを更新する。
2. `<html>` に置く属性名と、表示要素を探す属性名を**分ける**（例：ルートは `data-release`、表示要素は `data-app-version`）。

現状の `:not(html):not(body)` は「この3箇所は安全」を保証するだけで、「**将来も安全**」は保証していません。

### P2-2｜版表示を更新するコードが3世代あるが、対象要素が存在せず一度も動かない

```js
function v85VersionTarget(){
  return document.querySelector('#appVersion,[data-app-version]:not(html):not(body)');
}
```

**実測でこれは `null` を返します。** `#appVersion` は存在せず、`[data-app-version]` を持つのは `<html>` だけなので、除外すると候補がゼロになります。

したがって `const av = v85VersionTarget(); if(av) av.textContent = V85_META.version;` は**恒久的に何もしません**（V83層・V84層・V85層の3箇所すべて）。

画面に出ている「V85 モバイル初期遷移・DOM完全性ホットフィックス版」は、同じ関数の別の行
`const sub = document.querySelector('header .sub'); if(sub) sub.textContent = V85_META.subtitle;`
から来ています。実測でも `<span class="sub">` でした。

**つまり、事故を起こしたコードが担っていた仕事は、そもそも別の経路で行われていました。**
危険は消えましたが、QAの「安全セレクタが存在する」というゲートは、**そのコードが動くことを証明していません**。

**修正案**：この3箇所を**削除する**か、`#appVersion` を実際に1つ置いて機能させるか、どちらかにしてください。「安全だが何もしないコード」を3世代分残すのは、P2-1の罠を将来踏む足場になります。

### P2-3｜静的ゲートが文字列一致なので、書き方を変えると通る

```js
const destructiveSelectorAbsent = !Array.from(document.scripts).some(
  s => /querySelector\(\s*["']\[data-app-version\],#appVersion["']\s*\)/.test(s.textContent||''));
```

自分のソース文字列を正規表現で探す作りです。**空白の入れ方・属性の順序・変数経由・分割**のいずれかで書き方が変われば素通りします（例：`querySelector('#appVersion,[data-app-version]')`、`const S='[data-app-version]'; querySelector(S)`）。

実効的な守りは `domIntegrity()` 側なので、**P1-1（描画経路への配線）を直せば、こちらの比重は下がります**。静的ゲートは「この1文が復活していないこと」の確認と位置づけ、依存しないでください。

### P2-4｜基底層に旧キーのデッドコードが残っている（この版では無害と見なせない）

5748〜5753行に、初代の保存関数が残っています。

```js
function loadPlans(){
  try{ PLANS = migratePlans(JSON.parse(localStorage.getItem("lpcf_plans") || "[]")); }
  catch(e){ PLANS = []; }
}
function storePlans(){
  try{ localStorage.setItem("lpcf_plans", JSON.stringify(PLANS)); }catch(e){}
}
```

`"lpcf_plans"` は**個人版の保存キー**です。ここを読むと、同一オリジンで個人版を開いた端末では他人（利用者本人）の実データが出ます。

**実測では漏れていません。** 個人版キーに識別用の印を置いて確かめました。

| 測ったこと | 実測 |
|---|---|
| 実行時の `loadPlans` の正体 | `v83LoadPlans`（V83層が上書き） |
| 印を置いて `loadPlans()` を呼ぶ | **読み込まれない**（`PLANS` は空） |
| V85で保存したときの書込先 | `lpcf_v61_plans` のみ（`lpcf_plans` は**不変**） |
| `V61_PLAN_KEY` | `lpcf_v61_plans` |

**しかし、この版に限って「死んでいるが残っている」を無害と見なせません。**
V83のP0は、まさに「**残っていた旧コードに、別の経路が到達した**」事故でした。V84で症状がマスクされたのも同じ構図です。

さらに、そちらのプライバシー監査は
`['旧版保存領域を使わない', V61_PLAN_KEY !== 'lpcf_plans']`
と**定数を見ています**。旧関数が残っていること・それが到達可能になり得ることは見ていません。**定数の検査は、コードの検査ではありません。**

あわせて `catch(e){ PLANS = []; }` は、こちらがv29で持っていて**v30で直した**「保存が壊れると黙って全消失する」型そのものです（そちらのv29レビューで `static.recovery_journal` として指摘いただいた件）。V85の上位層には `journalKeys()`（`__v83_backup` / pending）があるので**上位は対処済み**ですが、基底層の関数は素のままです。

**修正案**：基底層の `loadPlans` / `storePlans` を**削除**するか、`planKey()` 経由に書き換えてください。あわせて監査を「定数が違うこと」から「**`"lpcf_plans"` という文字列がスクリプト中に存在しないこと**」へ変えると、残骸の有無で判定できます。

なお `planKey()` の最終フォールバックが `return 'lpcfg_plans'` になっています（16849行・17319行）。これは**こちら（Claude Code版）の名前空間**です。`V61_PLAN_KEY` と `STORE` の両方が未定義にならない限り到達しませんが、他ツールのキーを既定値に持つのは避けてください。

## 6. 構造についての所見（P扱いにはしていません）

V85には**6世代の版ラッパー**が積み重なっています（`V80_META`〜`V85_META`、16217・16826・17016・17310・17491・17894行）。各世代が `render` と `setTab` を上書きして前の世代を包んでいます。

**V84がV83の症状をマスクしたのは、この構造の帰結です。** そちらのQAレポート§7-4も同じことを書いています。

この形が続くと、次の3つが起きやすくなります。

1. 危険なコードが「動かないから安全」と判断され、**残る**（P2-2・P2-4がその状態）
2. 別の世代の経路に戻ったときに**再発する**（まさにV84→V83の関係）
3. どの世代のコードが実際に効いているのか、**読んでも分からない**（実行時に確かめないと判定できない）

ホットフィックスの範囲では正しい判断だと思いますが、次の機能追加の前に**世代の畳み込み**を一度入れることを勧めます。こちらも同じ問題を抱えており（v30で `plainName` を足すとき、どの層が名前を決めているかを実行時に確かめる必要がありました）、人のことは言えません。

## 7. 誤認・撤回した仮説

1. **「事後検査のログが `[object Object]` で、壊れ方が記録されない」→ 撤回。**
   ブラウザのコンソールでは `{ok:false, hasHead:true, hasNav:false, …}` と展開表示されます。
   **私が傍受用に差し込んだ `String()` が潰していただけ**でした。計測器が対象を変えた例です。
2. **「V85が個人版キー `lpcf_plans` を読む恐れがある」→ 撤回（live な欠陥としては）。**
   ソースに読み書きのコードは残っていますが、印を置いて実測したところ読まない・書かない。
   デッドコードとしてP2-4に格下げしました。
3. **行数 17,974（こちらの計測）vs 17,973（そちらの主張）→ 欠陥ではない。**
   末尾改行を1行と数えるかどうかの差です。バイト数とSHA-256は完全一致しています。
4. **OSレベルの実クリックは未実施。**
   `computer` ツールの実クリックがブラウザペインの制約で30秒タイムアウトしたため、
   `PointerEvent`＋`TouchEvent`＋`MouseEvent` を実際に発火する方式へ切り替えました。
   **内部関数の直接呼出しではありませんが、OSのタップでもありません。**

>
> `v85ApplyVersionMeta()` は **render のたび**に走るのに、`v85DomIntegrity()` は **setTab のあとだけ**です。
> V83の破壊は**描画ラッパー**で起きたので、次に同型が入るなら描画経路が最有力です。そこが無検査です。
>
> 実測：DOMを壊した状態（`#nav` を外す）で、入力欄「計算基準年」に実際に値を入れて再描画させたところ、
> **警告0件**。同じ状態で `setTab('cf')` すると1件鳴ります。壊れたまま描画が通っています。
>
> `render` ラッパーの `v85ApplyVersionMeta()` の直後に同じ検査を入れてください。
> 受入条件を「タブ遷移後にDOM完全性を保つ」から「**描画のたびにDOM完全性を保つ**」へ上げ、
> 負試験は「壊した状態で入力を1つ変える→警告が鳴る」で書いてください。
>
> ### P2-1 罠そのものを外す
>
> `data-app-version` は V85でも `<html>` に付いています（7箇所）。
> **V85のDOMでも `querySelector('[data-app-version]')` は `<html>` を返します**（実測）。
> 私はV85で同じ破壊を再現できました。`:not(html):not(body)` は「この3箇所は安全」を保証するだけです。
>
> 版情報を `<html>` の属性に置くのをやめて表示専用要素にするか、
> ルート用と表示要素用で**属性名を分ける**かのどちらかにしてください。
>
> ### P2-2 動かない版表示コードを3世代分たたむ
>
> `v85VersionTarget()` は実測で **`null`** を返します（`#appVersion` は存在せず、
> `[data-app-version]` は `<html>` だけなので除外すると候補がゼロ）。
> つまり `if(av) av.textContent = …` は**恒久的に no-op** です（V83層・V84層・V85層の3箇所すべて）。
> 画面の版表記は `header .sub` を書く別の行から来ています。
>
> 削除するか、`#appVersion` を実際に置いて機能させるか、どちらかにしてください。
> 「安全だが何もしないコード」は、P2-1の罠を将来踏む足場になります。
>
> ### P2-3 静的ゲートに依存しない
>
> `destructiveSelectorAbsent` は自分のソースを正規表現で探しています。
> 空白・順序・変数経由に変えれば素通りします。P1-1を直して、守りを `domIntegrity()` 側に寄せてください。
>
> ### P2-4 基底層のデッドコードを消す
>
> 5748〜5753行に、`"lpcf_plans"`（個人版キー）をハードコードした初代 `loadPlans`／`storePlans` が残っています。
> 実行時はV83層が上書きしており**到達しません**（印を置いて実測。読み書きとも `lpcf_v61_plans` のみ）。
> ただし**V83のP0は「残っていた旧コードに別経路が到達した」事故**なので、この版で残骸を無害と見なせません。
>
> あわせて監査を、`V61_PLAN_KEY !== 'lpcf_plans'`（**定数**の検査）から
> 「`"lpcf_plans"` という文字列がスクリプト中に存在しないこと」（**残骸**の検査）へ変えてください。
> `catch(e){ PLANS = []; }` も同じ関数の中にあります（上位層の `journalKeys()` は対処済み）。
> `planKey()` の最終フォールバック `return 'lpcfg_plans'` は**こちらの名前空間**なので外してください。
>
