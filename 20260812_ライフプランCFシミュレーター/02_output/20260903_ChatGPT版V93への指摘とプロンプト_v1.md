## 3. V93で直っていたもの（私のV91レビュー分・3件すべて）

版名のとおり、**私のV91レビューの3件は全部直っています。**

### 保存競合の同期（V91 P1-1／V92でも未解決だった分）

| 手順 | v93の実測 |
|---|---|
| 別タブの有効な保存が着地（storageイベント未配送）→ 保存を押す | `v93-revision-conflict` の警告、保存は中止、**画面は即座に同期**（別タブGが入り3件に） |
| もう一度保存を押す | **成功**（通知0件、別タブGを保ったまま4件目が入る） |

V91・V92では**3連続で失敗し、画面も同期されず、タブを離れて戻るまで保存できませんでした**。V93は「競合→即同期→再保存が通る」になっています。通知の文面が約束したことを、同じ処理の中で実行するようになりました。

### 資金判定の引数（V91 P1-2）

価格5,000万円・自己資金0・借入0で `fundingState` が `{level:"insufficient", gap:50000000, ready:false}` を返します。V91・V92は `{level:"ready", gap:0}` でした。`audit().checks` に **`fundingShortageProbe`** という負試験も追加されていて、同じ誤りが再発したら監査で落ちる形になっています。**指摘を1回直すだけでなく、再発を検知する試験を足したのは良い対応だと思います。**

### 実DOM監査（V91 P2-1）

`audit().checks` に **`workTypeCurrent` が入りました**（V91・V92には無く、自作フィクスチャの `workTypeMatrix` だけでした）。実画面の働き方ボタン6件すべてを同名「働き方」に壊すと、**`audit().ok` が false になります**（V91・V92は true のまま）。V87の発端だった不具合が、監査で検出できる状態に戻りました。

### ヘッダの版番号二重表示（V91 P2-2）

`ライフプラン・シミュレーター V93 保存競合同期・資金判定・実DOM監査正本化版` — 「V93 V93」の重複が消えています。

## 4. 残っているもの（V92から未解決の3件）

V93は私のV91レビューへの反映版なので、**V92レビューの分が未反映なのは時間順として自然**です。事実だけ記録します。

### P1｜税・社会保険料率の負値が通り、手取りが増える

年齢40歳・年収600万円・生活費300万円で `tax.hokenRate` を **−50** にすると：

| 状態 | `decisionValidation` | 1年目の税・社会保険料 | 1年目の手取り |
|---|---|---:|---:|
| 基準（健保 10.306%） | `ok:true` | 1,421,680円 | 1,578,320円 |
| **健康保険料率 −50%** | **`ok:true`・blocking 0** | **105,800円** | **2,894,200円** |

手取りが年132万円増えます。`semanticDecisionIssues` は住宅費・資産・費用を見ますが、**税・社会保険料率を見ていません**。あわせて `inputSpec` の `/(?:rate|growth|inflation)/i` 分岐が `tax.hokenRate`・`retire.bonusRate`・`retire.youngerRate` に `min="-99.9"` を付けており、**DOM側が負の入力を誘っています**。

**これだけは直したほうがよいと思います。** 他の残件と違い、**結果の数字が静かに良くなる**経路だからです。異常値とはいえ、詳細設定の前提を触る利用者は実在します。

直し方：(a) `semanticDecisionIssues` に税・社会保険料率と比率系の下限0を追加。(b) `rate` 総当たり分岐をやめ、**負を許す欄を明示列挙**にする（負が正当な「変動率」と負が無意味な「料率・割合」は名前では見分けられません）。

### P2｜保存経路が共通バリデータを通らない

`house.mgmtFee = -1200000` で `decisionValidation(PARAMS).blocking` は `["管理費"]` を返すのに、**保存ボタンで保存され、通知は0件**でした（保存領域に「負の管理費」が入る）。

V92で私はこれをP1としましたが、**P2へ引き下げます**。判断（準備度）とJSON取込は正しく止まるので、**利用者が誤った結論を読むことはありません**。保存できてしまうプランは、開き直しても準備度が止めます。「保存不可」とQAレポートに書いてあったのに実際は保存できた、という**報告の正確さ**の問題を、私が製品の危険度と混ぜて重く見せていました。

### P2｜保存領域を外部から空にすると、そのセッションでは保存できなくなる

通常どおり保存 → 別タブや設定画面から保存領域を空にする → 保存を押すと、`v93-revision-invalid`「保存領域が読み取れない状態へ変わったため保存を中止しました」で保存されません。`focus` でも `resync()`（明示的に呼んで `false`）でも回復せず、**リロードが必要**です。3連続で試して3回とも同じでした。

**保存領域は壊れているのではなく、空です。** `strictRaw(null)` の `kind:"missing"` を、`storePlans` の revision 照合と `resync` が `ok:false` としてだけ扱っています（`loadPlans` は正しく区別しています）。

こちらもP2へ引き下げます。**データは失われず**（利用者自身が消した後の話）、リロードで回復するためです。ただし「壊れている」という文面は誤りなので、**メッセージだけでも「もう一度開き直してください」に変えると親切**だと思います。
