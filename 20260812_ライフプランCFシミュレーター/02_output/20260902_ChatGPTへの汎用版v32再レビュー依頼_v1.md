## 2. P1-2 控えの保全

`updateBackup(payload)` を作り、**控えを書く前の生値を退避**してから更新します。
新しい控えの読み戻しに失敗したら、**旧控えを書き戻し、その書き戻しも読み戻して確認**します。
戻せなければ `pending` と `marker` を残し、**次回起動時に正常な主領域から作り直す**（`repairBackupIfMarked`）。

追加した保存キー：`lpcfg_plans_pending` / `lpcfg_plans_marker` / `lpcfg_plans_lock`。

通知は「何が保存され、何が未保全か」を分けて書きます。

- 旧控えを維持できたとき：「控えは**ひとつ前の内容のまま**残しています」
- 戻せなかったとき：「控えを作り直す印を残しました。次に開いたときに作り直します」

実測（故障注入）

| 故障 | v31 | v32 |
|---|---|---|
| 控えへの書込みが**1回だけ** `[]` に化ける | 控え `[]`（最後の正常な控えを喪失） | **控え `["旧"]` を維持**＋`planbakfail` |
| 控えへの書込みが**毎回** `[]` に化ける | 控え `[]`・印なし | 控えは戻せないが**印が残り、次回起動で `["新"]` に作り直された** |

**★この2つは別の故障だと気づくのに手間取りました。** 最初は前者を「毎回壊れる」故障で書いてしまい、
**旧控えを書き戻す操作も同じように壊れる**ので、どんな実装でも旧控えは維持できません
（＝満たせない試験を作っていた）。ご提示のシナリオは `once` 付きの1回だけの故障でした。
また「書込みが**無視**される」故障だと**旧控えがそのまま残る**ので印は不要です。
**「壊れて別の値になる」と「書けずに元のまま」は別の故障**として分けました。

## 3. P1-3 複数タブ競合（対策3段＋正直な留保）

ご提案どおり3つ重ねました。

1. **revision（保存の起点）**：`PLANS` を作った時点の主領域の生値を `PLANS_REV` に持ち、
   書く前に一致を確かめる（compare-and-set 相当）。
2. **期限付き協調ロック**：`lpcfg_plans_lock` に `{id, until}`。期限4秒なので、
   タブが落ちても自然に回収されます。期限内の他タブが持っていれば保存を見送ります。
3. **最終読み戻し**：主領域の読み戻しに成功したあと、**控えを更新する前にもう一度**主領域を確認。
   別タブの有効な内容になっていたら、控えもメモリもそちらへ揃えます。

あわせて `storage` イベントを購読し、別タブの保存を検知したら画面の一覧を合わせます（`planexternal`）。

実測

| 試験 | v31 | v32 |
|---|---|---|
| 窓A：自分の保存開始**前**に別タブが書いた | **保存 true・`[旧,このタブ]` で上書き** | **保存 false・`[旧,別タブ]` のまま・メモリ同期・`planconflict`** |
| 窓B：読み戻し成功後・控え更新前に別タブが書いた | primary `[旧,別タブ]` / backup `[旧,このタブ]` / メモリ `[旧,このタブ]` の**三者不一致** | **primary＝backup＝メモリ が一致**・保存 false |
| 期限内の他タブのロック | 機能なし | **保存を見送り `planlock`** |
| 期限切れのロック | 機能なし | **回収して保存できる** |
| 別タブが不正値を書いた | 書く前へ戻す | 書く前へ戻す（維持） |
| 競合が無い通常保存 | 成功 | 成功（締めすぎていない） |

### 3.1 留保：ご提示の窓Aの故障注入は、そのままでは成立しません

ご提示のハーネスは、**自分の `localStorage.setItem` の実行中**に別タブの書込みを割り込ませています。

```js
localStorage.setItem = function(k,v){
  if(k===STORE.plans && once){ once=false; localStorage._rawSet(k,other); }
  return orig(k,v);            // ← 自分の値が最後に入る
};
```

この順序では、**最後に自分の値が入るので、別タブの内容は正当に上書きされます。**
どんな実装でも「保存 false・primary は別タブのまま」にはできません。
そして **localStorage の書込みは同期でストレージ・ミューテックスに守られる**ため、
**この割り込み順序は実際のブラウザでは起こりません**（同一オリジンの別タブは別のイベントループで、
`setItem` の内側に入り込めない）。

そこでこちらの試験は、別タブの書込みを**自分の commit の外**で起こす形にしました。
これが現実に起こる窓で、revision 照合で止まります（上表のとおり）。

**「ロックを無視するタブが、自分の書込みの最中に書く」ケースは、
localStorage に本物の CAS が無いため検出できません。** ご指摘のとおりです。
緩和はロックと revision まで、と割り切っています。この判断が妥当かご意見をください。

## 4. P1-4 未入力で住宅ローン控除を肯定しない

`isBlank(P)` ／ 住宅購入OFF ／ 物件価格0 ／ 借入合計0 のいずれかなら、判定せず断りを出します。

> **まだ判定できません。** 住宅購入をONにして、物件価格と借入額を入れると、
> 住宅ローン控除の要件と控除額をここに出します。いまの0円は計算の結果ではなく未入力の状態です。

実測：未入力で「住宅とローン」「年次表」「診断」の3タブを見て、
`要件を満たしています` / `控除される総額` / `適用できます` / `尽きません` /
`破綻ではありません` / `乗り切れます` が**すべて0件**。
入力後は「要件を満たしています／満たしていない要件があります」が**出る**（抑制しすぎの確認）。

**v31はCF表と診断を抑えたのに、この控除ブロックだけ漏れていました。**
「症状の出た場所だけを覆っていないか」を直すたびに確かめる、という自分のルールに反しています。
