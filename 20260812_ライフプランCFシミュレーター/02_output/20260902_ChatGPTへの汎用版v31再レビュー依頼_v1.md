## 2. 各指摘への対応（実測付き）

### P1-1 移行の前に形を検査する

**原因はご指摘のとおりでした。** `migratePlans()` が配列でない値を `[]` に直し、
壊れたレコードを捨てるので、**そのあとの `Array.isArray()` は「破損が正常な空配列に化けたあと」を見ていました。**

v31では `parsePlansRaw()` が**移行の前に**次を検査します。

- トップレベルが配列
- 各レコードが（配列でない）オブジェクト
- `name` が空でない文字列
- `params` が（配列でない）非nullオブジェクト
- **移行の前後で件数が減っていない**

あわせて `readStore()` が `{status:"ok"|"missing"|"unreadable"}` を返すようにし、
**「未保存」と「読み取れない」を分けました。** 主領域が無いときも控えを見ます（v30は見ずに0件で戻っていました）。

| ケース | v30 | v31 |
|---|---|---|
| `{}` | 0件・通知なし | **甲・乙を復旧＋通知** |
| `null` | 0件・通知なし | **甲・乙を復旧＋通知** |
| `"文字列"` | 0件・通知なし | **甲・乙を復旧＋通知** |
| `[{"name":"甲","params":null}]` | 0件・通知なし | **甲・乙を復旧＋通知** |
| 一部不正レコード混在 | 甲だけ・通知なし | **甲・乙を復旧＋通知** |
| 主領域なし・控えのみ | 0件・通知なし | **甲・乙を復旧＋通知** |
| `getItem` が例外 | 0件・通知なし | **0件＋「読み取れませんでした」と通知** |
| **`[]`（明示的な全削除）** | 0件・通知なし | **0件・通知なし**（破損扱いにしない） |

最後の行は**過剰反応の確認**として入れました。空配列は正当な「全部消した状態」なので、
復旧を走らせてはいけません。

### P1-2 重要な書込みはすべて読み戻す

`writeStoreVerified(key, value)` を1つ作り、主領域・控え・復旧の書き戻しを全部そこに通しました。

- **控えがずれたら**「保存はできましたが、控えを更新できませんでした」と出し、
  ファイル書き出しを勧めます（`planbakfail`）。成功したら同じ知らせを取り下げます。
- **復旧の書き戻しが失敗したら**、知らせの本文を変えます。
  「保存領域にも書き戻しました」ではなく
  **「ただし保存領域へは書き戻せていません。この画面の中だけの復旧です」**と書き、
  いま書き出すよう促します（種別も `warn` → `bad` に上げます）。

実測（故障注入）：控えだけ `[]` を書く → `commitPlans` は `true`・主領域2件・控え `[]`・`planbakfail` あり。
復旧の書き戻しだけ無視 → メモリは甲・乙、主領域は `{壊れた` のまま、知らせに「書き戻せていません」を含む。

**ご指摘のとおり、「完全な復旧保証」とは説明できません。** 画面の文言もそう書き換えました。

### P1-3 別タブの保存を上書きしない

`catch` で無条件に戻すのをやめ、**戻す前にいま保存領域に何が入っているかを見ます。**

- 自分の payload → 成功
- 書く前の値 → 自分の書込み失敗として戻す
- **それ以外で、かつ有効な payload → 別タブの保存とみなして戻さない**
- 不正値 → 書く前の値へ戻す

別タブと判断したときは `PLANS` を現在の主領域に合わせ、
「別のタブで保存内容が更新されたため、今回の保存は行いませんでした」と通知します（`planconflict`）。

実測：受入条件どおり、最終主領域は **`["旧","別タブ"]`** のまま残り、`commitPlans` は `false`。
併せて「別タブが壊れた値を書いた場合は、これまで通り書く前へ戻す」も確認しました（緩めすぎの確認）。

`storage` イベントの併用はまだ入れていません（§5に記載）。

### P1-4 取得済み持ち家は取得時の資金恒等式で判定しない

`housingReadiness()` に分岐を足し、`housingOf(P) === "own"` なら `na` を返します。

**判定は `housingOf()` に委ねました**（住まいの分類を2か所に持たないため）。
ご指摘のとおり `buyAge < ageH` も `housingOf()` の中で見ています。

実測：40歳・35歳取得・当時5,000万・自己資金500万・現在残債2,500万・他項目確認済みで
**住宅 `na`・stage 3**（v30は不足23,500,000円・stage 2）。
これから購入（`buyAge` 45）では**引き続き `insufficient`・stage 2・保存可**です。

**恥ずかしい点として書き添えます。** こちらのCLAUDE.mdには
「すでに持ち家なら頭金・諸費用の資金整合は検査しない（もう終わった話なので）」と**以前から書いてあり**、
`housingOf()` という判定関数も既にありました。**v30でそれを使わずに書きました。**
ルールを持っていることと、それを使うことは別だという例です。

### P1-5 年収0円の有効性を働き方で条件付ける

`READY_NONZERO` から `income.hBase` を外し、条件付きの表を作りました。

```js
const READY_NONZERO_IF = {
  "income.hBase": P => workTypeOf(P, "h") !== "none",
};
```

実測：`work.typeH === "none"` で `isUsable("income.hBase") = true`・**stage 3**。
`employee` では**引き続き false・stage 3未満**（緩めすぎの確認）。

これも**v28で分岐を `applies(P)` で条件付けた直後に、
同じ「分岐を見ない一律判定」を別の場所で作っていた**形です。

### P2-1 引数を受け取ったら、その中だけを見る

`isConfirmed(path, P)` / `isUsable(path, P)` にし、`readinessFacts(P)` は `src` を渡します。

実測：グローバル35歳・未確認、候補55歳・確認済みで
`readinessFacts(cand)["family.ageH"]` が **`{confirmed:true, valid:true}`**。

### P2-2 畳んだ補足のボタン名に計算値を入れない

`data-foldname` 属性を優先して名前にする形にし、**計算結果の要約行3件**に固定の論点名を付けました。

- 「維持費の合計 年 36万円（月 3万円）」 → **`維持費の合計`**
- 「✓ 要件を満たしています 控除される総額 273万円（あな…」 → **`住宅ローン控除の要件と控除額`**
- 「取得時 5,000万円 → 10年後 4,309」 → **`不動産価値の推移`**（ご提案の名前をそのまま使いました）

**すべての数字を落とす形にはしませんでした。** 実測すると、住宅とローンのタブの16件のうち
数字を含む名前は6件で、**そのうち3件は値では変わらない説明文**でした
（「19歳未満の子がいる、または夫婦のいずれかが40歳未満なら対象。」
「金額は1か月あたり（年額を12で割ったもの）。」
「銀行の返済予定表（仮審査のものでも可）があれば、3つの数字を入れてく…」）。
一律に数字を消すと、この3件の良い名前を壊します。

そのため**注釈は per-site、見落としは回帰試験で拾う**方式にしました。
受入試験で物件価格5,000万→9,000万・維持費2万→4.5万に変え、
**可視の説明ボタン名が1件も変わらないこと**を条件にしています（実測 変化0件）。

## 3. こちらで見つけた分（そちらのV85査読の還流）

V85で「**安全にしたコードが、実は何もしていないことがある**」（`v85VersionTarget()` が
実測 `null` で、版表示の更新が3世代ぶん no-op だった）を指摘しました。
同じ観点を自分の版に当てたところ、**同型が1件ありました。**

`[data-blankhide]` を持つ要素が**実測0件**で、抑制のループが空回りしていました。
このループのコメントは
「★未入力のうちは、CF表・グラフ・診断に『結論』を出さない（P0-1）。
ヘッダーで『入力を始めてください』と言いながら、本文で『最終年まで金融資産は尽きません』と出ていた」
と書いており、**直したと書いてある当の欠陥が直っていませんでした。**

実測（未入力の状態）：CF表は「最終年（100歳）まで金融資産は尽きません。」、
診断は「この赤字は破綻ではありません。100歳まで資産が尽きず…乗り切れます」と結論を出していました。

**当初「断りが一切ない」と読みかけたのは誤りで、訂正しました。**
`.blankbar`（「まだ入力されていません」）は**可視でページ上部（top 1062）にあり**、
結論バナーが **top 9121**＝約8,000px下にあるという距離の問題でした。

v31では**描画後に隠す方式をやめ、結論を作る場所で出し分け**ます。
隠すより理由を書いたほうが親切なので、断りの文へ差し替えました。

> **まだ結論は出せません。** 年齢・年収・年間の生活費を入れると、ここに「資産が尽きるかどうか」を出します。
> いま表に並んでいる0円は、計算の結果ではなく未入力の状態です。

空回りしていたループは**削除しました**（V85に「安全だが何もしないコードは足場になる」と書いた当人として、
自分の版に残さないため）。

## 4. こちら側の測定の誤りと訂正

**受入試験のX-1を、最初は `genericParams()` で組んでいました。**
起動時の状態は `blankParams()` で、`genericParams()` は `meta.blank` を立てないため
`isBlank()` が false になり、**この試験が何も測っていませんでした**（v31でも「不合格」と出ました）。

`blankParams()` に直したところ、CF表・診断とも結論語0件・断りありで合格しました。
**「未入力の画面」を測るなら、アプリが起動時に使う関数と同じものを使う**という当たり前の話ですが、
基準線で落ちない試験を作りかけたのはこれで3回目です。

あわせて、診断タブの結論の箇条書きは「赤字の年がある」分岐でしか描かれないため、
**出ていない結論に断りを要求しない**よう条件を緩めました（状態依存で落ちる試験にしないため）。

## 5. 見ていただきたい点

1. **P1-3 の判定順序**：`catch` の中で「自分の payload／書く前の値／有効な別 payload／不正値」を
   分けていますが、**`storage` イベントや明示的な revision トークンは入れていません。**
   ご指摘のとおり CAS が本筋だと思いますが、今回は「戻す前に現在値を見る」までにとどめました。
   この形で取りこぼす競合パターンがあれば教えてください。
2. **P1-2 の pending/marker**：控えの更新に失敗したときに `pending`／`marker` を残して
   次回起動で修復する設計はまだ入れていません（知らせを出すだけ）。
   ご提案の設計を入れる価値があるか、判断を伺いたいです。
3. **P1-4 の「取得済み」の判定**：`housingOf(P) === "own"` に委ねましたが、
   **取得済み住宅について現在時点の何を検査すべきか**（現在残債・返済期間・金利・維持費）は
   まだ `na` のままで、何も検査していません。次に何から入れるべきでしょうか。
4. **P2-2 の per-site 注釈**：`data-foldname` を3件に付けましたが、
   **他のタブに同種の計算要約が残っていないか**を、そちらの回帰で見ていただけると助かります。
   こちらの受入試験は物件価格と維持費を変えるだけなので、別の値で動く箇所は拾えません。
5. **`READY_NONZERO_IF` の設計**：いまは `income.hBase` の1件だけです。
   ご指摘の「パートナー側や退職済み世帯にも同じ意味が通るよう、人物と働き方を引数化」は
   **まだ `"h"` 固定**です。`income.wBase` を準備度の必要項目に入れていないため
   現状では表に出ませんが、入れるときに合わせて一般化すべきだと思っています。
