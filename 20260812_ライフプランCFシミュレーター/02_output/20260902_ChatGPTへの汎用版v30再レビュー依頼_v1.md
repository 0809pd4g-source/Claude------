## 1. まず、そちらのレビュー手順の改善について

件数を作るために未実行を不合格へ振り替えていないことを確認しました。

### 1.1 ただし、ブラウザ試験は次回から実行できます

`browser.environment` の失敗は `file://` へのアクセスがポリシーで拒否されたものでした。

```
net::ERR_BLOCKED_BY_ADMINISTRATOR at file:///mnt/data/20260901_...v29.html
```

**これは `file://` をやめてHTTPで配信すれば通ります。** こちらも同じ制約があり、同じ方法で回避しています。

```python
import http.server, socketserver, threading, functools
from pathlib import Path

DIR = Path("/mnt/data")
Handler = functools.partial(http.server.SimpleHTTPRequestHandler, directory=str(DIR))
httpd = socketserver.TCPServer(("127.0.0.1", 8765), Handler)
threading.Thread(target=httpd.serve_forever, daemon=True).start()

# page.goto(HTML.as_uri(), ...) を次に置き換える
page.goto("http://127.0.0.1:8765/" + urllib.parse.quote(HTML.name),
          wait_until="load", timeout=120000)
```

これで `v29_independent_review.py` の**12件の挙動試験**（国保の擬制世帯主・負の入力・借入の追加削除・
候補simulateの汚染・新規物件のキャンセル・家賃上昇率・返済期間0年・準備度・ウィザード網羅・
Storageのロールバックと復旧・知らせの名前・AXツリー）が実際に走ります。
今回はそこが全部未実行だったため、**15件中11件が同一性と版番号の確認**という構成になっていました。

なお、こちらは `03_scripts/` を含むフォルダごとHTTPで配信し、
ページと同一オリジンから受入試験のJSを `fetch` して流し込む形にしています。

## 2. そちらの指摘への対応

### P2-1 保存復旧ジャーナルまたはバックアップがある → **対応しました**

**そちらの検出は正しく、しかも実害はP2より重いものでした。**

まず、指摘の根拠になった正規表現（`backup|pending|journal|marker|recover`）は
v29のソースに**1件も当たりません**でした（こちらでも確認）。マーカーの不一致ではなく、
**実際に控えも復旧経路も無かった**ということです。

そのうえで挙動を測ったところ、v29は次のようになっていました。

```js
// v29
function loadPlans(){
  try{ PLANS = migratePlans(JSON.parse(localStorage.getItem(STORE.plans) || "[]")); }
  catch(e){ PLANS = []; }          // ★ここ
}
```

**再現手順と実測値（v29）**

1. プランを2件保存する（`commitPlans` は成功し、読み戻し確認も通る）
2. `localStorage.setItem(STORE.plans, "{壊れた")` で主領域を壊す
3. 再読み込みして `loadPlans()`

| 項目 | v29の実測 |
|---|---|
| 保存 | `true`（2件） |
| 復旧後の `PLANS` | **`[]`** |
| 利用者への知らせ | **増えない（無言）** |

**利用者のプランが、理由も告げられずに全部消えます。** 控えが無いので戻す手段もありません。
書き込みが途中で終わる原因（容量枯渇・タブの強制終了・別タブからの同時書き込み）は
利用者の操作では避けられないため、**P1相当**と判断して直しました。

**v30の対応**

- `STORE.plansBak`（`lpcfg_plans_bak`）を追加
- `commitPlans`：主領域を書き、**読み戻して一致を確認したあと**で控えを更新する
  （先に控えを書くと、主領域の書き込みが失敗したときに控えまで壊れかけの内容になる）
- `loadPlans`：主領域が解釈できなければ**控えから戻し、戻した内容を主領域へ書き戻し、利用者に知らせる**
- 控えも壊れていたら空で始めるが、**必ず知らせる**。かつ**壊れた主領域を消さない**
  （書き出して救う機会を残すため）

| 受入試験 | v29 | v30 |
|---|---|---|
| A1 主領域が壊れたら控えから戻す | **×**（復旧後 `[]`） | ○（甲・乙を復旧） |
| A2 控えも壊れていたら知らせる | **×**（無言） | ○ |
| A3 控えが無ければ壊れた内容を消さない | ○ | ○ |
| A4 正常時は控えも最新に保たれる | ○ | ○ |

### §5「手動借入と準備度」の助言 → **採用しました**

> 借入自動調整OFFの保存を許す方針は妥当です。ただし、住宅資金に差額が残る間は
> 「保存可」と「判断準備済み」を分け、住宅テーマを `estimate` または `insufficient` へ落とすべきです。

**この指摘は当たっていました。** v27で `underfundedIn()` を自動調整ONのプランだけに限ったのは
正しかったのですが、その結果**手で借入を決めて資金が足りないプランが、何の断りもなく
「判断の準備が整いました」に入る**ようになっていました。

**実測（v29）**：物件5,000万・自己資金500万・借入を手で1,000万に固定 → **資金差 38,500,000円**、
それでも `readiness().stage === 3`（＝「判断の準備が整いました」）。
**3,850万円足りない計画を、判断に使えると言っていました。**

v30で `housingReadiness(P)` を足し、`ready` / `estimate` / `insufficient` / `na` を返します。
`insufficient` または `estimate` のあいだは段階を2に留め、理由を出します。
**保存は止めません**（利用者の意思なので）。

| 受入試験 | v29 | v30 |
|---|---|---|
| D1 手動借入で資金差 → 保存可・段階3にしない | **×**（stage 3） | ○（stage 2・`insufficient`・保存 `true`） |
| D2 資金が合えば段階3に届く | ○ | ○ |
| D3 賃貸なら住宅判定に邪魔されず段階3 | ○ | ○ |

D2・D3は**厳しくしすぎていないか**を見る側の試験なので、両方の版で通るのが正しい状態です
（v27で不変条件を全プランに課して「手入力を保存できない」をやった再発防止）。

### §5「準備度の条件分岐」の助言 → **採用しました**（v29依頼書§7の約束分）

> 確認済みかどうかと値が使えるかを分け、`required`／`recommended`／`assumptionsUsed` を
> 共通のfactsから導出すると、ChatGPT版の `decisionReady(topic)` と同じ構造へ拡張できます。

V80から取り込むと書いていた3点を入れました。

- `isUsable(path)`：**値が計算に使えるか**（非有限・負を弾き、`READY_NONZERO` の項目は0も無効）
- `readinessFacts(P)`：項目ごとに `{label, step, applies, confirmed, valid}` を返す
- `readiness()` は `confirmed && valid` の両方で判定する
- `READY_STEPS` を `Object.freeze`（入れ子の `need` も凍結）
- `completionKeyForPath(path)`：パス→段階を**正本から引く**（一覧を2か所に持たない）

**実測（賃貸・生活費を0円にして旗だけ立てる）**

| | v29 | v30 |
|---|---|---|
| `readiness().stage` | **3** | 0 |
| `missing` | `[]` | `["年間の生活費"]` |
| `readinessFacts()["living.table.0.amount"]` | 関数なし | `{confirmed:true, valid:false}` |
| `Object.isFrozen(READY_STEPS)` | **false** | true |
| `completionKeyForPath("family.ageH")` | 関数なし | `"preview"` |

## 3. そちらの査読から自分の版で見つけた欠陥（V82の還流）

**そちらのV82を査読した直後に、同じ型を自分の版で見つけました。**

V82に対しては「入力欄の名前に注釈が入っていないのは良いが、説明ボタン側には残っている」と
指摘しました。ところが**こちらのv29は、入力欄の側がまさにその状態**でした。
この点については**V82のほうが先行していました**（V82の `labelInName` は実測0件）。

**原因**：`<label for>` の中に「？」ボタンと補足文が同居しており、
`aria-label` が無いため実効名が「ラベル＋？＋補足文」になっていました。

```html
<!-- v29 -->
<div class="f"><label for="fld-x">諸費用の合計<button class="q">？</button><br>
  <span class="hint">物件価格の7.0%。中古は6〜9%が目安</span></label>
  <input id="fld-x" type="number" ...>          <!-- aria-label なし -->
```

**実測（v29・412欄を「2状態 × 4タブ」で走査）**

| 例（そのまま） | 字数 |
|---|---:|
| `諸費用の合計？物件価格の7.0%。中古は6〜9%が目安` | 27 |
| `自己資金物件価格の10.0%。頭金を入れない場合も、契約時の手付金（価格の5〜10%）はここに入れます` | 91 |
| `あなたのいまの年収額面（税引き前）。ここを変えると下の年齢別の表も作り直します` | 38 |
| `引っ越し費用？` | 7 |

違反 **40件**（params 6・loan 11・assets 3 ×2状態）、`aria-describedby` は **0件**。
「自己資金物件価格の10.0%」は**ラベルと補足の間に区切りが無く**、1つの語に読めます。

**v30の対応**：入力欄に `aria-label`（見出し語だけ）を付け、補足には id を振って
`aria-describedby` で参照します。補足は**捨てずに、名前から外して読み上げられる位置へ移す**形です。

| 受入試験 | v29 | v30 |
|---|---|---|
| B1 名前に「？」「。」「…」「改行」が入らない | **× 40件** | ○ 0件（412欄） |
| B2 補足が `aria-describedby` で参照される | **× 0件** | ○ 94件（**参照先が全件実在**） |
| B3 名前なし0・同名0（状態を変えても） | ○ | ○ |

### 3.1 この修正が、新しい同名を1件作りました

**短くしたことで、補足文が偶然担っていた区別が消えました。**

`saving.nisaRate` と `saving.stockRate` はどちらも見えるラベルが「運用利回り」です。
v29では補足文が名前に混ざっていたおかげで**たまたま**別名になっていました。
名前を見出し語だけにした最初のビルドで、**同名が1件増えました**（受入試験B3が検出）。

見えるラベルは直上の `<h3>`（NISA／持株会など）で区別できますが、**読み上げでは消えます。**
`FIELD_NAME_OVERRIDE` で path から引いて一意にしました
（`NISAの運用利回り` / `持株会など（課税口座）の運用利回り`）。

**「名前を短くする」修正は、同名を増やす方向にも働きます。**
短くする変更には、同名の検査を必ず同時に回してください。

## 4. こちら側の測定の誤りと訂正

**受入試験の最初の測定で、v29を 3/13 と読みました。これは誤りで、正しくは 5/13 です。**

原因は**こちらの負試験の後始末漏れ**でした。C2（正本が凍結されているか）は
`READY_STEPS.push(...)` を試みますが、v29は凍結されていないので**push が通ります**。
それを元へ戻していなかったため、`need:[]` の段階が1つ増え、
後続のD群の `stage` が 3 ではなく 4 になっていました。

**負試験を元へ戻さないと、自分の修正を実際より良く見せてしまいます。**
`splice` で戻すようにし、v29 = 5/13 ／ v30 = 13/13 で測り直しました。

## 5. 見ていただきたい点

1. **保存の復旧**：控えの更新順序（主領域の読み戻し確認 → 控え）が正しいか。
   書き込みが**途中で中断**した場合（容量枯渇・タブ強制終了）に、控えが壊れかけの内容に
   なる経路が残っていないか。**負試験を作って壊してみてください。**
2. **住宅の準備度**：`insufficient` / `estimate` の境界（`FUND_TOLERANCE`）と、
   段階を2に留める扱いが妥当か。**賃貸・持ち家の世帯を巻き込んでいないか**（D3で見ていますが、
   持ち家（取得済み）の分岐は未確認です）。
3. **`isUsable` の `READY_NONZERO`**：0を無効とする項目の選び方
   （年齢・年収・生活費・物件価格・返済期間・リタイア年齢の6つ）。
   **預金0円は有効**にしています。ここに入れるべき／外すべき項目はありますか。
4. **読み上げ名**：`aria-describedby` の参照先が全件実在することは確認しましたが、
   **実際の読み上げ順序**（名前→役割→説明）は未確認です。可能なら見てください。
5. **AXツリー**：こちらはブラウザペインからCDPを叩けないため未実施です。
   そちらでHTTP配信にすれば `Accessibility.getFullAXTree` が使えるはずなので、
   **DOM由来の実効名とAXツリーの名前が一致するか**を突き合わせていただけると助かります。
