## 2. P1（そちらの試験を走らせて再現・修正）

### 取得済み持ち家で、いまの借入が計算できない状態でも「判断の準備が整いました」になる

**v32での実測**（そちらの試験コードそのまま）

```
housingReadiness → {level:"na", gap:0, note:""}
readiness()      → stage 3「判断の準備が整いました」／missing []
```

前提は「現在40歳・35歳で取得済み・残債3,000万円・返済期間0年」です。さらに測ると、

- 初年度返済 **0円**、返済総額 **0円**、利息合計 **0円**
- つまり**残債3,000万円が返済ゼロとして黙って計算から消えていた**
- それでも診断画面は「77歳で資産が尽きます」等の**断定的な結論**を出す
- 保存だけは `badLoansIn` が「返済期間が 0 年」で止める

**原因**は v31 で自分が入れた修正の副作用でした。「取得済みなら取得時の資金恒等式で判定しない」を入れるとき、`housingReadiness` を `na` で早期リターンさせ、あわせて `READY_STEPS` の住宅まわりの要件を丸ごと `housingOf(P) === "buy"` 限定にしました。

```js
["house.price","物件価格", P => housingOf(P) === "buy"],
["house.loans.0.years","返済期間", P => housingOf(P) === "buy"],
```

その結果、**取得済み世帯では返済期間を誰も検査しなくなりました。** 直したかったのは「過去の帳尻（頭金・諸費用の一致）」なのに、**「現在の条件（いまの借入が計算できるか）」まで一緒に落としていた**わけです。

そちらの設計回答の「過去の取得資金恒等式は判定しません。一方、現在残債が正数なら残存期間・金利段階…を確認し、足りなければ estimate へ落とす」がそのまま答えになっていました。

**v33での修正**（3点）

1. `ownedHousingReadiness(P)` を追加。残債が正の借入だけを対象に、返済期間1年以上・金利段階が数値であることを確認し、駄目なら `insufficient` を返す。完済済み（残債0）は検査しない。
2. `READY_STEPS` の返済期間要件を `P => housingOf(P) === "buy" || hasLoanBalance(P)` に広げた。
3. `readiness()` に**保存の入口と同じ検査**（`badLoansIn`）を通し、保存できない値では段階を1に抑える。**判定を2本持たない**ようにした（v32は保存だけ止めていたので、保存できない入力のまま診断だけが読めた）。

**v33での実測**

| 状態 | v32 | v33 |
|---|---|---|
| 取得済み・残債3,000万・返済期間0年 | stage 3 / housing `na` | **stage 1 / housing `insufficient` / missing「返済期間」** |
| 同じ状態で返済期間を30年に直す | stage 3 | stage 3（元に戻る） |
| 取得済み・完済済み（残債0） | stage 3 | stage 3（妨げない） |
| これから購入・返済期間0年 | stage 1 | stage 1（従来どおり） |

## 3. P2（そちらの指摘）

### `pending` が書かれるだけで復旧に使われない

そちらの指摘（`pending_mentions: 6, read_markers: 0`）のとおりで、**こちらもv32の依頼書 §7 に未着手として書いていた**ものです。「台帳に載っているが効いていない」状態でした。

そちらの設計回答「markerが未完了を示し、pendingが厳格検証に通り、primaryが欠損・破損している場合に限って復旧候補とします。正常なprimaryや他タブの新しい値より優先してはいけません」をそのまま実装しました。

`pendingPlans()` を追加し、`recoverPlansFromBackup` の**控えも駄目だった場合の最後**に置いています。

| 条件 | v33の挙動 |
|---|---|
| 主領域も控えも破損＋marker＋pendingが有効 | pendingから復旧し、主領域へ書き戻して控えも作り直す |
| markerが無い（pendingだけある） | **使わない**（従来どおり「壊れています」で0件） |
| 正常な控えがある | **控えを優先**（pendingは見ない） |

## 4. 設計回答への対応

### 0円の年収の有効性を人物ごとに一般化

そちらの「人物と働き方で条件付けるべきです。パートナーなしは非適用、働いていない・退職済みは確認済み0円を有効、会社員は0円を要確認」に沿って `zeroIncomeNeedsCheck(P, who)` を作り、`income.hBase` と `income.wBase` の両方に同じ規則を当てました。

v31・v32は**本人だけを条件付けており、パートナー側は規則の外**にありました。規則を持っていることと、もう一人にも使っていることは別だという、こちらが何度も繰り返している型です。

| 条件 | 0円は有効か |
|---|---|
| パートナー不在 | 有効（そもそも当てはまらない） |
| パートナーあり・働かない | 有効 |
| パートナーあり・会社員 | 要確認 |
| 本人・働かない | 有効 |
| 本人・会社員 | 要確認 |

自営業の0円は「確認済みなら有効だが注意表示」というご提案でしたが、**v33では会社員と同じく要確認のまま**にしました。注意表示の仕組みを別途持たずに有効化すると、0円のまま段階が上がってしまうためです。ここは意図的な逸脱として記録しておきます。

### ロック期限4秒

「期限そのものより、各書込み前後でロック所有権とprimary revisionを再確認することが重要」に同意し、**書込みの直前にロック所有権を確かめる**処理を足しました。期限が切れて別のタブに取られていたら、書かずに降ります。期限は4秒のままにしています（保存は同期で数ミリ秒なので、長くすると他のタブを待たせる時間だけが伸びるため）。

## 9. 見てほしいところ

1. **`ownedHousingReadiness` の検査項目が足りているか。** いまは残債が正の借入について「返済期間1年以上」「金利段階が数値」だけを見ています。そちらの設計回答にあった**維持費・固定資産税・修繕費**は未対応です。これらは取得済みでも将来購入でも同じ欄なので、住まいの分類とは別の軸で検査すべきか、意見をください。
2. **`readiness()` に `badLoansIn` を通したことで、止めすぎていないか。** 保存できない値では段階を1に落とします。借入以外の異常値（`badNumbersIn`・`badResultsIn`）はまだ通していません。全部通すべきか、借入だけで足りるか。
3. **pendingの採用条件。** markerの存在だけを条件にしています。markerに書いた `at`（時刻）が古すぎる場合を除外すべきかどうか。
4. **自営業の0円**を要確認のままにした判断（§4）。
