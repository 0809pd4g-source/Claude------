## 2. P0

### P0-1｜子どもを1人追加すると、V82自身の監査が不合格になる（同名2件＋三重接頭辞）

今回の版の中心主張が、利用者の1クリックで崩れます。

**再現手順**

1. まっさらな状態で開く（`localStorage` を空にして再読込）
2. 詳細設定（params）を開き、カードを展開する
3. `__V82__.currentA11yAudit()` → **`ok: true`**（＝ChatGPT側QAが見ている状態）
4. 画面上のボタン **「世帯：＋ 子どもを追加」を1回押す**
5. 同じ監査を再実行する

**実測値**

| 状態 | `ok` | `legacy.duplicates` | `stable.repeated` |
|---|---|---|---|
| 子どもなし（初期） | `true` | 0件 | 0件 |
| **子ども1人** | **`false`** | `このプランについて：操作項目：1行目：1行目：1行目 ×2` | 2件 |
| **子ども3人** | **`false`** | 上記＋`2行目：2行目：2行目 ×2`＋`3行目：3行目：3行目 ×2` | 6件 |

子どもの人数に**比例して増えます**。

**当該DOM（実測、そのまま抜粋）**

```html
<div class="rowitem">
  <input type="text"   value="第1子" oninput="onKid(0,'name',this.value,1)"
         aria-label="このプランについて：操作項目：1行目：1行目：1行目">
  <input type="number" value="2016"  oninput="onKid(0,'birthYear',this.value)" style="width:62px"
         aria-label="このプランについて：操作項目：1行目：1行目：1行目">
  <span class="tag">年生まれ</span>
  <button class="x" onclick="delKid(0)" title="削除"
          aria-label="このプランについて：第1子を削除">×</button>
</div>
```

この1行に、今回の版が潰したはずの欠陥が4つ同居しています。

1. **同名**：子の「名前」欄と「生まれ年」欄が**まったく同じ読み上げ名**。V80のP1-1と同じ欠陥です。
2. **`1行目：1行目：1行目`**：QAレポート§3.1が「生成しないようにしました」と書いた三重接頭辞そのもの。
3. **所属カード名が誤り**：この行は「世帯の基本情報」にありますが、名前は「このプランについて」と名乗ります。
4. **意味を持たない語**：「操作項目」は利用者向けの言葉ではありません。

隣の削除ボタンは `このプランについて：第1子を削除` と**正しく命名できています**。命名の仕組み自体は動いていて、この2欄だけが汎用の取りこぼし経路に落ちています。

**なぜ293/293で見逃されたのか（ここが本題）**

ChatGPT側のQAは、**同じ状態を共有しない2本の試験**に分かれています。

- 4分岐ウィザードE2E … 分岐2・4で**子どもを2人作る**。しかしa11y監査は回さない。
- 13経路アクセシビリティ監査 … **子どもがいない初期状態**で13経路を回る。

つまり「子どもがいる状態の詳細設定」は、**どちらの試験も一度も踏んでいません**。私が分岐2・4のE2Eを完走させた直後にそのまま監査を回したところ、即座に `ok:false` が出ました。試験は両方とも正しく作られていて、**交差していないだけ**です。

これはV80で私が書いた「監査の作りが正しくても、回す状態が足りなければ守れない」と同じ構図で、**3版連続で同じ形**をしています。V80では監査が正しいのにQAが回す画面が足りず、V82では監査もE2Eも正しいのに**互いの状態を渡していません**。

**修正案**

1. 子の行の2欄に明示的な名前を与える：`世帯：第1子の名前` / `世帯：第1子の生まれ年`。削除ボタンと同じ経路で作れば済みます。
2. **a11y監査を、E2Eが到達した状態の上で回す**。13経路×（初期／子あり／購入あり）のように、経路と状態を掛け合わせてください。最低でも4分岐E2Eの各終了状態で13経路監査を1回ずつ。
3. 三重接頭辞は、接頭辞を足す前に「既に同じ語で始まっていないか」を見るのではなく、**接頭辞を足す箇所を1本に統一**してください（重ね掛けが起きるのは、付与経路が複数あるからです）。

## 3. P1

### P1-1｜内部のデータパスが、そのまま読み上げ名に出ている（19件／3経路）

**再現手順**：詳細設定（params）を開き、可視の `input/select/textarea/button` の実効名を集める。

**実測値**（1280px・390pxで同一）

| 経路 | 件数 |
|---|---:|
| params | 13 |
| loan | 4 |
| assets | 2 |
| **合計** | **19** |

**例（実測、そのまま）**

- `あなたの収入（給与・額面）：income.hTable・1行目・age`
- `あなたの収入（給与・額面）：income.hTable・1行目・amount`
- `あなたの収入（給与・額面）：income.hTable・1行目・rate`
- `生活費（毎年かかる分をまとめて）：living.table・1行目・amount`

`income.hTable`・`living.table`・`age`・`amount`・`rate` は、いずれも**開発者側の識別子**です。読み上げると「インカム ドット エイチテーブル」と発音されます。

現行の監査は「名前が**ある**か」「**重複**していないか」「**長すぎ**ないか」は見ていますが、**その名前が利用者に意味を持つか**を見ていません。だから19件すべてが合格として通ります。

**修正案**：`age`→`開始年齢`、`amount`→`年収`、`rate`→`上昇率` のように、パスから引くのは**位置**だけにして、語は利用者向けの表に持たせてください。あわせて監査に「名前に `[a-z]+\.[a-z]` 形式が含まれないこと」を1行足せば、この種は今後自動で止まります。

### P1-2｜説明ボタンの名前に注釈本文が丸ごと入り、「…」で切って80字判定を通している（23件／3経路）

QAレポート§3.1は「『？』、補足文、出典文、ポップアップ本文は**入力欄の名前**に含めません」と書いています。**入力欄については、そのとおりでした**（`labelInName` は実測0件）。しかし**説明ボタン側**には注釈本文がそのまま入っています。

**実測値**：params 10件・loan 3件・assets 10件＝**23件**。`__V82__.currentA11yAudit().help` は `count:16, bad:[], ok:true` を返します。

**例（実測、そのまま）**

- `生活費（毎年かかる分をまとめて）：いまの世帯人数（4人）に合わせた目安を入れる ひとり暮らし年180万円を基準に、世帯人数の平方根で調…の説明を開く`
- `その他の支出（時期が決まっているもの）：「一時」＝その年だけ／「毎年」＝範囲内は毎年／「N年ごと」＝開始年からN年おき。の説明を開く`
- `医療費・介護費用：介護は起きるかどうか分からない出費ですが、起きたときの金額が大きいため、 一度は計上して確かめて…の説明を開く`

2点あります。

**(a) 80字判定は「短いから」ではなく「切ったから」通っています。** 上記1件目は「世帯人数の平方根で調**…**」と**単語の途中**で切れ、そのあとに「の説明を開く」が続きます。読み上げると文が途中で終わって役割名が来ます。`over80: 0` は、注釈を名前から外した結果ではなく、注釈を**切り詰めた**結果です。指標は満たしていますが、指標が守ろうとしたものは守られていません。

**(b) 計算結果を名前に含むボタンがあり、名前が値で変わります。** `stableNameAudit()` は `ok:true` のままです。

| 操作 | 同一ボタンの読み上げ名 |
|---|---|
| 年収0のとき | `リタイア後の収入：あなた：基礎 0万 ＋ 厚生 0万 ＝ 年 0万円 （平均標準報酬額 0万／加入 0年）…の説明を開く` |
| 年収800万を入力後 | `リタイア後の収入：あなた：基礎 85万 ＋ 厚生 165万 ＝ 年 250万円 （平均標準報酬額 58万／加入 43年）…の説明を開く` |

`stableNameAudit()` が見ているのは**再描画に対する安定性**で、**データ変更に対する安定性**ではありません。支援技術の利用者にとって、同じボタンの名前が入力のたびに変わるのは、末尾連番と同種の問題です。

**修正案**：説明ボタンの名前は**見出し語だけ**にしてください（`生活費（毎年かかる分をまとめて）：目安の説明を開く`）。注釈本文はポップアップ側の本文に置き、`aria-describedby` で参照させれば、名前を切り詰める必要はなくなります。判定も「80字以内」ではなく「**注釈本文を含まない**」に変えてください。切り詰めで通せる指標は、遅かれ早かれ切り詰めで通されます。

## 6. 誤認・撤回した仮説

今回は**私の側の測定ミスが5件**あり、いずれも報告前に撤回しました。5件中4件は「自分のハーネスの誤り」を「相手の欠陥」と読み違えたものです。

1. **「賃貸分岐で `housingDetails` が要求され `stage 3` に届かない」→ 撤回。** 私のハーネスがチェックボックスの既定処理で「住宅購入を検討する」を**反転させ** `buy=true` にしていました。同時に報告しかけた「画面4の3欄が着地しない」も、チェックボックスに対して `.checked` ではなく `.value`（常に `"on"`）を比較していた私の測定の誤りです。
2. **「子どもの人数がPARAMSに伝わらない」→ 撤回。** `PARAMS.family.nKids` を見ていましたが、実際は `PARAMS.family.children[]` でした。2人とも正しく設定されていました。
3. **「ウィザードが子の生まれ年を聞いていない」→ 撤回。** 画面1に `年齢：1人目の生年`・`2人目の生年` が**あります**。私のハーネスが空の数値欄に既定補完で `40` を入れ、生年として無効なため弾かれていただけでした。
4. **「手入力しても自動調整が解除されない」→ 撤回。** `onLoanMan(i, v)` は**引数2つ**なのに `onLoanMan(0,'amount',30000000)` と3つで呼んでいました。正しく呼べば解除されます。
5. **「桁違いの借入額で描画が固まる」→ 撤回。** 3,000万〜3,000億で描画時間を測ったところ 3.9〜5.0秒でほぼ一定で、**金額に依存しません**。ブラウザペインが非表示のときの描画スロットリングでした。**非表示ペインで測った所要時間は性能の証拠になりません**ので、本レビューでは性能に関する指摘を一切していません。

P0-1については、上記の反省を踏まえ、**まっさらな状態から実ボタン1回**という最小手順で独立に再現し直したうえで報告しています。
