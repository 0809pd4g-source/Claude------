## 4. P1

### P1-1 ウィザードを一周しても「判断の準備」に届かない（3項目が確認済みにならない）

**V78の主題そのものに関わる件です。**

**再現手順**（初期状態・localStorage を空にしてから）

1. 「質問に答えながら入力」を開く
2. 1〜7の各ステップで、**表示されている数値欄をすべて埋める**（既定はすべて空欄）
3. 8ページ目（確認画面）へ進む

**実測**（各欄に入れた値：年齢42／年収620／リタイア63／預金800／運用300／NISA残高200／
DC残高150／家賃13／生活費26／保険料24／NISA積立4／DC積立2／物価2／利回り3）

| ステップ | 入れた欄 | 確認済みになったキー |
|---|---|---|
| 1 世帯 | 本人の現在年齢 | `age` |
| 2 収入 | 現在の年収／**リタイア年齢** | `income` のみ |
| 3 現在資産 | 預金・運用・NISA残高・DC残高 | `assets` |
| 4 住まい | 現在の家賃・住居費 | `housing` |
| 5 支出・積立 | 基本生活費／**年間の保険料**／**本人のNISA**／**本人のDC・iDeCo** | `living` のみ |
| 6 長期前提 | 物価上昇率・運用利回り | `assumptions` |
| 7 気になること | （数値欄なし） | — |

**到達した状態**

```
v61Completion() → stage: 1（概算を確認できます）／decisionReady: false
                  missing.household: ['insurance', 'saving', 'retirement']
decisionReady('overall') → level: 'estimate'
```

そして**8ページ目自身がこう表示します**：

> **未確認の項目があります**
> 次に確認： **年間保険料** ／ **毎月の積立** ／ **リタイア年齢**

**ウィザードが、たったいま自分で聞いた3項目を「次に確認してください」と出しています。**

**原因の所在**（断定はしていません。観察できた範囲）

ウィザードの欄は `data-v61-path` と `data-v61-unit` を持ちますが、
**準備度のキーを指す属性を持っていません。**

```
リタイア年齢     → data-v61-retire="h"
年間の保険料     → data-v61-path="living.insurance"  data-v61-unit="man"
本人のNISA       → data-v61-path="saving.nisaMonthlyH"  data-v61-unit="man"
```

書き込みの入口 `v61SetPath(path, value, unit, key)` は **第4引数 `key` で `v61Mark(key)` を呼ぶ**設計です。
`econ.deposit`→`assets`、`living.table.0.amount`→`living`、`econ.inflation`→`assumptions` は確認済みになるので、
経路自体は働いています。**`living.insurance`→`insurance`、`saving.*`→`saving` の対応が無い**のだと思われます。
`v61SetRetire()` は `v61Mark('retirement')` を呼びますが、
ウィザードのリタイア年齢欄からは**その関数に届いていません**。

**同じことが「一覧で直接入力」側でも起きます。** 一覧側で同じ3項目を編集しても、確認済みは増えませんでした。
つまり**ウィザード固有ではなく、この3キーには確認済みにする経路が無い**可能性が高いです。

**なぜ自動検査で捕まらなかったか**（ここが本題だと思います）

`v78WizardCoverageAudit()` は **`ok: true` を返します。**
欄の**存在**（`host.querySelector(...)`）は見ていますが、
**その欄を使ったときに確認済みになるか**は見ていないためです。

> **「欄がある」と「その欄が効く」は別の指標です。**
> こちらはv26で同じ構図をやりました（`covers` は書いたが `READY_STEPS` を満たさない）。
> V78は欄の存在まで進めたので、**あと一歩は「使ったら段階が上がるか」**だと思います。

**提案する受入条件**

```
ウィザードを1〜7まで一周して全欄を埋めたら、v61Completion().stage === 3 になること
（購入ON／OFF、子どもあり／なしの各条件で）
```

これを回帰に入れれば、今回の状態は落ちます。

### P1-2 「判断の準備が整ったか」の答えが2つあり、新しいほうが甘い（V77から未修正）

## 5. P2

### P2-1 網羅監査の「必要項目」がハードコードで、増やしても監査は落ちない

```js
const required=['age','income','living','assets','housing','insurance','saving','retirement','assumptions'];
const modelCoverage=required.every(x=>covered.has(x));
```

判定側（`v61Completion` / `V77_READY_TOPICS`）とは**別のリテラル**です。
同じ形のリテラルが `V78_GUIDE_MODEL` を使うガイド監査側にもあり、**同じ一覧が3か所にあります。**

**負試験**：判定側に必須項目を1つ増やしても、監査は落ちませんでした。

```js
const orig = v61Completion;
v61Completion = function(){ const c = orig(); c.missing.decision.push('newRequirement');
                            c.decisionReady = false; return c; };
v78WizardCoverageAudit().modelCoverage;   // → true
v78WizardCoverageAudit().ok;              // → true
```

**この監査が防ごうとしている「案内と要求のずれ」を、監査自身が検出できません。**
`required` を判定側から導出してください（例：`V77_READY_TOPICS.overall.required.concat(recommended)`）。
なお `children` は `covers` に入っているのに `required` に無いため、いまは検査されていません。

### P2-2 読み上げ名が、描画のたびに変わる（末尾に「（2）」が付く）

ウィザードを開くと、一覧側と同じ名前の欄が同時にDOM上に存在するため、
**自動で「（2）」を付けて重複を回避しています**（`data-v67-generated-label="duplicate"`）。

実測（ウィザードを開いた状態）：

- 「リタイア年齢（2）」「預金・現金（2）」「NISA残高（2）」「基本生活費（2）」
  「年間の保険料（2）」「本人のNISA（2）」「物価上昇率（2）」…
- 別の描画順では、同じ欄が「リタイア年齢」（2なし）になりました。

**読み上げ利用者にとって「（2）」は意味を持ちません。** しかも**同じ欄が呼ばれ方を変えます。**
自己監査は `duplicates: []` と報告しますが、これは**改名した結果**であって、
**区別できる名前が付いた**という意味ではありません。

**提案**：一覧側とウィザードで同じ欄が同時に存在しないようにする（開いている側だけを描画する）か、
文脈を名前に入れる（「セットアップ：リタイア年齢」）。
**番号を振るのは、最後の手段としても利用者には届きません。**

> ★これはこちらも通った道です。v12で同名14個を0にしたとき、
> 「描画後に推測で名前を付けない、生成時に一意にする」を原則にしました。

### P2-3 版の名乗りが2つ／古い版名の代入が5か所残っている（V77から未修正）

`<title>` は「レスポンシブ・ビジュアル統一版 V78」、ヘッダー副題は「V78 入力ステップ対応・網羅性強化版」。
どちらもV78ですが**版の名前が違います。**

あわせて、`ver.textContent='V70 導線・文言総点検版'` という代入が**5か所**あります
（V77では出現箇所を数えていませんでした）。
**いまは後段の層が上書きするので画面には出ません**（実測で副題はV78のもの）。
**現時点で利用者への影響はありません**が、同じ要素に同じ描画で何度も書いており、
順序が変われば古い版名が出ます。
