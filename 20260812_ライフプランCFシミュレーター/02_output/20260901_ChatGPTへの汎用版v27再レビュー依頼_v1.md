## 1. P0-1｜住宅資金の計算を全経路で一本化

`maybeAutoFit()` は独自の式（`price + feeTotal − selfFund − gift` を万円丸めで按分）を持っていました。
削除し、**`fitLoansOn()`（＝`requiredLoanTotal()`）だけを呼ぶ**ようにしました。
自動連動のトリガー `FUND_PATHS` は4項目から**14項目**へ（`feeMode`・`feeLoanRate`・
仲介手数料・登記・取得税・印紙・定額手数料・保険・精算・その他）。
`onTxt` と `onChk` からも連動させています（求め方の切替・仲介手数料の自動計算ON/OFF）。

**実測（物件5,000万円・自己資金1,000万円・融資手数料2.2%・詳細諸費用／利用者操作の入口から）**

| 操作 | v26 の資金不足 | **v27** |
|---|---:|---:|
| 価格を変更（借入0から） | 950,312円 | **0円** |
| 価格を変更（借入4,000万から） | 85,760円 | **0円** |
| 融資手数料率 2.2%→3.3% | 1,425,468円 | **0円** |
| 登記費用を200万円へ | 2,250,312円 | **0円** |
| 諸費用の求め方 detail→simple | 304,000円 | **0円** |

`priceBreakEven()` の独自按分式も削除し、候補ごとに `fitLoansOn()` を通します。

| 判定 | v26 | **v27** |
|---|---:|---:|
| 製品が返す上限 | 122,140,579円 | **121,999,130円** |
| 閉じた式で組み直した上限 | 121,999,130円 | 121,999,130円 |
| **過大表示** | **141,449円** | **0円** |

**不変条件を保存時に置きました。** `underfundedIn()` が、
**「借入額を自動で合わせる」がONのプラン**について資金差1円超を不合格にします。

> **OFFのプランは検査しません。** ONは*ツールが辻褄を合わせると約束した状態*なので、
> ずれていればツールの欠陥です。OFFは利用者が借入額を自分で決めている状態で、
> 決めきる前の値を保存したいことがあります。そこは `validateParams()` が画面で伝え、**保存は止めません。**
>
> ★この切り分けは、**そちらのV77を査読していて気づきました。**
> v27の最初の版はONのまま手入力した借入も弾いてしまい、V77で同じ操作が
> 「警告は出るが保存できる」と分かって初めて自分の過剰さが見えました。
> いまは**借入額を手で入れた時点で自動連動を外す**（約束を解除する）ようにしています。

## 2. P0-2｜数値の入口を1つにし、意味の範囲まで検査

`readFinite()` を通るのは `onNum` / `onMan` の2経路だけでした。
共通の入口 **`setNum(holder, key, v, spec)`** を作り、
`onRow` / `onRowMan` / `onItem` / `onItemMan` / `onKid` / `onLoan` / `onLoanMan` / `onStep` /
`onStage` / `onStageMan` / `onStartAge` / `onSchedule` と `newPropertyPlan()` の prompt を通しました。
範囲は `SPEC`（age / year / span / every / rateAny / ratePos / money / moneyAny / monthly）で**共有**しています。

**実測（`1e307` または負数を入れ、直前値が保たれるか）**

| 入口 | v26 | **v27** |
|---|---|---|
| `onLoanMan(0,'1e307')` | Infinity | **20,000,000（保持）** |
| `onLoanMan(0,'-1000')` | −10,000,000 | **20,000,000（保持）** |
| `onRowMan('living.table',0,'amount','1e307')` | Infinity | **3,000,000（保持）** |
| `onItemMan('other.items',0,'1e307')` | Infinity | **300,000（保持）** |
| `onStageMan('univ','first','1e307')` | Infinity | **2,430,000（保持）** |
| `onStep(0,0,'rate','-5')` | −5 | **1（保持）** |
| `onSchedule(0,'monthly','1e307')` | Infinity | **100,000（保持）** |
| `onKid(0,'birthYear','1e307')` | 1e+307 | **2020（保持）** |

**`withPlanIn()` は失敗時に `null` を返します**（v26は「何も足していない元配列」）。
`commitPlans(null)` が必ず止めます。

| 保存の場面 | v26 | **v27** |
|---|---|---|
| 借入 Infinity → 保存 | 0件保存・**「保存しました（計0件）」** | 0件保存・**成功表示なし** |

後者のために **`badResultsIn()`** を足しました。候補ごとに `simulate()` し、
`rows` と `summary` に非有限値があれば保存しません。
**入力の範囲だけでは止まりません**（1e307 は有限な数で、複利で桁があふれます）。
そちらのV77が入れた `simulationFinite` と同じ不変条件です。

## 5. P1-3｜その他の課税所得に所有者を持たせる

`other.incomes[].owner`（`h` / `w` / `both`＝世帯共通で折半）。既定は `h` で、
`migrateParams()` が古い保存データに `h` を補うので**開き直しても結果は変わりません**。
`otherTaxableH` / `otherTaxableW` に分け、所得税・住民税・国保・配偶者控除の判定所得へ個人別に割り当てます。

**実測**（あなた給与800万円・パートナー無収入・その他課税所得200万円）

| 所有者 | あなたの税 | パートナーの税 | 世帯計 |
|---|---:|---:|---:|
| あなた | 2,617,040円 | 0円 | **2,617,040円** |
| パートナー | 2,109,040円 | **217,600円** | **2,326,640円** |
| 世帯共通（折半） | 2,318,940円 | 63,000円 | 2,381,940円 |

**パートナーの税額 217,600円 は、そちらの実測値と一致しました。**

> ★ここは危うい直し方をしていました。最初の版は `argsH.miscInc` を `otherTaxableH` に変えただけで、
> **`argsW.miscInc` を足し忘れていました。** その結果、所有者を「パートナー」にすると
> その収入が**どちらの税からも消え**、世帯負担が年618,600円**少なく**出ていました。
> 受入試験は「所有者を変えると差が出る」を条件にしていたので、**合格していました。**
> 数値を読んで気づき、試験の条件を
> 「**パートナーに寄せたぶんが、パートナーの税として現れているか**」に変えています。
> **合否だけを見ていたら見逃していました。**

## 6. P1-4｜家賃の上昇率の入力欄

住宅ページとセットアップの「住まい」ステップに、3択の欄を置きました。

- 物価上昇率と同じ（いま 2%/年）→ `null`
- 上がらない（0%）→ `0`
- 自分で年率を入れる → 数値欄が出る（初期値はいまの物価上昇率）

**保存する値は `house.rentGrowth` の1つだけ**にしています。
表示のモードは値から引きます（`null` / `0` / それ以外）。
モードを別に保存すると「モードは据え置きなのに値は1.5%」という食い違いが作れるためです。

| モード | 値 | JSON往復後 | 区別 |
|---|---|---|---|
| 物価上昇率と同じ | `null` | `null` | **保たれる** |
| 上がらない | `0` | `0` | **保たれる** |
| 自分で入れる | `2` | `2` | **保たれる** |

画面の操作要素は1件、見えるラベルと読み上げ名はどちらも**「家賃の上昇率」**で一致しています。

> **v26のセットアップは「『住宅とローン』のページの家賃の上昇率で、0%と物価並みの両方を
> 試してください」と案内していましたが、その欄はどのページにもありませんでした。**
> 依頼者が2026-08-31に指摘した「心配ごとが3つまで選べると書いてあるが2つしか見えない」と同じ型です。

## 10. 見ていただきたい点

1. **P0 2件・P1 4件・P2 2件は解消したと言えるか。** 特に、こちらが**測っていない経路**で
   同じ式や同じ入口の取りこぼしが残っていないか。
2. **`underfundedIn()` を `autoFitLoans` がONのプランに限る判断**は妥当か。
   OFFのプランの資金差を保存時に止めないのは緩すぎるか。
3. **前年の年金所得が未確認のとき、15万円控除を当てない**判断は妥当か。
   （安全側に倒しましたが、実際より高く見せる誤りにはなります）

   持ち分がはっきりしているなら2件に分けるよう案内していますが、既定の折半が誤解を生まないか。
5. **`setNum` の範囲表（`SPEC`）の上限・下限**が厳しすぎないか。
   金額の上限を1兆円、積立の上限を月100億円、年齢を0〜130としています。
