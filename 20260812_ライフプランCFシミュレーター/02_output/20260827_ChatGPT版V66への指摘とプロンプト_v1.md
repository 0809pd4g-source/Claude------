## P0-1　収入表を編集すると、入力画面が古い年収を表示し続ける

**画面に見えている操作だけで再現します。スクリプトは使っていません。**

### 再現手順

1. 未入力の状態から「入力」画面で **現在年齢40歳・現在の年収600万円** を入力
2. 「詳細設定」タブへ移動し、**あなたの収入（給与・額面）の表の金額セル**（画面に見えています）を **300** に変更
3. 「入力」画面へ戻る

### 実測値

| | 値 |
|---|---|
| `income.hBase` | **6,000,000**（更新されない） |
| `income.hTable[0].amount` | 3,000,000 |
| **計算に使われる初年度給与** | **3,000,000** |
| **入力画面が表示する「現在の年収」** | **600**（＝600万円） |
| `validateParams()` の指摘 | **なし** |

**利用者には「年収600万円」と表示されたまま、300万円で計算された結果が出ます。**
どちらが正しいのかを知る手がかりが画面にありません。

### なぜ起きたか

`v61SetIncome()` が `hBase` と `hTable` の両方を更新するのに対し、
`onRowMan('income.hTable', …)` は `hTable` だけを更新します。
**同じ値に書き込み口が2つあり、片方からもう片方への戻りがありません。**

### 修正案

`onRowMan` が `income.hTable` を触ったときに `hBase` を追随させるのが最小の修正です。

```js
/* 収入表を直接編集したときも、入力画面が見せる「現在の年収」を合わせる。
   ★同じ値の書き込み口が2つある状態にしないこと。
     v61SetIncome だけを直しても、表からの編集は素通りする。 */
function v66SyncBaseFromTable(who){
  const P = PARAMS;
  const key  = who === "w" ? "wTable" : "hTable";
  const path = who === "w" ? "wBase"  : "hBase";
  const age  = who === "w" ? P.family.ageW : P.family.ageH;
  const rows = P.income[key] || [];
  /* 現在年齢に効いている行（現在年齢以下でいちばん新しい行）を正とする。 */
  const cur = rows.filter(r => Number(r.age) <= Number(age))
                  .sort((a, b) => a.age - b.age).pop();
  if(cur) P.income[path] = Number(cur.amount) || 0;
}
```

`onRow` / `onRowMan` が `income.hTable` / `income.wTable` を更新した直後に呼んでください。
**逆方向（`v61SetIncome`）は既に正しいので触らないでください。**

なお、こちらの版でも**同じ形の不具合**を作っていました
（v10で `dc.limitEmployee` を分割したとき呼び出し側を直し忘れ）。
**「片方向だけ直して終わったつもりになる」のは、この設計に共通する落とし穴だと思います。**

## P1-1　会社員のiDeCo上限が、実際の上限の2.4倍で判定されている

`dcMonthlyLimit()` は会社員に対して **`employeeCombinedCurrent`（55,000円）** を返します。
これは**企業型DCの事業主掛金等との合計上限**であって、**iDeCo単独の上限ではありません。**

**そちら自身が、この関数のすぐ上のコメントに正しく書いています。**

> 会社員は勤め先の制度によって上限が違う（企業年金なし23,000円・企業型DCあり20,000円など）

**コメントは正しく、コードがそうなっていません。**

### 実測値（40歳・単身・年収800万円・会社員）

| 月額の拠出 | 警告 | 初年度の税・社会保険料 |
|---|---|---|
| 0円 | なし | 2,105,340円 |
| 23,000円（企業年金なしの実際の上限） | なし | 2,021,440円 |
| **55,000円（上限超）** | **なし** | **1,904,540円** |
| 68,000円 | あり | 1,857,140円 |

**月55,000円を入れても警告が出ず、23,000円のときより年116,900円だけ税が安く出ます。**

自営業側は正しく動いています（68,000円で警告なし・75,000円で警告あり）。

### 修正案

```js
/* 会社員のiDeCo上限は「1つの数字」ではない。
   55,000円は事業主掛金等との合計上限であって、iDeCo単独の上限ではない。
   1つにまとめると、企業年金がある人に過大な積立を許してしまう。 */
function dcMonthlyLimit(P, who){
  const after202612 = /* 既存の判定をそのまま */;
  if(workTypeOf(P, who) === "self")
    return after202612 ? POLICY.privatePension.idecoSelfFrom202612
                       : POLICY.privatePension.idecoSelfCurrent;
  if(after202612) return POLICY.privatePension.employeeCombinedFrom202612;
  const hasDb = who === "w" ? !!P.saving.hasDbW : !!P.saving.hasDbH;
  return hasDb ? 20000 : 23000;   // POLICYへ idecoEmployeeWithDb / NoDb として追加
}
```

**あわせて「勤め先に企業年金があるか」の設定が要ります**（現状は持っていません）。
合計上限（55,000円）の警告は、**iDeCo単独の警告とは別に**残してください。

**こちらのv11でまったく同じ修正をしました。** 実測でも同じ構図
（自営業へ誤警告／会社員の上限超を見逃し）だったので、参考になれば。

## P1-2　アクセシブルネームが重複し、型名が漏れている

QAの「名称なし操作要素0件」は**そのとおり**でした。
ただし **`0件` は「名前がある」ことしか測っていません。**

### 実測値（詳細設定画面・全折りたたみを展開）

| | 件数 |
|---|---|
| 見えている操作要素 | 70 |
| 名前なし | **0**（主張どおり） |
| **名前が `：number` で終わる（型名の漏れ）** | **15** |
| **同名が複数ある** | **4グループ・計19個** |

同名の内訳：

| 名前 | 個数 |
|---|---|
| `▼あなたの収入（給与・額面）：number` | **6** |
| `▼パートナーの収入（給与・額面）：number` | **6** |
| `▼生活費（毎年かかる分をまとめて）：number` | **3** |
| `スライダー` | 4 |

**収入表の「年齢」「金額」「上昇率」の3欄が、すべて同じ名前で読み上げられます。**
読み上げ利用者は、いま何の欄にいるのか分かりません。
キャッシュフロー表では「表示単位」が2個同名です。

### なぜ起きたか

`v63DerivedLabel()` が**描画後に名前を推測して付けています。**

```js
const key = el.id || el.getAttribute('name') || el.dataset.v61Path
          || el.dataset.v61Income || el.dataset.v61Age || el.type;
return [heading, hint, key].filter(Boolean).join('：') || '入力項目';
```

`id` も `name` も無いセルでは `el.type`（＝`number`）まで落ちるため、
**同じ見出しの下にある欄がすべて同名になります。**

### 修正案

**描画後に推測するのをやめ、生成時に名前を出してください。**
表のセルを作る関数（`onRow`/`onRowMan` を出している箇所）で、
行番号と列の意味を名前に含めます。

```js
// 例：収入表の1行分
`<input type="number" aria-label="${esc(who名 + 'の収入 ' + (i+1) + '行目の年齢')}" …>`
`<input type="number" aria-label="${esc(who名 + 'の収入 ' + (i+1) + '行目の金額（万円）')}" …>`
`<input type="number" aria-label="${esc(who名 + 'の収入 ' + (i+1) + '行目の上昇率（%）')}" …>`
```

`v63EnsureAccessibleNames()` は**入れ忘れの保険**として残してよいですが、
**主たる手段にしないでください。**

**判定の指標も変えることをお勧めします。**
「名称なし0件」に加えて、**「同じ画面に同名の操作要素が無いこと」**と
**「名前が型名（number/text/select-one）で終わらないこと」**を入れてください。
こちらは前者の観点が抜けていたので、この査読で自分の版にも足します。

## P1-3　依頼書に書かれた負試験1が、監査で落ちません

そちらの依頼書「負試験」の1番：

> 年収入力後も`income.hTable`を0円のままにする

この状態を作って `window.__V66__.audit()` を実行しました。

| | 結果 |
|---|---|
| `income.hBase` | 6,000,000 |
| `income.hTable[0].amount` | 0 |
| **初年度給与** | **0円** |
| **`audit().ok`** | **true** |
| **不合格になった項目** | **なし（14項目すべて合格）** |
| `validateParams()` の指摘 | なし |

**V66でいちばん重要な修正が、壊しても検出されません。**

監査の「年収を直接入力できる」は**入力欄の存在**を見ているだけで、
**入力した値が計算に届いているか**を見ていません。

### 修正案

監査に**恒等式の検査**を足してください。

```js
/* ★「入力欄がある」ことと「入力が計算に届く」ことは別。
   壊したときに落ちる検査でなければ、再発を防げない。 */
(function(){
  const P = PARAMS, age = P.family.ageH, base = P.income.hBase || 0;
  if(base <= 0) return {name:'年収が年次計算に届く', pass:true, detail:'未入力のため対象外'};
  const row = (P.income.hTable || [])
    .filter(r => Number(r.age) <= age).sort((a,b) => a.age - b.age).pop();
  const ok = row && Math.abs(Number(row.amount) - base) < 1;
  return {name:'年収が年次計算に届く', pass:!!ok,
          detail:`hBase=${base} / 現在年齢に効く行=${row ? row.amount : 'なし'}`};
})()
```

**足したあと、意図的に `hTable` を0にして落ちることを必ず確かめてください。**

こちらは同型の見落としをしています。PDF照合も回帰テストも `defaults()` から始めるため、
**「未入力から入力する」経路を一度も通っていませんでした。**
そちらの前回の指摘で発覚し、`check_input_flow.py` を新設しました。
**新しい入口を作ったら、その入口を通る検査を同時に作る**という教訓です。

**ウィザード自体は良い出来でした。** 6ステップ・名前なし0件・同名なし・型名漏れ0件。

## 誤認・対応不要（こちらが疑って、確かめたら問題なかったもの）

### ① 高所得世帯で子2人の国保増分が小さい → 賦課限度額が効いていた

本人600万・配偶者400万（ともに自営業）で子2人を足したとき、
増分が **4,880円** しかなく、当初は「子どもの均等割が抜けている」と疑いました。

**確かめたら、こちらの疑いが誤りでした。**

| 世帯 | 子2人による増分 |
|---|---|
| 低所得（大人1人・所得200万） | **128,200円** ＝ 均等割(47,300+16,800)×2 と**完全一致** |
| 高所得（大人2人・所得535万+335万） | 6,880円 |

高所得側は**医療分が上限660,000円・介護分が170,000円に張り付いていた**ためで、
**制度どおりの正しい挙動**でした。

### ② 老齢基礎年金 847,296円

公表される年額は100円単位に丸められるため（令和7年度は月69,308円×12＝831,696→**831,700円**）、
令和8年度の公表年額は **847,300円** になると思われます。

ただし **847,296円は月額×12の厳密値**で、**実際の受給額としてはそちらの方が正確**です。
差は年4円で、**対応不要と考えます。**（参考：こちらは847,300円を採っています。）

### ③ 自動年金OFFのとき「過去の厚生年金」が効かない

`pensionAuto=false` で `pastKoseiPensionH=500,000` を入れても年金が増えないことを確認しましたが、
**そのとき入力欄自体が画面に出ません**（自動ONで1件・OFFで0件を対照試験で確認）。
**沈黙して無視される状態ではないので、問題ありません。**

### ④ 保存の異常系

`setItem` が例外を投げる状態にして確かめました。

| | 結果 |
|---|---|
| 画面の文言 | 「保存できませんでした。」 |
| 通知 | 「ブラウザの保存容量がいっぱいです。JSONファイルへ書き出して保存してください。」 |
| **嘘の成功表示** | **なし** |
| 入力の保持 | 保持されている |

**正しい実装です。** こちらのv4は同じ場面で「保存しました（計1件）」と表示していました（v5で修正）。
