## 3. 実測で解消を確認したもの

### 3.1 準備度の一貫性（V77・V78のP1-1）→ **解消**

V77・V78で使った再現を、そのまま流しました。

```js
PARAMS.meta.v61.confirmed = {age:1,income:1,living:1,assets:1,retirement:1,housing:1,
  insurance:1,saving:1,assumptions:1,children:1,housingDetails:1};
PARAMS.house.buy = true; PARAMS.house.price = 0;
PARAMS.house.loans = [{name:'本人',amount:0,years:0,steps:[{y:1,rate:1}]}];
PARAMS.family.children = [{name:'子1', birthYear:0, plan:{}}];
```

| 判定 | V78 | **V80** |
|---|---|---|
| `v61Completion().stage` | 2 | **2** |
| `decisionReady('overall')` | **`ready`** | **`needs-input`**（不足＝お子さんの生年・物件価格・返済期間） |
| `decisionReady('housing')` | **`ready`** | **`needs-input`**（物件価格・返済期間） |
| `decisionReady('education')` | **`ready`** | **`needs-input`**（お子さんの生年） |

**`facts` が `confirmed` と `valid` を別々に持つ設計**が要点だと思います。
「確認したという旗」と「その値がいま使えるか」を分けたので、
旗だけ立った状態が `ready` に化けません。`labels` で利用者向けの言葉も返しています。

`V80_READINESS_MODEL` が `Object.freeze` されており、実行中に書き換えられません
（負試験でこれに阻まれました）。**正本を凍結するのは良い判断だと思います。**

## 4. P1

### P1-1 詳細設定タブで、助けの「？」ボタンと入力欄が**まったく同じ読み上げ名**を持つ

**再現**：390×844 で「詳細設定」タブを開く。

```js
__V80__.a11yAudit()      // → ok:false, duplicates 6件
__V80__.stableNameAudit() // → ok:false, duplicates 1件
```

**重複している6組**（いずれも `<button class="q">`＝助けの「？」と、その値の `<input>`）：

| 読み上げ名 | 要素 |
|---|---|
| `経済の前提：物価変動率？` | `q-econ_inflation` と `v67-econ-inflation-value-…` |
| `経済の前提：預金の利回り？` | `q-econ_depositRate` と 値欄 |
| `経済の前提：運用資産の利回り？この値が結果を大きく左右します。低めの想定も必ず確認してください` | `q-econ_investRate` と 値欄 |
| `保険料・その他の借入：支払保険料（住宅取得前）？` | `q-living_insurance` と 値欄 |
| `リタイア後の収入：あなたの退職一時金？` | `q-retire_lumpH` と 値欄 |
| `このプランについて：操作項目：1行目：1行目：…（「1行目：」が14回）` | 入力2件 |

どちらも**明示的な `aria-label`** で同じ文字列が付いています。
読み上げでは「経済の前提：物価変動率？」が2回続き、
**どちらが説明を開くボタンで、どちらが数値を入れる欄なのか区別できません。**

**最後の1件は接頭辞の重ね掛け**です。QAレポート §3.4 が
「過去の自動命名が接頭辞を重ねる問題を検出したのでV80で命名処理自体を置き換えた」と
書いている、まさにその形が残っています。

**そして重要なのは、これを見つけたのが**`__V80__.a11yAudit()`**＝そちらの監査そのもの**だという点です。

| 状態 | `a11yAudit().ok` | 重複 |
|---|---|---:|
| input / plans / check / cf / graph / compare / about | **true** | 0 |
| ウィザード | **true** | 0 |
| **詳細設定（params）** | **false** | **6** |

9状態のうち**8つは合格、詳細設定だけが不合格**です。
QAレポートは「アクセシビリティDOM監査 16/16 合格」「同一role＋同一name 0」と報告し、
AX状態として「入力画面／ウィザード/モバイル詳細」を挙げていますが、
**その「モバイル詳細」は詳細設定タブを開いた状態にはなっていない**と思われます。

> **監査の作りではなく、監査を回した状態の網羅が足りていません。**
> これはこちらが何度も踏んだ形で、CLAUDE.mdにも
> 「指標の範囲を書かない報告は、正しい数字でも誤読させる」と記録しています。

**提案**：`a11yAudit()` / `stableNameAudit()` を**全タブ×代表幅**で回し、
1つでも `ok:false` があればQAを失敗にする。いま**すでに検出できる**ので、回す場所を増やすだけです。
名前からは「？」と説明文を外し、助けのボタンは `◯◯の説明を開く` のように**役割で名乗る**のがよいと思います。

### P1-2 「ウィザードE2E」がDOMを通っていない

`__V80__.wizardJourneyAudit()` の中身は次の形でした。

```js
function wizardJourneyAudit(opts){
  PARAMS = v61BlankParams();
  v61SetAge('h',42); v61SetIncome('h',620); v61SetRetire('h',63);
  if(opts.child){ v61SetChildCount(1); v61SetChildYear(0,2028); }
  v61SetPath('econ.deposit',800,'man','assets');
  …
```

**`v66WizardBody()` を一度も描画せず、イベントも発火せず、「次へ」も押していません。**
設定関数を直接呼んでいるだけです。

依頼書 §A には「**関数を直接呼ぶだけでなく、実際のDOMイベントから通してください**」と
書かれています。**その条件を、そちら自身のE2Eが満たしていません。**
QAレポート §4.4 の「ウィザードE2E 4分岐すべて合格」は、
**ウィザードの画面を経由した証拠にはなっていない**ということです。

**ただし製品は正しいと考えます。** 上の 3.2 のとおり、こちらがDOMイベントで測ると
リタイア年齢・保険料・積立・長期前提・生年・物件価格のすべてが確認済みになります。
**問題は試験の側だけ**です。

**提案**：`renderWizardStep()`（既にある）で描いたホストを**実際にDOMへ挿入**し、
`input`／`change` を dispatch して「次へ」を押す形にする。
`wizardCoverageAudit()` は既に描画して `actionKeys` を集めているので、
その仕組みを journey 側へ持ってくれば足ります。

### P2-1 旧世代の監査が2つ残っており、要求項目がハードコードのまま

`window` には**2世代の監査**が同居しています。

| 関数 | `required` | 検査数 | 由来 |
|---|---|---:|---|
| `v79GuideMapAudit` / `v79WizardCoverageAudit` | **ハードコードの9項目**（`children`・`housingDetails` を含まない） | 9 | 旧 |
| `__V80__.guideMapAudit` / `__V80__.wizardCoverageAudit` | **モデルから導出した11項目** | 10（`世帯・子あり` を含む） | 新 |

HTML内に次のリテラルが**2箇所**残っています。

```js
required=['age','income','living','assets','housing','insurance','saving','retirement','assumptions'];
```

反映判断 §2.3 は「監査専用の手書き配列を廃止し、準備度正本から必要区分を生成する」と
書かれていますが、**廃止されたのは新しい方だけで、旧い方は残って `window` から呼べます。**
将来のQAが名前で `v79WizardCoverageAudit()` を呼ぶと、**弱い方の答えが返ります。**

**提案**：旧世代を削除するか、新しい実装への別名にする。

### P2-2 読み上げ名に説明文が丸ごと入っている

```
経済の前提：運用資産の利回り？この値が結果を大きく左右します。低めの想定も必ず確認してください
```

`<label>` の本文（「？」ボタンと注釈を含む）をそのまま名前にしているため、

## 6. 誤認・撤回した仮説（3件・すべてこちらの測定側）

**この版では、こちらの測り方の誤りが3件ありました。報告前に全部取り下げています。**

1. **「ガイド監査が `ok:false`」→ 撤回。**
   `v79GuideMapAudit().overflow` が22件でしたが、**ブラウザペインが非表示で
   `innerWidth === 0`** でした。1280×900 を明示したら overflow 0・`ok:true`。
   自分のCLAUDE.mdに「非表示の要素は測れない」と書いてある、その通りの誤りです。

2. **「ウィザードを一周しても段階1で止まる」→ 撤回。** 3回別々の理由で外しました。
   - 埋めた値が**既定値と同じ**で `change` が出ていなかった（V78の査読で一度踏んだ誤りの再発）
   - `pick()` の正規表現で **「運用利回り」が「運用」に先に当たり**、資産の値を入れていた
   - **入力のたびに再描画されるため、まとめて取った要素参照が切り離され、
     各画面の1つ目の欄しか効いていなかった**

   1欄ずつ引き直して測り直したところ、**5/5 のキーが確認済みになりました**（3.2）。

3. **「`V80_READINESS_MODEL` を誰も読んでいない」→ 撤回。**
   グローバル名の出現が1回だったので「定義だけ」と読みかけましたが、
   実体はIIFE内の局所名 `READINESS_MODEL` で**8回参照**されていました。

**なお、こちらのDOM経由の4分岐E2Eは完走できていません**（上記の理由でハーネスが安定せず）。
P1-2で「製品は正しいと考えます」と書いたのは、**1欄ずつの実測**にもとづく判断です。
