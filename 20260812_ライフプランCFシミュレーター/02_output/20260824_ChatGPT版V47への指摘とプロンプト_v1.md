## 結論・要点

**V47のQAレポートは「完成」と判定しているが、実物をブラウザで開くと、レポートが
「0件」と報告した項目が実際には残っている。** 原因は、**完全一致の文字列で検査したため、
言い換え・語順違い・`<title>`タグをすり抜けたこと。**

一方で、**設計として学ぶべき点は複数ある**。とくに「人物に紐づく任意の収入／支出ストリーム」
という考え方は、こちらの版の構造的な弱点（大人2人固定）を突いている。

**この査読によって、こちら側のバグも1件見つかった**（その他収入がまったく課税されていなかった）。
これは修正済み。

---

## 背景・経緯

依頼者からChatGPT版V47とそのQAレポートを受領。「よいところは取り込み、改善点はChatGPTに渡す
プロンプトを作る」という依頼。

検証方法は、レポートの記述を信じずに**実物を機械的に数え、さらにブラウザで実際に開いて確認**した。

## 論点・気づき

### A. QAレポートの主張と実物の食い違い（4件）

| レポートの主張 | 実物 |
|---|---|
| 「静的な通常表示テキスト内の『妻年収』: **0件**」 | 「妻年収」は確かに0件だが、**「妻の収入」「妻のベース年収」が27件**あり画面に出る |
| 「『妻向け』: **0件**」 | 「妻向け」は0件だが、**`<h2>` に「奥様向け・3分ガイド」**がある（ほか「妻へ渡す前の最終確認」） |
| 「旧タイトル『ライフプラン・住宅購入シミュレーター』: **0件**」 | **`<title>` が「ライフプラン・住宅購入シミュレーター｜正式版 V39」**。ブラウザのタブとブックマークに出る。**版番号もV39のまま**（h1は正しく「ライフプラン・シミュレーター」） |
| 「西小岩・平井等は内部データとして残し、**一般利用の通常導線には表示しない**」 | **プラン比較タブに西小岩・平井・栄町が100件以上表示される。** ほかに「はじめてガイド」「住宅種別・不動産」タブにも出る |

**これは「検査した」という記録が「直っている」ことを保証しない典型例。**
検査すべきは文字列ではなく条件（＝一般の利用者に個人依存の情報が見えないこと）だった。

### B. 「汎用モデルが正本」は名目で、実体は2人固定モデル

レポートは「`persons[]`／`incomeStreams[]`…を正本とし、`owner/spouse` は互換アダプター」と
書いているが、コードを追うと**逆**だった。

- `incomeStreams` の既定は
  `[{id:'salary-primary', personId:'person-1', source:'annualOverrides.ownerSalary'}, ...]`
  ＝**旧モデルへのポインタ**。`expenseStreams` は既定で空配列。
- `v42MakeLegacyLinks()` が旧モデルへのリンクを作る。
- `owner` 114箇所・`spouse` 531箇所。計算の本体は依然として2人モデル。

つまり `persons[]` は**旧モデルの上に貼ったUI層**で、正本ではない。
レポートの「正本／互換アダプター」の記述は**実装と逆**になっている。

### C. 追加した収入が定率でしか課税されない（精度上、最も重い）

3人目以降の大人や副業の収入は `incomeStreams` として足されるが、税は

```js
const tax = v * Math.max(0, n(s.taxRate, 0)) / 100;   // 既定 taxRate: 15（%）
```

**利用者が入れた一律の率（既定15%）を掛けるだけ。** 次がすべて反映されない。

- 給与所得控除 / 青色申告特別控除
- 累進税率（その人の他の所得との合算）
- **社会保険料（まったくかからない）**
- 扶養・配偶者控除への影響

年収500万円の3人目を足すと、実際の負担は社会保険料込みで概ね20%前後だが、
この計算では15%・社保0。**世帯収入を増やすほど、実際より楽な結果が出る**（危険側）。

### D. 「完成判定」が早い

レポート自身が「実ブラウザでの全クリック・全入力パターンを自動化したE2E試験は未実施」と
認めながら「完成判定」としている。

**こちらは実際に、静的検査を通ったのに実ブラウザで動かない不具合を経験している。**
`onclick="...${JSON.stringify(name)}..."` がダブルクォートでHTML属性を途中で切っており、
グラフの凡例が2日間まったく効いていなかった。DOMスタブのテストはイベント属性を解析しないため
「異常なし」と出ていた。

V47は `JSON.stringify(` が49箇所あるが、HTML属性の中で使っている箇所は0件だった（この点は問題なし）。
ただし**実ブラウザで一度も開いていないなら、この種の不具合は原理的に検出できない。**

### E. 住宅が導線から抜けきっていない

25タブのうち **4つが住宅専用**（住宅・金利／住宅ローン控除／住宅種別・不動産／住宅ローン）。
モジュール設定に「住宅購入・住宅ローン」のチェックはあるが、
汎用ツールとしては**OFFのときタブ自体が消える**のが自然。

## 取り込むもの（こちらの版へ）

### 1. 人物に紐づく任意の収入／支出ストリーム（構造として学ぶ）

こちらの版は `family.ageH` / `ageW` の**大人2人固定**で、
親との同居・3人目の稼ぎ手・成人した子の収入を表現できない。
V47の `persons[]` + ストリームという考え方は、この弱点を正しく突いている。

**ただしV47のように定率課税で足すのでは意味がない。**
取り込むなら「人物ごとに税・社会保険を計算する」ところまでやる必要がある。
大改修なので、次の改訂の設計課題として記録する（今回は着手しない）。

### 2. 「次に何をすればよいか」の提示

V47のダッシュボードは、入力チェックの結果に応じて**次の推奨操作**を出す。
こちらの「入力の確かさ」は「何が仮の値か」までで、次の行動を示していない。
セットアップを終えたあとの導線として取り込む価値がある（次回の候補）。

### 3. 感度分析の言い切り（表現として）

> 感度分析は予測ではなく、条件を機械的に動かした場合の幅を見る機能です。

この言い切りは良い。こちらにも同種の注記はあるが、ここまで明快ではない。

## この査読で見つかった、こちら側のバグ（修正済み）

**「その他収入」が `personTax` に渡っておらず、まったく課税されていなかった。**

- `otherIncome` は収入合計には足されるのに、税の計算に入っていなかった
- 児童手当は非課税なので正しいが、**副業・賃貸・配当・原稿料なども無税**になっていた
- **手取りを多く見せる（危険側）誤り**

修正内容：

- 項目ごとに**課税／非課税**を選べるようにし、**既定を課税**（安全側）にした
- 課税分は**雑所得**として総所得に足す（給与所得控除は使わない）
- 誰の収入かを持っていないため**あなたの所得に足す**ことを画面に明記した
- 検算：雑所得100万円で 合計所得 356万→456万、税・社保 +202,100円。
  「非課税」にすると増分0円

V47の同じ箇所（定率課税）を見たことで気づいた。**他ツールの査読は、自分のツールの検査になる。**
