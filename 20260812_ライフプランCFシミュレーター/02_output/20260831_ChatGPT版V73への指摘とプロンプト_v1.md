## 3. P1（配布前に直すことを勧めます）

### P1-1　ラベル潰れの修正が `<select>` 行だけで、`<input>` 行に同じ症状が残っている

追加されたCSSは `select` を含む行だけを対象にしています。

```css
@media(min-width:761px){
  .f:has(>select)>select{min-width:0;max-width:100%;}
  .f:has(>select)>label{flex:0 0 auto;min-width:6em;}
}
```

`.f > label` の既定は `flex:1 1 0%` / `min-width:0` のままなので、
**`<input>` を持つ行では同じ潰れが起きます。**

再現：**用語・制度の解説ページの「探す」ラベル**（`#dictQ` の行）。

| 画面幅 | 「探す」ラベルの幅 | 高さ | 監査 `labelWidths` |
|---|---:|---:|---|
| 1440 | 490.7px | 18.8 | true |
| 1024 | 239.4px | 18.8 | true |
| 900 | 115.4px | 18.8 | true |
| 880 | 95.4px | 18.8 | true |
| 850 | 65.4px | 18.8 | true |
| **820** | **35.4px** | 18.8 | **false** |
| **768** | **0px** | **37.5** | **false** |
| 390 | 350.7px | 19.5 | true |

**768pxはそちらのQAの5つの画面幅の1つです。** 実ビューポート768×1024でも同じ0pxを再現しました。
スクリーンショットでは「探」「す」が縦に積まれた1〜2px幅の帯になり、**読めません**（V72のP1-1と同じ見え方です）。

**修正案（実際に当てて確かめました）**

```css
@media(min-width:761px){
  .f>label{min-width:6em}
  .f>input,.f>select{min-width:0;max-width:100%}
}
```

| | 「探す」 | `labelWidths` | 幅40px未満 | 行の溢れ |
|---|---:|---|---:|---:|
| ①無改変 | 0 × 37.5px | false | 1件 | 0件 |
| ②`flex:0 0 auto` を付けた版 | 75 × 18.8px | true | 0件 | **6件** |
| ③**`min-width` だけの版（推奨）** | **75 × 18.8px** | **true** | **0件** | **0件** |
| ④外して戻す | 0 × 37.5px | false | 1件 | 0件 |

★**`flex:0 0 auto` は付けないでください。** ヒント文を内側に持つラベル
（「若い頃の年収の水準＋説明」など）が縮めなくなり、**行が6件溢れます**（②）。
いま `select` 行に付いている `flex:0 0 auto` も、同じ理由で外して `min-width` だけにするほうが安全です。

### P1-2　監査が「利用者が見ていないDOM」を測っている

**用語ページを一度も開いていない状態と、開いた後で、監査の結果が変わります。**

768×1024（実ビューポート）:

| | `dict` の `minLabelWidth` | `labelWidths` | `layoutAudit().ok` |
|---|---:|---|---|
| 起動直後（用語ページ未訪問） | 417.7 | true | **true** |
| `setTab('dict')` の後 | **0** | **false** | **false** |

原因：`setTab('dict')` で `#s-dict` が作り直されます（`innerHTML` の長さが **27,569 → 27,156** に変化）。
`v72MeasureCurrentDetail` はセクションの `.on` を付け替えて測るだけで**再描画を通さない**ため、
**利用者が実際に見る姿とは別のDOMを測っています。**

そちらのハーネスは `layoutAudit()` をループの早い段階で1回記録し、
`setTab('dict')` はその後のAX検査で初めて呼びます。
**この順序のおかげで、P1-1が235/235をすり抜けています。**

**提案**：各ページの測定を、実際の描画を通した状態で行ってください
（`v72WithDetailTab` の中で当該ページの描画関数を呼ぶ、または全13ページを1巡してから監査する）。
併せてハーネス側でも、**AX検査などで全ページを巡回したあとに `layoutAudit()` をもう一度記録**して、
前後で一致することを合否条件にすると、この種の取りこぼしが出なくなります。

### P1-3　390pxの基準線がまだ `false`（`shell.h` を外しても `section.y` が同じ差を運ぶ）

`shell.h` と `headHeight` を狭幅の判定から外した対応は方向として正しいのですが、
**`section.y` が同じ「説明文1行ぶん」の差をそのまま持っています。**

実ビューポート 390×844（dpr 2）・無改変・注入CSS 0件:

```
layoutAudit().ok        = false
geometry                = false
geometryKeys            = section.x, section.y, section.w, shell.x, shell.w
headHeight              = 173.2（params/edu/assets/stress） / 194.8（loan/dict）
section.y               = 461.7 ×4 / 483.3 ×2   → 差 21.6px
```

共通シェルが本文の上にあるため、**説明文が1行か2行かでシェルの高さが変わり、
そのぶん `section.y` がずれます。** 前回こちらが挙げた21.6pxと同じ値です。

幅を掃引すると、**主要なスマートフォン幅が軒並み不合格**でした（iframe計測）:

| 画面幅 | 320 | 360 | **375** | **390** | **412** | **414** | **430** | 480 | 540 | 600 | 680 | 760 | 761 | 800 |
|---|---|---|---|---|---|---|---|---|---|---|---|---|---|---|
| `ok` | ○ | ○ | **×** | **×** | **×** | **×** | **×** | ○ | ○ | ○ | ○ | ○ | ○ | ○ |

**影響が大きいのは、これによって390pxの負試験6件がすべて無効になることです。**

```
負試験: ok=false / baselineBefore=false / baselineAfter=false / 検出 0件 / 6件中
```

ガードが正しいので「検出した」と誤って主張しない点は良いのですが、
**モバイルの負試験が1件も機能していない状態**です。

**修正案（実際に当てて確かめました）— 検査を緩めるのではなく、製品側を揃える**

```css
@media(max-width:760px){ #v72DetailDesc{ min-height:2lh } }
```

| | `headHeight` の種類 | `section.y` 差 | `geometry` | `ok` | 負試験 |
|---|---|---:|---|---|---|
| ①無改変 | 172.9 / 194.4 | 21.6px | false | **false** | **検出0/6** |
| ②`min-height:2.9em` | 186.1 / 194.4 | 8.4px | false | false | — |
| ③**`min-height:2lh`（推奨）** | **194.4 の1種類** | **0px** | **true** | **true** | **検出6/6・復元6/6・基準線 前後とも true** |
| ④外して戻す | 172.9 / 194.4 | 21.6px | false | false | 検出0/6 |

**`section.y` を判定から外す方向は勧めません。**
ページを切り替えるたびに本文が21.6px跳ねるのは利用者にも見えるので、
**揃えるべきは検査ではなく表示のほう**です。説明文に2行ぶんの高さを確保すれば、
跳ねが消えると同時に監査も負試験も生き返ります。

## 4. こちらの誤認（報告前に取り下げ）

**内蔵受入試験が 12/13 に見えました。** 不合格は「入力例：出所をsampleで記録」で
`source:'unset'`、`PARAMS.income.hBase = 0`。

原因は**こちらの環境**でした。`v61LoadSample()` は先頭で `confirm()` を見ており、
ブラウザペインはダイアログを自動的に閉じる（＝false）ため、入力例が一切読み込まれていませんでした。
そちらのハーネスと同じく `window.confirm = () => true` を当てたところ **13/13** です。

★**「相手の不具合」と読む前に、自分の環境が同じ前提を満たしているかを確かめる。**
今回はそちらのハーネスに `confirm` の polyfill があったことが手がかりになりました。

## 5. こちらが取り込みたいもの

今回、**そちらの実装のほうが優れている点**が2つありました。V23で取り込みます。

1. **保存後の書き戻し確認**（`v61StorePlans`）

   ```js
   localStorage.setItem(V61_PLAN_KEY, payload);
   const verify = localStorage.getItem(V61_PLAN_KEY);
   if(verify !== payload) throw new Error('保存後の確認に失敗しました');
   ```

   こちらの `commitPlans()` は `setItem` が例外を投げなければ成功とみなしています。
   **静かに切り詰められた・追い出された場合を捕まえられません。** この読み戻しは安く確実です。

2. **スナップショット＋ロールバック方式**

   `before = clone(PLANS)` を取り、失敗したら戻す形が全経路（保存・複製・改名・削除・全削除・取込）で
   一貫していました。こちらの「候補を作ってから commit」と安全性は同等で、**既存コードへの改修量が小さい**。
   こちらのv21で起きた「helperだけ直して呼出側が取り残される」事故は、この形なら起きにくいです。
