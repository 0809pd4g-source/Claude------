## P1-1　モバイルで、選択中の詳細設定タブが画面の外にある

**PCでは解消した「同じ階層なのに現在地が分からない」が、390pxでは残っています。**

### 実測（390×844・タブを実際にクリックして測定）

タブ行は幅344pxで、中身は822px（2.4画面分）あります。

| 押したタブ | 切替後の `scrollLeft` | 選択中タブの左端 | 見え方 |
|---|---:|---:|---|
| 住宅とローン | 0 | 161px | 全部見える |
| 教育費 | 0 | 299px | **右端が切れる** |
| 資産形成 | 0 | 437px | **完全に画面外** |
| ストレステスト | 0 | 575px | **完全に画面外** |
| 用語・制度の解説 | 0 | 713px | **完全に画面外** |

タブ行の表示範囲は x=23〜367px です。**6つのうち3つは、選択しても一切見えません。**

### 原因（こちらで特定しました）

**6ページがそれぞれ別のタブ行を持っています。**
切替後に表示されるのは「まだ一度もスクロールされていない別のDOM要素」なので、
`scrollLeft` は必ず0から始まります。

実証：タブ行を `scrollLeft=478` までスクロールしてから「資産形成」を押すと、
切替後の要素は**別物**（`同じ要素か: false`）で `scrollLeft=0`、選択中タブは画面外でした。

「スクロール位置がリセットされる」のではなく、**そもそも引き継げない構造**です。

### 利用者への影響

- 「資産形成」を押した直後、タブ行には「世帯・収入・生活」「住宅とローン」しか見えない
- **どこにいるのかが分からない**（見出しは出るが、タブの選択状態は見えない）
- 押すために毎回スクロールが必要で、押した後にまた先頭へ戻る

**PCで解決した課題が、モバイルでは形を変えて残っています。**

### 修正案

切替後に、選択中のタブを見える位置へ寄せてください。

```js
/* 詳細設定の各ページは別のタブ行を持つため、切替後の要素は scrollLeft=0 で始まる。
   選択中のタブが画面外だと、モバイルでは現在地が分からない。 */
function v71ScrollActiveTabIntoView(){
  const shell = [...document.querySelectorAll('.v71-detail-shell')]
    .find(el => el.offsetParent !== null);
  if(!shell) return;
  const row = shell.querySelector('.v71-detail-tabs');
  const sel = row && row.querySelector('.v71-detail-tab[aria-selected="true"]');
  if(!row || !sel) return;
  /* ★`scrollIntoView` は縦にも動くため、ページが上下に飛ぶ。
     タブ行の中だけを横に動かす。 */
  row.scrollLeft = sel.offsetLeft - (row.clientWidth - sel.offsetWidth) / 2;
}
```

`v61SetTab()` の末尾（描画後）で呼んでください。
**`behavior:'smooth'` は付けないことをお勧めします。**
描画していない環境ではアニメーションのフレームが進まず、まったく動かないことがあります
（こちらはこれで一度誤診しました）。

**より根本的には、タブ行を1つにして全ページで共有する**ほうが確実です。
そうすればスクロール位置が自然に保たれ、DOMも6分の1になります。

## P1-2　ページを切り替えると、画面全体が横に7.5pxずれる

QAレポートは共通シェル左端を「約110px」と書いていますが、**6ページ中4ページは102.5px**でした。

### 実測（1440×900）

| ページ | シェル左端 | ページ高さ | 縦スクロールバー |
|---|---:|---:|---:|
| 世帯・収入・生活 | **102.5px** | 4,435px | 15px |
| 住宅とローン | **102.5px** | 2,735px | 15px |
| 教育費 | **110px** | 900px | **0px** |
| 資産形成 | **102.5px** | 2,803px | 15px |
| ストレステスト | **110px** | 900px | **0px** |
| 用語・制度の解説 | **102.5px** | 4,734px | 15px |

### 原因

**縦スクロールバーの有無です。** 中身が画面に収まるページではスクロールバーが消え、
`clientWidth` が 1425→1440 になります。中央寄せの1220pxの箱は
`(1440−1220)/2 = 110`、スクロールバーありなら `(1425−1220)/2 = 102.5` に来ます。

`html` の `scrollbar-gutter` は `auto`、`overflow-y` は `visible` でした。

### 入力を進めても残ります

| 状態 | 左端の種類 |
|---|---|
| 完全未入力 | 102.5 と 110（教育費・ストレステストが110） |
| 年齢・年収・生活費・子2人・住宅ON | 102.5 と 110（ストレステストが110） |
| 家計の全体像まで入力 | 102.5 と 110（ストレステストが110） |

ストレステストは `v70-gate`（「まだ判断材料として表示しません」）で中身が抑止されるため、
**判断準備が整うまでは必ず短いページ**です。つまりこのずれは常態です。

### 利用者への影響

タブを押すたびに、**ページ全体が7.5px横に飛びます。**
1回では気づきにくいですが、6つのタブを行き来すると「揃っていない」と感じます。
**今回の改修が狙った「レイアウトが変わった印象」の、最後の一片だと思います。**

### 修正案

1行で直せます。

```css
html{
  /* ページの中身の量でスクロールバーが出たり消えたりすると、
     中央寄せの箱が7.5px横に動く。常に場所を空けておく。 */
  scrollbar-gutter: stable;
}
```

古いブラウザも対象にするなら `html{ overflow-y: scroll; }` でも同じ効果になります。

## P2-1　レイアウト監査が、寸法のずれを検出できません

**依頼書の負試験6件を実際に流しました。**

| 負試験 | `__V71__.layoutAudit()` |
|---|---|
| ① 1ページだけ最大幅を1220→800pxに変更 | **ok: true（検出できない）** |
| ② 1ページだけ共通タブを1項目削る | ok: false（検出） |
| ③ 1ページだけ操作ボタンの順序を入れ替える | ok: false（検出） |
| ④ 1ページだけ旧戻りバーを表示する | ok: false（検出） |
| ⑤ 1ページだけシェルの上端を60pxずらす | **ok: true（検出できない）** |
| ⑥ 390pxでラベルの最小幅を12pxに潰す | **ok: true（検出できない）** |

`v71LayoutAudit()` が見ているのは、シェルの有無・タブの文言と順序・
選択中が1つであること・旧要素が可視でないこと・操作ボタンの文言と順序**だけ**です。

**QAレポートが誇っている数値（1,220px・164.75px・181px）を、監査自体は一度も測っていません。**

つまり**現物は正しいが、次の改修で寸法を壊しても検査は落ちません。**
今回P1-2で見つかった7.5pxのずれを監査が素通りしたのも、同じ理由です。

### 修正案

`layoutAudit` に寸法の一致検査を足してください。

```js
/* ★「共通シェル」を名乗る以上、寸法が同じであることまで見ないと再発を防げない。
   幅・高さ・上端・左端を6ページで比べ、1pxでも違えば落とす。 */
const geo = [];
V71_DETAIL_PAGES.forEach(x => {
  v61SetTab(x.tab);                       // 表示してから測る（非表示だと0になる）
  const el = document.querySelector(`.v71-detail-shell[data-v71-detail-shell="${x.tab}"]`);
  const b = el.getBoundingClientRect();
  geo.push({tab:x.tab, x:Math.round(b.x*10)/10, y:Math.round(b.y*10)/10,
            w:Math.round(b.width*10)/10, h:Math.round(b.height*10)/10});
});
const same = k => geo.every(g => Math.abs(g[k] - geo[0][k]) < 1);
const geoOk = ['x','y','w','h'].every(same);
```

**足したあと、わざと1ページの幅を変えて落ちることを必ず確かめてください。**
（こちらは今日、新しく足した検査が実は効いていなかったのを2回見つけました。
「検査を足した」と「壊したら落ちる」は別です。）

**あわせて、モバイルで選択中タブが見える位置にあるかも検査に入れてください**（P1-1の再発防止）。

## P2-2　非表示の旧DOMが27要素・その中に操作要素が47個あります

| 旧要素 | 個数 | 表示中 |
|---|---:|---:|
| `.v68-returnbar` | 6 | 0 |
| `.v69-detail-subnav` | 5 | 0 |
| `.v69-detail-hub` | 1 | 0 |
| `.v70-hidden` | 15 | 0 |

**利用者への影響はありません。** すべて `display:none` なので、
キーボードのフォーカスも到達しません（`display:none` は仕様上フォーカス不可）。
さらに `display:flex` を素で当てても消えなかったので、`!important` で守られています。
**この防御は良い作りだと思います。**

指摘は**保守性**の観点です。

- 旧DOMの中に**操作要素が47個**あり、すべて `tabindex="-1"` でも `disabled` でもありません
- 将来 `!important` を外したり、親のCSSを整理したりすると、**47個が一度に復活します**
- そのときの状態は「新旧2つのナビが同時に出ている」で、**今回直した課題の再発**です

実際に `!important` で強制表示したところ、監査は落ちました（④で確認）。
**検査は効いているので、消すか、残すなら「なぜ残すか」をコメントに書いておくのが良い**と思います。

こちらも同種の経験があります。同じことをする仕組みを2つ作ってしまい、
片方に気づかず並存させたことがありました（`prepareStackTables` と `mobileCards`）。
**「あとで消す」は消えないので、消すなら今、残すなら理由を書く**という結論です。

## 誤認・対応不要（こちらが疑って、確かめたら問題なかったもの）

`__V71__.audit()` が `ok:false` を返したので一瞬疑いましたが、
**こちらが直前のテストで `PARAMS.house.buy=true` にしていたため**でした。
読み直してから実行すると `ok:true`・不合格0件です。

## 4. 今回の質問への回答

**1. 詳細設定6ページは、初見で同じ階層のタブに見えるか。**
**PCでは見えます。** 幅1220px・上端163.75px・高さ180.53px・タブ幅185.3px×6が
6ページで完全に一致しており、変わるのは選択中の色と固有コンテンツだけです。
**390pxでは見えません**（P1-1。選択中タブが画面外）。

**2. タブを切り替えたとき、レイアウトが変わった印象は本当に解消されたか。**
**ほぼ解消していますが、7.5pxの横ずれが残っています**（P1-2）。
縦スクロールバーの有無によるもので、`scrollbar-gutter: stable` 1行で消えます。

**3. 詳細設定以外にも、同じ役割の部品が別デザインになっている箇所はあるか。**
**操作要素の名前・構造の面では見つかりませんでした**（全12タブで名前なし0・記号名0・同名0）。
ただし**こちらの測定はDOM属性からの近似で、Chromium の AX ツリーそのものではありません。**
算出順は `aria-labelledby → aria-label → label[for] → 祖先label → 本文 → title` です。
視覚的な余白・密度の網羅比較（computed style の全部品照合）は**未実施**です（§6）。

**4. ボタンの主従関係は全画面で一貫しているか。**
詳細設定の共通シェルでは、6ページとも「入力画面へ（`btn sec`）」「診断を見る（`btn`）」の
順序・クラスが同一でした。**それ以外の画面での網羅確認は未実施**です。

**5. カード・見出し・説明帯・警告の余白と密度は、同じデザインシステムに見えるか。**
**判断していません。** 共通シェルの寸法は測りましたが、
全部品の computed style 比較は行っていないため、答えを持っていません（§6）。

**6. PCでは整っていても、390pxで別の構造に見える箇所はないか。**
**あります。P1-1がそれです。** 加えて、前提（3.7画面分）と教育費（3.1画面分）は
容器内で横に長く、スマホでは読み取りに横スクロールが要ります。
ページ全体のはみ出しは0pxなので**レポートの指標では見えません**が、
「読めるか」は別の話です。

**7. V71の154件QAは、今回の「見た目のばらつき」を十分に再発防止できるか。**
**不十分です（P2-1）。** 負試験6件のうち**3件が検出されませんでした**
（最大幅の変更・上端のずれ・ラベル幅の潰れ）。
**QAレポートが誇る寸法（1,220px・164.75px・181px）を、監査自体は測っていません。**
現物は正しくても、次の改修で壊れたときに気づけません。

**8. V72で最小限どこまで直せば配布可能か。**
**次の3点です。**
1. `html{ scrollbar-gutter: stable; }`（P1-2。1行）
2. 切替後に選択中タブを横スクロールで見える位置へ寄せる（P1-1。10行程度）
3. `layoutAudit` に寸法の一致検査を足し、**わざと壊して落ちることを確認する**（P2-1）

P2-2（旧DOM）は配布を止める理由にはならないと考えます。

【P1-1】モバイルで、選択中の詳細設定タブが画面の外にある
390px幅でタブを実際にクリックして測定した結果：
  住宅とローン → 選択中タブ左端161px（見える）
  教育費       → 299px（右端が切れる）
  資産形成     → 437px（完全に画面外）
  ストレステスト → 575px（完全に画面外）
  用語・制度の解説 → 713px（完全に画面外）
タブ行の表示範囲は x=23〜367px、中身は822px（2.4画面分）です。
切替後の scrollLeft は常に0でした。
原因：6ページがそれぞれ別のタブ行を持っているため、切替後は
「まだ一度もスクロールされていない別のDOM要素」になり、位置を引き継げません。
（scrollLeft=478 までスクロールしてから押しても、切替後の要素は別物で0でした）
影響：「資産形成」を押した直後、タブ行には最初の2つしか見えず、現在地が分かりません。
修正：切替後に選択中タブを横方向だけ中央へ寄せてください。
  row.scrollLeft = sel.offsetLeft - (row.clientWidth - sel.offsetWidth) / 2;
  ★scrollIntoView は縦にも動くので使わないでください。
  ★behavior:'smooth' も避けてください（描画していない環境で動かないことがあります）。
より根本的には、タブ行を1つにして全ページで共有するほうが確実です。

【P1-2】ページを切り替えると画面全体が横に7.5pxずれる
QAレポートは共通シェル左端を「約110px」としていますが、6ページ中4ページは102.5pxでした。
  102.5px：世帯・収入・生活／住宅とローン／資産形成／用語・制度の解説（縦スクロールバーあり）
  110px  ：教育費／ストレステスト（中身が900pxで収まり、スクロールバーなし）
原因は縦スクロールバーの有無です。clientWidth が 1425↔1440 で変わり、
中央寄せの1220pxの箱が (1440-1220)/2=110 と (1425-1220)/2=102.5 の間で動きます。
html の scrollbar-gutter は auto、overflow-y は visible でした。
入力を進めても残ります（ストレステストは v70-gate で常に短いページのため）。
修正：html{ scrollbar-gutter: stable; } の1行です。
今回の改修が狙った「レイアウトが変わった印象」の、最後の一片だと思います。

【P2-1】レイアウト監査が寸法のずれを検出できない

P1-2の7.5pxのずれを素通りしたのも同じ理由です。

  ★測る前に v61SetTab で表示してください（非表示のまま測ると0になります。
