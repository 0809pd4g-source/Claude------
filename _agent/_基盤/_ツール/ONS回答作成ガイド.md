> 作成日: 2026-10-05
> 用途：ONS問合せ（ベンダからの仕様問合せ）の厚労省回答案と、ONS問合せ会議での読み合わせスクリプトを作るときの手順と注意点。
> 出典：2026-10-05のONS回答作成（6件：退院時サマリーFHIR記述／identifier／健診の履歴照会／健診の連携先保険者／患者共有フラグ／緊急時の同意省略）で、ユーザーから受けた指摘と、その場で効いたやり方をまとめたもの。

> 関連：定常業務マニュアル（ONSの会議・台帳運用の正本）、`電カル共有_用語集.md`、`関係者プロファイル.md`

## 1. プロセス（標準の流れ）

1. **問合せを読み、質問を分解する**
   - 質問を1問ずつに分ける。ただし「例えば〜」「もしくは〜」は**直前の質問の言い換え**なので、別の質問として分けない（2026-10-05 identifier件で指摘）
   - ベンダが**混同している言葉**がないかを見る（例：「更新」と「再検査」、「5情報送信のBundle」と「5情報のリソース」）。混同があれば場合分けして答える
2. **経緯を確認する**
   - 同じベンダの前回までの問合せと**厚労省回答の全文**を手元に置く（無ければユーザーに依頼）
   - 基金（機構）コメント・仮回答案があれば読み、区分（厚労エスカレ・回答案**作成**依頼／回答案**確認**依頼）を確認する
3. **一次資料で根拠を確認する**（下の「資料の当たり方」）
   - ページ番号は**原本PDF**で確定させる（MD化した資料はページが分からない）
4. **回答案を書く**（下の「回答文の書き方」）
5. **基金仮案・関連する他の回答案と突き合わせる**
   - 結論が同じか違うか、言い方（強さ・呼び方）がそろっているかを表にする
   - 基金仮案と結論が違う場合は、**根拠を1つに絞って**本田さん相談文を作る
6. **本田さん確認事項（相談文）を作る**
   - 短い本文（論点・ACN案・根拠1つ）＋（補足）の形。補足は必要なものだけ（2026-10-05 ユーザー指示）
7. **読み合わせスクリプトを作る**（厚労省向け。下の「スクリプトの作り方」）
8. **記録する**
   - 会議ごとのフォルダ（例：`01_定常業務/YYYYMMDD_ONS問合せ会議/`）に、最終の回答案・相談文・スクリプト・想定質問を**1ファイルにまとめる**
   - 日次メモの「ONS読み合わせメモ」には要点（経緯・根拠・注意点）だけを書く
   - 新しく出た用語は `電カル共有_用語集.md`、関係者の情報は `関係者プロファイル.md` に追記
9. **台帳綺麗化 → 機構へ連携**（ONSの後。手順の正本は定常業務マニュアル最新版 Section 7-2）
   - 綺麗化：回答欄を整え、M列を「ONS回答済(連携日)」にして本田さんにRv依頼（連携日まではグレーアウトしない条件付き書式。2026-10-06変更）
   - Rv OK後：M列はそのままで機構へ連携。**機構へのコメントはK列**に書き、FIXした回答なので**【回答案】の見出しは付けない**（2026-10-06 本田さんコメント）

## 2. 資料の当たり方

| 知りたいこと | まず見る資料 | 置き場所 |
|---|---|---|
| 本サービスの運用ルール・実装要否 | 技術解説書 v2.1.0 | `_agent/_基盤/_input/`（MD）、原本PDFは `02_仕様・技術/20260723_技術解説書2.1.0版/01_input/` |
| 電文の項目・必須かどうか | 別紙3-1 XMLレイアウト、外部IF仕様書 | `_agent/_基盤/_input/` |
| 退院時サマリー・診療情報提供書のFHIRの書き方 | 各HL7 FHIR記述仕様 第1.13版（巻末に「リソース記述に関する共通表」） | `_agent/_基盤/_input/eDischargeSummaryFHIR_v1x.pdf`、`eReferralFHIR_v1x.pdf` |
| 健診のFHIRの書き方 | 健康診断結果報告書 HL7 FHIR記述仕様 第1.7版 | `_agent/_基盤/_input/eCheckupGeneralFHIR_v1x.pdf` |
| 5情報・identifier・プロファイル | JP-CLINS 実装ガイド v1.13.0 | Web（jpfhir.jp）。**ユーザーにブラウザで原文確認を依頼**する |
| 保険者側の扱い | 保険者向け運用手引き | 厚労省サイト（PDF） |

- 共通表では、5情報などのリソースは「JP-CLINSの診療情報・サマリー汎用を参照」とだけ書かれ、中身は実装ガイド側にある。**記述仕様に書いていない＝指定なし、ではない**（2026-10-05 identifier件で基金仮案がここを誤った）
- Webページを取得ツールで読むと**要約で文言が抜けたり変わったりする**（同じ箇所で根拠の一文が出たり消えたりした）。回答の根拠に使う文は、必ずユーザーに原文を目で確認してもらう
- 資料に「書いていない」ことを根拠にする場合は、どこまで探したかを明記する

## 3. 回答文の書き方

- **質問との対応が分かる形にする**：「＞」で質問を引用し「→」で答える。または「①〜」で直接答える（その場合は1文目で何の回答か分かるようにする）。どちらにするかはユーザーの指示に従う
- **聞かれたことだけに答える**：理由説明・関連知識・聞かれていない注意点は、回答から外して「想定質問」や「Rv用メモ」に回す（2026-10-05 「冗長」「回答に直接関係ある？」と複数回指摘）
- **「前回ご案内のとおり」は、前回回答に同じ内容が実在するときだけ**使う。前回はセクション名だけ・今回は要素名まで、のように粒度が違えば使わない（問合せ対応のため**クレームにつながる**。2026-10-05 指摘）
- **資料の記載と回答方針を混ぜない**：「技術解説書に記載のとおり…『患者同意済』として登録可能」のように、資料にない言葉を資料の記載として読める位置に入れない
- **言い切りすぎない**
  - システムの動き（エラーになる、表示されない等）は、資料で確認できない限り断定しない。「必須項目のため省略できません」→「必ず設定してください」のように**指示の形**にする
  - 厚労省の方針として決まっていないこと（引き継ぎ禁止、周知する等）は書かない。「周知を検討いたします」も約束として受け取られる
  - 「等」で範囲を広げると、例外まで含めて誤解される（例：「5情報以外（CarePlan、Consent等）は指定なし」→Composition等には決まりがある）。範囲が言い切れないときは「ここを見れば分かる」という案内＋例1つにする
- **例示は確認してから使う**：例に挙げるリソース・ケースが本当にその分類に当てはまるかを資料で確認する（Encounterを「5情報以外・指定なし」の例にして誤った）
- **対象の範囲が限られる言葉は、限定を付けて書く**：例）患者共有フラグは感染症5項目だけが対象なので、回答で「検査項目」「検査結果」と書くときは「感染症の検査項目（感染症5項目）」と分かるようにする（2026-10-06 コメント）。「聞かれていないから書かない」より、相手の誤解を防ぐ方を優先する
- **呼び方をそろえる**：同じものを「同意」「患者同意済」「1（紹介元医療機関で同意）」のように複数の言い方にしない。関連する回答案どうしでもそろえる
- **抜粋（参考）の付け方**
  - 前回までの書き方に合わせる：「-------【参考：技術解説書2.1.0版 P.xx 抜粋】-------」
  - 根拠が複数あるときは本文に（※1）（※2）を付け、抜粋の見出しにも同じ番号を付ける
  - 抜粋は**原文どおり**。中略は最小限にし、文脈を切り取ったと受け取られそうなら1文丸ごと載せる
  - 例（傷病名Dなど）を抜粋する場合は、その例の定義も添える
- 回答日は「2026MMDD」のまま置き、送付時に入れる
- **書き方の基礎チェック**（5W1H・平仄・出典・「の」の連続など）は、議事録と同じ `議事録・逐語録_共通ルール.md` §8-1 を使う（全資料共通の正本。2026-10-09）

## 4. 本田さんへの相談文

- 形：①何の件か（区分）②基金仮案とACN案の違い（1〜2行ずつ）③根拠を1つ ④（補足）
- 基金仮案と**結論が違う**とき、**厚労省の方針判断が要る**とき、**回答が未決の相談事項に左右される**とき（例：利用同意も省略できるか）は必ず相談文を作る
- 前提が未確定の回答は「判断をいただいてから回答」と明記する

## 5. 読み合わせスクリプトの作り方

- 厚労省は**FHIRや技術に詳しくない**前提（`関係者プロファイル.md`）
- **1件の型（全件そろえる）**：①何についての質問か（サービス・文書の種類・IF・技術解説書の機能番号）→②ご質問（平易な言葉で言い直す・文章）→③回答案（台帳の最終版の要点・文章、最後に根拠ページ）→④（あれば）機構への連携事項と確認依頼。用語の説明は①の中に一文で入れ、「用語」「前置き」などの別立てや番号付きの問答にしない（2026-10-06 #535だけ構成が違うと指摘）
- **スクリプトは台帳に入った最終の回答案から作る**。台帳の修正（根拠の差し替え、前置きの追加など）が入ったら、スクリプトもその都度直す（2026-10-06 #533の根拠が手引きP.10に変わった）
- **用語は回答文と同じ言葉**：「患者共有フラグ」を「印」と言い換えたら「印ってフラグですか？」と聞かれた。かみくだくのは①の説明文で行い、本文の用語は変えない（2026-10-06）
- 対象の範囲が限られる言葉は限定を付ける（「検査項目」→「感染症の検査（感染症5項目）」）
- **似た分野の質問は続けて読む**：冒頭に「共通の分野の質問です」と一言入れ、各件の型はそろえたままにする（2026-10-06 #534・#536）
- 読む順：ONS問合せ（番号順、似た分野はまとめる）→ 書面開催の週は開発進捗連絡会議の資料の読合せ（5-2）→ 締め
- 想定される質問の表（答え方＋根拠）を用意し、回答から外した注意点・未確認の点を入れておく
- 定着した内容は定常業務マニュアルSection 7-2「読み合わせスクリプトの作成」に反映済み（v26）

## 5-2. 開発進捗連絡会議（書面開催分）の資料の読合せ

- 前週版と今週版を比べ、①全体スケジュールの変更（サイレント変更は不可）②障害報告の有無（会議内で報告必須）③主な差分、の3点を確認する
- スケジュールが画像や図形の場合、文字の比較だけでは線の移動を見落とす。画像は画像どうし、図形は位置・文言を比べる（2026-10-05：富士通は画像で赤線位置のみ差分、NTTデータは図形40個が同一）
- 赤字になっていない変更も拾う（例：富士通の案件176「案件取り下げ」が赤字なし）→口頭で補足
- **スクラム・スプリントはNTTデータ社内の概念**。スプリントの延長・移動を読み上げると「遅れているのか」と受け取られるので、リリース時期・マスタスケジュール・進捗（オンスケ）が変わらないことを根拠付きで補足する（2026-10-05 ユーザー指摘）
- 説明は**スライドの順番どおり**に並べる（投影しながら話すため。2026-10-05 ユーザー指摘）

## 6. 気をつける典型パターン（実例）

| パターン | 実例 | 対処 |
|---|---|---|
| 前回回答の引用の誤り | 前回書いていない内容に「前回もご案内のとおり」 | 前回文を横に並べて確認してから書く |
| 記載にない限定・拡大 | 基金仮案「IG 2.4は臨床情報Bundleのみ」（IGに2文書も同じ仕様と明記） | 原文の見出し・冒頭文を確認 |
| 資料の例示が紛らわしい | 共通表の例「1311234567-2020-00123456」、プロファイルの例がURI形式・別リソースのパス | 回答には書かず、想定質問に入れておく |
| 記述仕様と技術解説書の書きぶりの違い | Encounterは記述仕様で必須（1..1）だが、技術解説書は「叙述のみでも差し支えない」 | 断定せず「確認して後日回答」 |
| 「今後実装」の記載 | 保険者向け運用手引き「今後…実装します」 | 現状を確認できなければ断定しない |
| 「次回改訂で検討」の約束 | Bundle.identifierのハイフン、健診の連携先保険者の明記 | 一覧で管理する（改善案参照） |
| 将来の取扱いの断言 | #537「モデル事業中と本格運用で取扱いは同じ」→ 技術解説書P.2・P.6〜7は「2.1.0版は検証用、全国運用向けは別途公開」（2026-10-08） | 将来の扱いを聞かれたら、まず技術解説書の位置づけ（P.2・P.6〜7）を確認する。関係者の見立ては「現時点では変更予定なし」の形で、確認が取れたときだけ添える |
| ベンダが引用したページをそのまま使う | v1でP.41・P.50・P.74を引用のまま記載し、MD版で抜粋が文の途中で切れていた（2026-10-08） | 原本PDFでページと文末まで確認する。前後の段落も読む（P.50の続きに「文書どうしの関連を確認できるようにしておく必要はない」があった） |
| 台帳の既存案の言い回しの確認漏れ | #519「他セクションの内容もすべて含めて当該セクションのtextに」（P.45と不一致）、#524「表4 CarePlanは特段の指定なし」（systemは固定値）（2026-10-08） | 相談中の案も、根拠の抜粋と1文ずつ突き合わせる。「指定なし」と書く前に、表の各行（system・value）まで確認する |

## 7. 改善案（試していないもの・試し中のもの）

- 2026-10-05：**前回回答の全文を最初に揃える**。毎回「2回目までの回答はこれです」と後から共有されて手戻りした → 問合せを受け取った時点で前回回答と基金コメントをまとめて依頼する
- 2026-10-05：**JP-CLINS実装ガイドの該当ページを手元に保存する**（PDF印刷やHTML保存）→ Web取得の要約に頼らず原文で確認できる
- 2026-10-05：**「次回改訂で検討」と回答した事項の一覧**を作る（技術解説書・手引き等の改訂時に反映漏れを防ぐ）。置き場所は要相談（例：技術解説書プロジェクトの未確認事項、または `_タスク管理`）
- 2026-10-05：回答案を作る前に**「聞かれていること」を1行で書き出す**→ 冗長な回答・聞かれていない注意点の混入を防ぐ
- 2026-10-05：**基金仮案との比較表**（質問×基金案×ACN案×違い）を毎回作る → 本田さん相談文がすぐ書ける
- 2026-10-05：電カル共有サービスの**運用マニュアル（10/1公開版）・医療機関向け指針**を `_agent/_基盤/_input/` に置く → 同意の扱いなど技術解説書にない論点を確認できる
