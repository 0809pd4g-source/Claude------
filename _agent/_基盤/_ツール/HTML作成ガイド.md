# HTML作成ガイド（型）— 手戻りを減らす軽い骨組み

Web/アプリ制作の経験がなくても、思いつきで改修を投げても手戻りが少なくなるための「軽い型」。**型は思いつきを縛るためではなく、思いつきを安く吸収できる土台を最初に作るためのもの**。土台があるほど大胆に試せる（壊れにくい）。

---

## なぜ手戻りが起きるか

HTMLには下に **“土台（骨組み）”の層** がある：目的／画面構成（目次）／色・余白の定義（CSS変数）／版番号・タイトルの一元管理／数値データの持ち方。
- 土台が固まっていれば、思いつき改修は「ここ差し替えて」「この色変えて」で**安く**通る。
- 土台が無いまま積むと、思いつきのたびに全体へ波及して**作り直し**になる。

→ だから「最初の1回だけ」土台を決める。あとは自由に思いつきを投げてOK。

---

## 層1：最初の1回だけ「キックオフ4問」

新規HTMLを作るとき、Claudeが会話で2〜3問だけ埋める。答えは `プロジェクト状況.md` に残して土台にする。

1. **目的**：何が伝われば成功？（1文）
2. **利用者**：誰が見る／前提知識は？
3. **最重要**：これだけは外せない1点
4. **ざっくり構成**：載せたい項目・画面（箇条書き・順不同でOK）
   - （任意）見た目のトーン／色・ダーク要否、数値データの出所・更新頻度

→ これを基に、**CSS変数・版定数・セクションID・データ一元管理**の骨組みを先に作る。

---

## 層2：いつでも「思いつき改修」歓迎（1行テンプレは任意）

添えると手戻りが減るのは **「どこを・どうしたい」** の2語だけ。触ってほしくない所があれば一言。

- 例：「**上のグラフ**、スマホで切れてる → **横スクロールで全部見える**ように。色や他の節は変えないで」
- **曖昧でも全然OK**：「なんか全体が固い → もう少し柔らかい印象に」
  → Claudeが方向を1〜2案出して「これでいい？」と確認してから着手する。

### 添えると効く項目（任意・書ける範囲で）

| 項目 | 例 |
|---|---|
| 場所（どこ） | 「#経済 の表」「ヘッダー」「全体」 |
| 意図（どうしたい／なぜ） | 「スマホで読めるように」「もっと信頼感を出したい」 |
| 触らないで | 「CSS変数・データ構造は変えない」 |
| 完成イメージ（あれば） | 「〇〇みたいな見た目」参考URL・画像 |

---

## Claude側の受け止め方（型を補う）

- 曖昧なら **1〜2点だけ確認** してから着手（意図・場所・スコープ）。
- 着手前に **影響範囲を一言宣言**（「#経済 だけ変えます、CSS変数は触りません」）。
- 大きめの変更は **「こう変えます」を先に提示 → 承認** してから実施。
- 反映は **差分編集**、版は **版フォルダ/`_vN`**、改訂後は **表示・コンソール0・リンク遷移を検証**（下の作業ルール A〜I）。

---

## 思いつきの自由は殺さない

- 層1・層2はどちらも **任意のガードレール**。最初の4問だけ付き合ってもらえれば、あとは何を思いついても安全に反映できる。
- 「型どおりに考える」必要はない。むしろ土台があるほど、思いつきを大胆に試せる。

## 作業ルール A〜I・検証・レビューの規律

HTML（単一ファイル）の新規作成・改訂に適用する。過去の遠回り事例から抽出したルール（2026-10-15 にルート `CLAUDE.md` から移設。HTMLの作業のときだけ読む）。

### Claudeが自動実行すること（明示指示がなくても守る）

**A. 着手前に既存の同種要素を確認する**
- 図・セクション・IDを追加する前に、同名・同種のものが既にないかを確認してから着手する。
- 理由：v39.22で追加した「年齢構成図」が既存の図2と重複し、v39.23でパッチが必要になった。

**B. 版番号はJS定数1箇所で管理する**
- `title`・ブランド表記・フッターの版番号は、`window.VERSION` 等のJS定数1箇所から参照し、複数箇所にハードコードしない。
- 理由：初期設計で分散させると、改訂のたびに更新漏れが起きる（v39.3パッチで修正）。

**C. 色は必ずCSS変数で定義する（ハードコード禁止）**
- 新しい色を追加するときは必ずCSS変数を追加し、ライト/ダーク両モードで意味のある値を設定する。
- 理由：ハードコードするとダークモード追加・修正時に大量のパッチが必要になる（v39でハードコード明色130箇所超を修正）。

**D. 同じ値の計算・設定経路は1本に一本化する**
- 同じ数値を複数の経路から設定できる構造は作らない。1箇所で定義し、他は参照のみにする。
- 理由：ライフプランシミュレーターv4で「維持費が既定値とUI選択で競合」するバグが発生（v5で修正）。

**E. 既存HTMLはEditツールで差分のみ変更する**
- 既存ファイルの改訂は全体書き直しでなく差分編集（Editツール）で行う。
- JSON・大きなデータ操作はスクリプト（`03_scripts/`）で安全に処理する。
- 画像等バイナリを含むHTMLは差分編集を特に厳守する。**埋め込み画像（`data:image/*;base64,...`）を含むHTMLを全体書き直しした場合は、`html_checker.py` でデコード健全性を必ず検証する**（IDATのzlib破損はブラウザが部分表示するため目視では発見しにくい）。
- 理由：大きなHTMLを全体書き直しすると意図しない回帰が起きやすい（v39.9でPythonによる安全なJSON整形を採用）。東ティモールKBではv34時の全体書き直しで地図PNGのIDATが破損し、v39.35まで1.5ヶ月気づかなかった。

**F. 外部依存（CDN・fetch）は提案・導入しない**
- 単一HTMLの方針（オフライン閲覧・配布性）を壊さない。ユーザーの明示的な承認なしに導入しない。

**G. 相互リンクする複数ファイル（サイト等）は「版フォルダ方式」で管理する**
- 個別ファイル名に `vN` を付けず**固定名**にし、版は `02_output/vN/` フォルダ単位で上げる。リンクには版番号を埋め込まない。
- 版フォルダ方式が使えない場合（単一HTMLを `_vN.html` 方式で管理する場合）：他成果物との相互リンクは固定名 `_latest.html` スタブ経由にする（`location.replace(TARGET + location.hash)` でリダイレクトしアンカーを保持）。改訂時はスタブの TARGET 1行のみ更新する。生成ツール: `_agent/_基盤/_ツール/make_latest_stubs.py`。`_vN.html` への直リンクは html_checker.py がWARNで検出する。
- 理由：個人サイト・東ティモール別版で、`_vN` 付きファイル間リンクが版ずれ・改名で切れた（別版はブリーフが索引_v3を指すのに最新は_v4、等）。

**H. サイト名・ブランド・タイトルの表記は1箇所から参照し、必ず一致させる**
- `<title>` と画面見出し(H1)・フッター等のブランド表記を食い違わせない（可能ならBと同様にJS定数化）。着手前に綴り（英字タグ等）も点検する。
- 理由：個人サイトで `<title>`「Field Notes」と H1「Logs」が不一致、タグ `#TravelAisa`（Asiaの綴りミス）が混入していた。

**I. 改訂後は必ず検証してから版を確定する**
- ブラウザ表示・コンソールエラー0・主要リンクの遷移を確認してから確定する（`/ship`）。
- 理由：表示崩れ・リンク切れの手戻りを防ぐ。

詳細は下記「HTML検証プロトコル（/ship 前）」を参照。

### HTML検証プロトコル（/ship 前）— 3層構成

**Layer 1｜静的チェック（常に実施・全HTMLで必須）**

```bash
python _agent/_基盤/_ツール/html_checker.py 02_output/ファイル名.html
```

- FAIL 0件を確認してから /ship する（WARN は推奨対処だが必須ではない）
- チェック内容（ブロッカー）：パース可能・外部CDN依存なし・charset宣言・ID重複なし・内部リンク解決
- チェック内容（警告）：CSS色ハードコードなし・版番号一元管理・title存在・viewport・lang属性・title/h1乖離・console.log残留

**Layer 2｜ブラウザ統合テスト（UIを変更したとき）**

ClaudeCodeのブラウザペインは `file://` が使えない。**`launch.json` に HTTP配信エントリを追加**してからプレビューを開く。

手順:
1. `.claude/launch.json` にプロジェクトのエントリを追加（`python -m http.server` 方式）
2. `preview_start {name: "プロジェクト名"}` でブラウザペインを開く
3. `read_console_messages(onlyErrors=True)` → JSエラー 0件を確認
4. `read_page()` → 主要セクションIDの存在を確認
5. `computer {action: "screenshot"}` → 見た目を視覚確認（UIを変えたとき）
6. `resize_window {colorScheme: "dark"}` → ダーク/ライト両モードを確認（テーマを変えたとき）
7. `resize_window {preset: "mobile"}` → モバイル375px確認（レイアウトを変えたとき）

**検証時の測定の落とし穴（測り方を誤ると誤診する）**

過去に「測り方」が原因で誤判定した実例から。ブラウザ検証で数値を測るときは特に注意する。
- **断りが「見えているか」は、有無ではなく画面上の距離で見る**：`.blankbar` がページ上部に可視でも、結論バナーが遥か下（例：top 1062 vs 9121）にあれば実質見落とす。セクション単位の走査は「ページのどこかにある」を見落とすので、断りと結論の位置関係で判断する。
- **横はみ出しは `scrollWidth - clientWidth` で測る**。`innerWidth` と比べてはいけない：端末エミュレーション下でははみ出すと `innerWidth` 自体が広がり（375のはずが613等）、**差が常に0になって絶対に検出できない**。ただし**ビューポートを明示的に与えたタブ**で測ること：背景タブ・非表示ペインでは `clientWidth` が0になり、あらゆる差分が無意味になる。`scrollWidth < clientWidth`（負値）は縦スクロールバー分であって、はみ出しではない。
- **監査・検証系の関数（`audit()` 等）は測定の前に呼ばない**：呼ぶと経路が再描画され段組みクラス等が変わる。測るなら「呼ぶ前／呼んだ後」を別々に記録する。
- **「console 0件」は新規タブで開いて測る**：ブラウザペインのコンソールは再読込・遷移でも消えず、前ページのエラーが残る。同じタブの再読込で 0件主張をしない。

**Layer 3｜スモークテスト（計算ロジックを持つHTMLのみ）**

- 計算エンジン・シミュレーション系のHTMLのみ作成する（インタラクティブなUIや見た目だけのHTMLは不要）
- `_agent/_基盤/_ツール/smoke_test_template.py` を `03_scripts/smoke_test.py` にコピーして設定する
- `dukpy`（JSエンジン）でブラウザなしに計算ロジックを検証する
- 計算エンジンを変更するたびに実行し、合格基準（CLAUDE.md に記載）とのズレを確認する

```bash
pip install dukpy   # 初回のみ
python 03_scripts/smoke_test.py
```

### レビュー・受入試験・版間比較の規律

自作・他版（ChatGPT版等）の**査読／受入試験／新旧比較**で誤診しやすい点。過去の実例から抽出。

**受け取ったレビューの扱い**
- レビューを受け取ったら、まず**「何件の試験が実際に走ったか」を確認する**（`browser_ran:false`・`ERR_BLOCKED_BY_ADMINISTRATOR` 等で0件のことがある）。走っていない試験があれば、指摘件数を見る前に**その試験をこちらで実行**してから修正に入る。
- 指摘が「合格の作り方（監査の判定方法）」を変えるときは、**何を測らなくなったか**を確認する。監査の合否には**実DOM／実データを測った結果を必ず1つ以上**含め、自作フィクスチャだけで合否を決めない。

**受入試験の書き方**
- 受入試験は**必ず新旧両方に流し、「旧版で落ちる」ことまで確認**する（比較用の試験が旧版で例外→未実行、を防ぐ）。旧版に無いAPIは代用を用意。非同期の入口（`FileReader`・`fetch`）は**待ってから**測る。パス名の正規表現は**末尾一致**にする（部分一致で別欄に当てない）。
- 直した条件そのものだけでなく、**その隣**（もう終わっている／符号が逆／桁が違う／境界のすぐ外）も並べる。
- 試験の対象を絞る正規表現は、**測る前に「何件拾うか」を数えて**確かめる。直した対象と一致しない絞り込みは、製品ではなく試験の欠陥。

**版間比較の作法**
- 比較する列は**`Object.keys()` から作るか存在確認を入れる**（手で列名を並べると、存在しないキーが両側 undefined で「常に一致」として紛れ込む）。
- 他版を測るときは**自分の版の変数名・作法を持ち込まない**。観測点は**相手の実装にある関数を包んで**取る。セレクタが複数一致しうるときは `find()` の先頭でなく**全件を列挙してから選ぶ**。
- 版間比較では、**その版の指紋（正規化した結果のハッシュ）を成果物に記録**する（次回、現物が手に入らなくても比較を続けられる）。

**設計：検査の免除・共通化**
- 検査を免除する分岐を作ったら、**免除した側に何の検査が残るかを数える**（全枝を試験するだけでは、免除側が空になったことに気づけない）。
- 「共通の正本で判定する」と決めたら、**接続する経路を列挙して表にし、1経路ずつ実際に叩いて通っているか実測**する（設計として繋いだつもりは根拠にならない）。
- 同じ値を**2箇所以上で表示**しているなら、**その2箇所の一致**を試験項目にする（食い違いそのものが検査になる）。
