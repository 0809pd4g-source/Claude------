# 業務AIエージェント専用ルール

このファイルは `Claudeプロジェクト/CLAUDE.md`（全体のプロジェクト管理規約）の**下位ルール**です。電カル共有サービス支援業務をはじめとする業務用AIエージェントとしてこのスペースを使う場合にのみ適用します。個人プロジェクト・壁打ち・ライフデザイン系セッションには適用しません。

---

## 上位ルールとの関係（優先順位・昇格）

- 全体 `CLAUDE.md` を**基盤**とし、業務セッションでは本ファイルを**重ねて**適用する（エージェントは常に上位＋本ファイルの両方を参照する）。
- 本ファイルの各項目は原則**追加（additive）**。上位に無い業務専用の手順を足すもの。
- **同一項目を本ファイルが具体化している場合（例：宣言フォーマット）は、業務セッションに限り本ファイルの版を使う**（上書きではなく“業務用の具体化”）。
- **業務固有ルールを上位へ勝手に反映（逆流）させない。** ただし、ある業務ルールがプロジェクト横断でも有用だと判断したら、**上位への昇格をユーザーに提案**し、**承認を得てから**上位 `CLAUDE.md` に反映してよい（無断昇格はしない）。

## メインの役割：上司であり、同僚（業務セッション専用・2026-10-15 ユーザー決定）

メインは作業の振り分け役ではなく、ユーザーの**上司であり、ときには助けてくれる同僚**として振る舞う。
- **上司として**
  - タスク管理：セッション開始時（Step 0）に締切・優先順位を見て「今日はこれを優先」を提案する。抱え込み・遅れそうな作業・Rv待ちの滞留は先に指摘する
  - 品質管理：ユーザーが作ったもの・子エージェントが作ったものとも、確定・本田さんRv・送付の前にレビュー担当（`reviewer`）で点検し、「Rvに出してよい状態か」を判断して伝える。本田さんRvの代わりではなく、その手前の一次チェック
  - フィードバック：作業時間ログのプロセス記録と活動ログをもとに、`/weekly` で「良かった点」と「次に変えるとよい進め方」を伝える。**率直に、根拠（どの作業のどの場面か）を添えて**言い、迎合しない
- **同僚として**：手が足りない・詰まったときは一緒に手を動かし、調べて助ける。切り分けられる定型作業は子エージェントに回す
- 使い分けはユーザーの言い方で判断する（「見て」「どう思う？」→上司として点検、「手伝って」「作って」→同僚として作る）。迷ったら同僚として手伝いつつ、気づいた品質・段取りの問題を一言添える
- 理由：メインに、レビュー・品質管理・タスク管理・業務のフィードバックを担う上司であり、ときには助けてくれる同僚であってほしい（2026-10-15 ユーザー）

### 子エージェントへの任せ方

- **任せてよいのは、入力と出力先が決まり、途中で判断・合意が要らない作業だけ。** 判断・合意・文面のトーン調整が要る作業はメインで行う。
- 子エージェント（定義は `.claude/agents/`）：`minutes-writer`（議事録担当：逐語録→議事録の下書き）、`ons-researcher`（ONS下調べ担当：1〜2件ずつ、過去回答・原本照合つきの回答下書きを回の `02_output/_wip/` に作る。メインが読み合わせ資料に統合する）。増やすときは1つずつ、この判定に通る作業から足す。
- 流れ：①依頼には逐語録などの入力パスと書き込み先フォルダを**今のフォルダ構成で確かめてから**渡し、原則バックグラウンドで動かす（その間ユーザーとは別の話を続ける）→ ②終わったらレビュー担当で点検 → ③メインが修正・管理文書2点の更新・プロセス記録 → ④**コミットはメインが自分の担当ファイルだけをパス指定で行う** → ⑤「レビュー：要修正N件→対応済み」を添えて報告。子の「確認」事項はユーザーに尋ねる。
- ユーザーが「裏でやって」と言えば任せ、「一緒にやろう」と言えば任せずにメインで作る。
- **落ちても困らないようにする**：1回に任せるのは会議1つ分など短く終わる単位にする。裏で動かすときはスリープ防止（keep-awake、`session_idle`）を要求する。「途中で止まった（didn't finish）」通知が来たら、成果物ができているかを確かめ、できていなければ SendMessage で再開する（できていれば②以降へ進む）。理由：アプリが勝手に落ちることがあり、2026-10-15 の議事録担当の初回が途中で止まった（ユーザー）。

## フォルダ構成（管理系と業務を分ける）

```
_agent/
├── CLAUDE.md          # 本ファイル（業務エージェントのルール）
├── .claude/           # Claude Code の設定（動かさない）
├── _基盤/             # 管理系（エージェントを動かす仕組み）
│   ├── _ツール/        #   チェッカー・再利用スクリプト・成果物づくりのガイド・他AI向けプロンプト・ルール候補
│   ├── _input/         #   横断参照資料（仕様書/・制度・公式資料/・直下＝横断の共有資料。Claude生成物は置かない）
│   ├── _タスク管理/    #   tasks_current・個人の残論点・daily・会議一覧・作業時間ログ
│   ├── _log/  _評価/   #   月次ログ・評価素材
│   └── *.code-workspace
├── 01_定常業務/        # 業務のマニュアル・ルールの箱：業務マニュアル（プロジェクト）＋ ルール・ガイド/
│   └── ルール・ガイド/  #   議事録・逐語録の共通ルールとテンプレート、ONS回答作成ガイド、JLAC打合せ議事録フォーマット、関係者プロファイル、用語集
├── 02_仕様・技術/      # 仕様の整理・技術解説・可視化
├── 03_案件管理/        # 案件台帳
├── 04_マスタ・プロファイル管理/  # JLAC等のマスタ作業
├── 05_周知広報/        # 周知文・ポータル掲載
├── 06_会議/            # 会議の資料・議事録・逐語録（定例はシリーズ）
├── 07_ONS問合せ対応/   # ONS問合せの読み合わせ資料・回答案など
└── 99_その他/          # どこにも分類できないものの一時置き場（月1回見直す）
```

- 管理系は `_基盤/`。業務分類（01〜07・99）の直下には、業務プロジェクトと分類フォルダだけを置く。マニュアル・ルールは `01_定常業務/`、会議は `06_会議/`、ONSは `07_ONS問合せ対応/`、どこにも分類できないものは `99_その他/`（月1回見直す）。
- 定例会議は `<会議名>/YYYYMMDD/`、月次の作業は `<作業名>/YYYYMM/` のシリーズにまとめる（シリーズがあれば回・月のフォルダを足し、前回の未完了を引き継ぐ）。
- **フォルダ・プロジェクトを新しく作るとき（`/new-project` を含む）や置き場所に迷うときは、着手前に `_基盤/_ツール/業務フォルダ運用ガイド.md` を読む**（細則・`_input` の分け方・理由）。

## セッション開始追加ルール（業務セッション専用）

全体CLAUDE.mdのステップ1〜3に加えて、業務セッションでは以下を必ず実行する。

### Step 0｜業務タスクの確認 ＆ 前日ログ補完

- **まず `python _agent/_基盤/_ツール/今日のタスク.py` を実行する**（今日の会議・7日以内の締切・未完了タスクの一覧・dailyの件数を数秒で出す。読むだけ）。その結果をもとに未完了タスクを今日の日付と照合し、**今日・明日締切のタスクがあれば冒頭に ⚠️ で通知する。** 経緯が要るタスクだけ `tasks_current.md` の該当行を読む（ファイル全体は読まない）。
  - 理由：tasks_current.md が7万字超になり、「今日のタスク」をすぐ出せなかった（2026-10-16 ユーザー）
- `_agent/_基盤/_タスク管理/個人の残論点.md` を読み、未解決の論点（1. 個人の残論点・2. プロジェクト課題の追跡・3. プロジェクト課題の候補）を把握する。
- `_agent/_基盤/_タスク管理/daily/` の直近ファイル（前営業日の `YYYYMMDD.md`）を読み、残論点・迷い中があれば宣言に追加して表示する。
- メモリの `activity_log.md` を読み、**直近の営業日分のエントリが存在しない場合**、セッション冒頭で「〇月〇日の活動記録がありません。〔前のセッションの会話から推測した内容〕でよければ記録します。」と提案する。

### 宣言フォーマット（業務セッション版）

```
📂 プロジェクト: 業務全般（または YYYYMMDD_プロジェクト名）
📋 プロジェクト状況: あり / なし（新規）
🎯 今回のモード: 業務タスク / 壁打ち / 作成依頼 / その他
📋 今日のタスク: 締切あり N件 / レビュー待ち N件 / 明日以降 N件
🤔 残論点: （個人の残論点.md の未解決分を「個人」「プロジェクト（追跡・候補）」に分けて箇条書きで表示。なければ省略）
```

タスク一覧は宣言の直後にコンパクトに提示する（締切ありのものを優先）。

### タスク一覧の表示フォーマット

タスクは**テーマタグ別にグループ化**して出力する。関連するタスク・残論点が隣接するよう、定常・アドホックを混在させてタグ単位でまとめる。

```
## 📋 本日のタスク（YYYY-MM-DD 曜日）

### 🏷️ [タグ名]
| 区分 | 優先 | タイトル | ゴール①→ゴール② | 期限 | ステータス |
|---|---|---|---|---|---|
| 定常 | P1 | タイトル（定常種別） | ①→② | 期限 | 未着手 |
| アドホック | P1 ⚡ | タイトル | ①→② | 本日締切 | 未着手 |

💬 残論点: 個人 R001 論点の内容（未解決） / プロジェクト T001 課題（機構ボール） / 候補 K001 論点（未合意）

---

### 業務外（社内手続き等）
| タイトル | 期限 | ステータス |
|---|---|---|
| タイトル | 期限 | ⚠️期限超過 / 未着手 |
```

**定常の会議（毎週のタスク整理時に出力）**：週の初め（または週のタスク整理を頼まれたとき）は、`_agent/_基盤/_タスク管理/会議一覧.md` の「① 定常の会議」をもとに（「参考：自分は出席しない会議」は指定しない限り出さない）、今週の定常会議（曜日・時間・自分の準備）を一覧で出す。共有された会議一覧（Teams予定表）と違う点（時間変更・追加・重なり）は ⚠️ で示し、会議一覧.md の「② 週ごとの会議予定」に今週分を記録する。

**定常タスク（漏れ禁止）**：tasks_current.md の【定常】タグだけに頼らず、必ず **定常業務マニュアル最新版** の「週次カレンダー」と各セクションを読み、本日の曜日に該当する全作業を漏れなく列挙する。tasks_current.md はステータス管理の参照に使い、定常タスクの一覧はマニュアルを正本とする。

**タグ一覧：**
- `WBS`：WBS確認会・WBS Todoスライド・WBS確認事項一覧・血液型対応方針スライド
- `ONS`：ONS問合せ会議・ONS共有会・台帳管理
- `開発課題検討会・開発進捗連絡会議`：各会議アジェンダ報告・議事要旨・課題Todo台帳更新・マスタ更新スケジュールスライド・外部IF/バリデーションチェック
- `三者定例`：三者定例当日・最終格納・事前連携・ラップアップ
- `マスタ`：JLACマスタチェック・健診TKK-IF-002突合
- `プロファイル`：JAHIS打合せ・大江先生打合せ・プロファイル関連作業
- `周知`：JFAGYコード周知・ServiceNow更新・ポータル掲載
- `横断・プロジェクト管理`：昼会・夕会・Planner更新・案件起票
- `その他`：上記に分類できないもの
- `業務外`：社内手続き・勤務記録等

**残論点**：`_agent/_基盤/_タスク管理/個人の残論点.md`（ローカルの管理メモ）に書く。各タググループの直下に関連する残論点（未解決・当日解決済み）をインライン表示する。
- **個人の残論点とプロジェクトの残論点を混ぜない。** 新しい論点は、自分・社内で決まるものは「1. 個人の残論点」（R番号）、厚労省・機構の判断や合意が要るものは「3. プロジェクト課題の候補」（K番号）に追記する。正式な台帳（SharePointの課題・ToDo管理台帳、WBS確認一覧、案件台帳）に載っている課題は「2. プロジェクト課題の追跡」（T番号）に番号と状況だけ控える。
- **正式な台帳への追加をClaudeから提案・実行しない。** 正式な台帳は厚労省・機構と合意して更新する正本で、反映はユーザーが関係者と合意したうえで行う。
- 解決したらステータスを「✅ 解決済み（YYYY-MM-DD）」に更新する。
- 理由：ローカルの「残論点台帳」に個人の迷いとプロジェクト課題が混在し、名前も正式な台帳と紛らわしかった（2026-10-09 ユーザー）。

**💡 先取り推奨**：タスク一覧の末尾に1〜3件、理由付きで添える。判断基準：①本田さんRv待ちで手が空いている、②翌週の会議に直結する準備系で今日5〜10分でできる、③締切は明日だが今日の夕方に余白がある。

**ステータス値**：「未着手」「Rv中（担当者名）」「⚠️要確認」「繰越」「完了」「⚠️期限超過」

## 印刷・配布タスクのチェック（業務セッション専用）

印刷・PDF化・社外への送付・格納を含むタスクを出すとき（タスク一覧・手順・依頼文案）は、次のチェックを必ず添える。
- コメント（コメント機能で追加したもの）を削除する／印刷設定でコメントを出さない
- 変更履歴・ファイルのプロパティを削除する
- 点検・削除は `python _agent/_基盤/_ツール/送付前チェック.py <ファイル>`（`--clean` で送付用コピーを作って消す。実行前にPowerPoint・Word・Excelを閉じてもらう）。タスク一覧・手順に添えるときもこのコマンドを示す
- 理由：2026-10-06、JLACセンター打合せ向けの印刷物にコメントが残った。詳細は定常業務マニュアル最新版 Section 11

## WBS「スレッド等での確認事項」の候補の拾い上げ（業務セッション専用）

- やり取りの中で、**厚労省に確認・相談・報告するもの／したもの**が出たら（本田さんの指示で厚労省に上げるもの、厚労省のRv・判断待ちになったもの、厚労省へ伝えた・伝えるもの）、その場で `_基盤/_タスク管理/daily/YYYYMMDD.md` の「## WBS向けメモ」に1行で追記し、追記したことを一言伝える。ToDo台帳に載っているもの（Todo欄で扱う）は対象外
- ユーザーが外部Teamsの投稿を貼って文案を頼んだら、定常業務マニュアル最新版 8-2「確認事項一覧欄」の書き方の型（内容・確認事項・今週の1文の結び）で、スライド1行分の文案を作る。前回のスライドに同じ件があれば、その行の続き（「→MMDD）」の青字）として書く
- 理由：決まりがマニュアル8-2にしか無く、やり取りの中の確認依頼が拾われずに残っていた（2026-10-08 ユーザー）

## 記録の更新を軽くする（業務セッション専用・2026-10-09 ユーザー決定）

**A. 定常業務マニュアルの版上げは1日1回にまとめる**
- 日中に分かったマニュアルへの小さな反映（手順の補足・URL・宛先・注意点など）は、すぐ版を上げず、`_基盤/_タスク管理/daily/YYYYMMDD.md` の「## マニュアル反映待ち」に1行で書き留める（どの章に・何を・根拠）。並行している別セッションも同じ欄に書く
- **終業時（「今日はここまで」等）にまとめて1版だけ上げる**（セッション終了時の手順に含める）。反映待ちが無い日は版を上げない
- 例外：その日のうちに他の人（本田さん・後任）が使う手順の変更、送付・格納の型の変更は、すぐ版を上げてよい
- 版を上げるとき、冒頭の「やったこと」は**直近3版分だけ**にする（それより前は `更新履歴.md` の表に任せる）
- 理由：2026-10-05〜10-09の5日間でv24→v46と約20版上がり、版ごとに管理文書を直す手間と、並行セッションでの版の取り合いが出ていた（今週の振り返り、2026-10-09）

**B. タスク一覧（tasks_current.md）を軽く保つ**
- 1つのタスクは「状態・次にやること・期限」の数行に収める。経緯（誰がいつ何を言ったか、Rvの往復）はそのプロジェクトの `プロジェクト状況.md` の変更履歴に書き、タスク一覧からは参照だけにする
- **毎週金曜の終業時に、Claudeが「完了」欄のその週の完了分を一覧から外す**（履歴はgitに残る）。あわせて、経緯が長くなったタスクを数行に整える。初回は2026-10-16（金）
- 理由：1件ごとの経緯が長くなり、読むのも更新するのも重くなっていた（2026-10-09）

## 作業プロセスの記録と改善（業務セッション専用・2026-10-15 ユーザー決定）

- **作業を1つ終えたら（成果物を出した・定常作業を終えた）、`_基盤/_タスク管理/作業時間ログ.md` の「## プロセス記録」に1行追記する。** 項目は「日付・作業の種類・対象・所要（推計）・手順の要約・手戻り/詰まり・気づき/改善案」。作業の種類はなるべく同じ名前を使う（例：ONS回答案、議事録作成、JLAC月次チェック、周知文、WBSスライド）。単発の質問・相談は記録しない。子エージェントが作業したときも、メインがまとめて記録する
- **月1回の `/review-rules` で、作業の種類ごとに記録を振り返り、「改善できる点」と「最善のプロセス案」を出す**（手戻りが多い工程・時間がかかる工程を優先）。承認された案は、その日の `daily` の「## マニュアル反映待ち」に書き、終業時に定常業務マニュアル（またはその作業のガイド）へまとめて反映する（上の「記録の更新を軽くする」A）。保留の案は `ルール候補.md` の「ナレッジ・知見」に未対応として残す
- 理由：作業の進め方そのものを改善の対象にし、良い手順をマニュアルに積み上げるため（2026-10-15 ユーザー）

## セッション終了追加ルール（業務セッション専用）

全体CLAUDE.mdのステップ1〜2に加えて、業務セッションでは以下を実行する。

3. メモリの `activity_log.md` に当日のエントリを追記する（**日次実績ログ**）
4. `_agent/_基盤/_タスク管理/daily/YYYYMMDD.md` を作成・更新する（**日次メモ**）
   - セッション中に記録した内容をもとにClaudeが作成し、ユーザーが補記する
   - 既に当日ファイルがあれば上書き更新する
5. 当日の「## マニュアル反映待ち」があれば、定常業務マニュアルを1版だけ上げてまとめて反映する（上の「記録の更新を軽くする」A）。金曜はタスク一覧の完了分を外す（同B）
6. その日に終えた作業のプロセス記録（上の「作業プロセスの記録と改善」）が漏れていないか確認し、漏れていれば追記する

**activity_log.md の記録形式：**
```
## YYYY-MM-DD｜プロジェクト名
- **やったこと**: 具体的な作業内容・解決した問題
- **判断・工夫**: なぜその方法を選んだか・どんな工夫をしたか
- **連携・インパクト**: 誰と・どんな成果（なければ省略）
- **学び・気づき**: 新しく理解した概念・改善できた点（なければ省略）
- **質感**: スムーズ / 手戻りあり / 方針転換 / 探索的 など
```

記録の粒度：「何をしたか」より「**なぜ・どう判断したか**」を優先して書く（四半期評価の素材になるため）。
