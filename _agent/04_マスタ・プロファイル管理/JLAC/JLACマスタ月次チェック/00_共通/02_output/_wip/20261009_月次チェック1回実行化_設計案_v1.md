## 結論（3行）

1. 判定・送付用・ACN確認用・報告は、ツールv20ですでに1回の実行で出ている。時間がかかっていたのは、その**前後の手作業**（ファイルと設定の指定、ダブルチェックの準備、指摘の理由の説明、送付前確認事項の整理、送付用とACN確認用への同じ修正の二重反映、000コード）だった。
2. 入口を `月次実行.ps1 -Month 202611提出分` の1コマンドにする。今月の設定は1ファイルにまとめ、これまでの出力に加えて、ダブルチェック（Excelで計算まで）・不一致の一覧・指摘ごとの根拠と説明文の下書き・前月の依頼が反映されたかの確認・000コード候補を出す。説明文の下書きは、jlac-coreが判定したときの根拠（新規と判定した理由・前月の同じチェックの結果・照合した値）から作る。判定そのものは変えない。
3. 11月分（2026-11-02（月）ごろに受領の見込み）までに作るMVPは、Claude Codeの作業で約9〜12時間。後回しにするのは、コメントの差し替えを設定ファイルで行う仕組み、二次Rvシートの自動引継ぎ、HTML版への反映。

### 2-4. 指摘の根拠と説明文の下書き

**考え方**：説明文はjlac-coreが判定したときの材料から機械的に作る。人が判定の仕組みを推し量って書かない（10/6の誤りの再発防止）。判定（どの行にどの指摘を付けるか・既知か）は変えない。

jlac-coreで指摘を記録するとき（`rec()`、v20の975行目付近）に、次の根拠を指摘明細に足す。判定の結果は変えず、記録を増やすだけ：

| 根拠の項目 | 中身 | 例（10/6再提出の既存行KA-08・1104行目） |
|---|---|---|
| 新規/既存の理由 | 「前月に同じJLAC11コードが無い」「連絡の新規行の開始行（13436）以降」「前月の何行目と対応」 | 前月の1104行目と対応（既存行） |
| 前月の同じチェック | 前月の対応する行で同じチェックに当たっていたか。当たっていたなら前月の文面 | 前月も当たっていた（文面：測定法「IFCC対応法_…‐…」…） |
| 既知と判定しなかった理由 | 「前月は該当なし」または「前月も該当。値が変わったため文面が違う」 | 前月も該当。測定法の値が変わったため、文面が違う |
| 照合した値 | 今の値・照合先（ファイル名・シート・列）・照合先の値 | 「IFCC対応法_…-…」／jlac11_3_1.1b.xlsx「測定法名称」列／「…」 |
| JLACセンターのコメントとの照合 | 一致した差分・一致しない差分 | ハイフンの変更が一致（連携済み）。ただしKA-08は残る |

説明文の下書きは、根拠の組み合わせごとに決まった文で作る（型は4つ程度）。例：
- 前月も該当・値が変わった：「前月も〔照合先〕と表記が異なる既知の行です。今回、〔項目〕が「旧」から「新」に変わったため、指摘の文面が前月と変わり、新しい指摘として出ています（ツールは指摘の文面が前月と同じときだけ既知とする設計のため）。」
- 前月は該当なし：「前月は該当していません。今回の変更（〔項目〕「旧」→「新」）で〔チェック名〕に当たるようになりました。」
- 新規行：「新規行（理由：〔新規/既存の理由〕）のため、すべての結果を指摘しています。」

出し方：ACN確認用に「指摘の根拠」シート（コメントを付けた行ごとに1行：行番号・JLAC11コード・チェックID・上の根拠・説明文の下書き）を足す。送付前確認事項_一次Rvの候補の「【結果】」の後ろに、説明文の下書きの代表1件を入れる。**下書きであることを見出しに書く**（「判定の材料から自動で作った文。ダブルチェックの照合が済んでから使う」）。

判定ロジックに手を入れないための確かめ方：v20とv21で、送付用の全シート・指摘明細（根拠以外の項目）・通知・コメントが一致することを `compare_outputs.py` で確かめる（5章）。

代わりの案（jlac-coreを変えない）：外のスクリプトで、`J._t.rowChecks` と前月の行を使って根拠を計算し直す。ただし前月の行の対応づけ（`bestPrev`）が外から呼べず、同じ処理を書き写すことになるため、勧めない（ロジックを別の場所に書き写さない、という月次の `CLAUDE.md` の決まりに反する）。

### 2-5. ダブルチェックと照合の自動化

- `make_doublecheck.py` の先頭の定数9個をやめ、明細.json の `settings`（提出ファイル・シート名・新規行の開始行・公開日・連絡用の列）と設定ファイルから読む。10/1提出版用の旧スクリプトは残したまま、新しい方は前月公開CSVだけに対応する（今と同じ）。
- **独立性を保つ決まり**：ダブルチェックがツールから受け取るのは「どのファイル・どの設定で実行したか」だけ。判定の結果は照合のときに読むだけで、検算の式には使わない（今と同じ）。設定が両方で同じになるため、設定の誤り（公開日の入れ違いなど）はダブルチェックでは見つからない。その分は2-2の設定の点検で止め、照合シートの先頭に使った設定を書いて目で確かめる。
- Excelでの計算：PowerShellからCOMで開き、`CalculateFull()` → 保存 → 閉じる。Excelがすでに起動しているとき・ファイルが開かれているときは実行しない（`送付前チェック.py` と同じ安全策）。時間の上限（例：15分）を決め、超えたら止めて「Excelで開いて手で計算」と案内する。
- 照合の読み取り：計算・保存後のファイルを読み取りだけで開き（openpyxlの `data_only=True`。保存はしない）、「照合」シートのE列が「不一致」の項目と、「今回」シートの行ごとの一致列（BG〜BK）が0の行を一覧にする。
- 「比較できない項目（—）」の数も出す。比較できる項目が前回より減ったら警告する（何を測らなくなったかを見落とさないため）。

- 引継ぎファイルは、送付を確定したときに作る（送付確定版のコメントから「削除を依頼」「修正を依頼」「追加」を拾って下書きを作るのは後回し。MVPでは手で書く。10月分は上の表のとおり）。
- これはチェックロジック外の確認で、jlac-coreの判定には入れない。

### 2-7. 送付用とACN確認用のずれの確認（MVP）、修正を1か所にまとめる（後回し）

- MVP：送付用のコメント列とACN確認用のAH列（連絡用の列が無い月はAG列）を、見出しの名前で探して全行比べ、違う行を一覧にするスクリプト（読み取りだけ）。今は毎回手で確かめている「AH列と全行一致」を自動にする。
- 後回し：Rvで直したコメントを `04_reference/コメントの調整.txt`（`行番号 ｜ JLAC11コード ｜ 差し替える文／追記する文`）に書き、ツールにかけ直すと送付用とACN確認用の両方に入る形。同じ修正を2つのファイルにする作業がなくなり、再提出のときもそのまま使える。jlac-coreの出力部分（`buildOutput`）を変えるため、v22以降で別に行う。

## 4. 1回の実行の流れ（MVP完成後）

1. 提出ファイルを `202611提出分/01_input/` に置く（前月公開CSV・コード表も）

4. 「月次実行の結果.md」を上から読む。ダブルチェックに不一致があれば、原因を調べるまで説明文を確定しない
5. ACN確認用の「送付前確認事項_一次Rv」を整え（候補と説明文の下書き・引継ぎの確認の結果が入っている）、本田さんにRvを依頼する
6. Rvを反映し、ずれの確認を流してから、`送付前チェック.py --clean` で送付用を作って送る

## 6. リスク

| リスク | 対策 |
|---|---|
| 根拠を足すときに、判定を変えてしまう（関係者合意済みのロジック） | 根拠は記録を足すだけにし、T1・T2で送付用・明細・通知の一致を確かめてから版を確定する |
| 説明文の下書きを、そのまま確定した説明として使ってしまう | 見出しに「下書き」と書き、ダブルチェックに不一致があるときはまとめ.mdの冒頭で止める |
| ダブルチェックがツールと同じ設定を使うため、設定の誤りは両方で同じになり、見つからない | 設定の点検（2-2）で止める。照合シートの先頭に使った設定を書く |
| Excelでの計算が遅い・止まる（ダブルチェックは約13MB。10/6分） | 時間の上限で止めて手での計算を案内する。Excelの起動中は実行しない。推測：数分〜10分程度（未計測。M2で測る） |
| JLACセンターの提出の形が変わる（列の数・シート名・新規行の連絡のしかた） | ファイルの役割の判定・列の見出しの照合で合わなければ止める（今のツールの判定を使う）。新旧混合に変わったとき（10/6）のように、ツールの版上げで対応する |
| PowerShell・Node・Python・Excelのどれかが無いPC（後任など） | HTML版は今のまま使える。手順書に「ダブルチェックはClaude Codeがある担当者が行う」と書く（論点1） |
| 引継ぎファイルの書き忘れ | 前月の月フォルダに送付確定版があるのに引継ぎファイルが無ければ、警告を出す |
