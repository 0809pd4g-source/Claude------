## #519 退院時サマリーの本文（text）と、参照するリソース（entry）の関係（日本IBM様・3回目）

### まず押さえること（説明の前提）

**退院時サマリーのFHIRデータの組み立て**（技術解説書P.42 図7「退院時サマリーのFHIR Document構成」）
```
退院時サマリー（Bundle：データ全体の入れ物）
└ Composition（文書の本体・目次）
   ├ ヘッダ部：患者（Patient）・入院情報（Encounter）・作成者（Practitioner）・作成機関（Organization）
   ├ 構造情報セクション
   │   ├ 入院時詳細セクション（コード322） … text＝「入院時詳細」欄の文章／entry→Encounter（1つ）
   │   ├ 入院時診断セクション（コード342） … entry→Condition
   │   ├ 入院中経過セクション           … entry→DocumentReference
   │   └ …（全23セクション）
   ├ 添付情報セクション … entry→DocumentReference
   └ PDFセクション     … entry→DocumentReference
```
- 各セクションには、2つの欄がある
  - **「text」**：人が読む本文。PDFに表示される文章と同じものを書く（Narrative＝ナラティブ記述と呼ぶ）
  - **「entry」**：機械が読む構造化データへの参照。**どのリソースを入れるかは、セクションごとに決まっている**
- **入院時詳細セクション**：退院時サマリーの「入院時詳細」欄のこと。例：「2025年7月20日に発熱と呼吸苦で救急外来を受診し入院。」（技術解説書P.57）。entryには、入院日・入院時病名・入院目的などを持つ入院情報（Encounterリソース）を1つ入れる
- **DocumentReference**：文書や添付ファイルを参照するためのリソース。退院時サマリーで使うのは、入院中経過セクション・添付情報セクション・PDFセクションだけ

### どんな質問か
日本IBM様は、入院時詳細セクションを例に質問している。
- 前提：入院時詳細セクションの「text」に、PDFに書いた文章（「入院時に確認した情報のナラティブ記述」）を入れている。「entry」には、仕様どおりEncounterを入れている
- **①（二択）**：その「text」の文章を、DocumentReferenceにして「entry」にも**追加すべきか**。それとも、各セクションに決められた型（入院時詳細ならEncounter）**以外は追加しない方がよいか**
- **②**：「entry」に入れたEncounterの「text」（入院時病名・入院目的など）を、入院時詳細セクションの「text」にも書く必要があるか。退院時サマリー（PDF）に書いていない内容でも書くのか

### 回答の考え方
- **①**：二択にそのまま答える。「追加すべきか」→必要ない。「決められた型以外は追加しない方がよいか」→追加しない。entryに入れるリソースはセクションごとに決まっていて（図7、共通表P.38「セクション構成の表のリソース種別・多重度が適用される」）、入院時詳細はEncounterだけ
- ①の2文目の「各セクション」は**全セクション**のこと。どのセクションでも「決められたもの以外は入れない」が成り立つので、範囲を広げても事実と食い違わない（「各セクションでDocumentReferenceは使えない」と書くと、入院中経過セクションで誤りになるので書かない）
- **②**：textとPDFは必ず一致させる決まり（P.43）。本文に書いていないものは、構造化データとしてだけ持たせる（P.43の「傷病名D」の例と同じ考え方）。だから、Encounterの中身をtextに写す必要はなく、PDFにない入院時病名・入院目的はEncounterにだけ入れる
- ②の「当該セクション」は、Encounterを参照している**その1つのセクション**（例では入院時詳細セクション）のこと。①の「各セクション」と混ざらないよう、1文目で例を示す
- 言葉は相手に合わせる：ベンダは「text」「entry」とかぎ括弧で書いているので、回答も「section.text要素」ではなく「text」「entry」にする
- 「前回回答のとおり」は、前回（9/2）に「PDFに表示する文書内容とNarrativeの内容は必ず一致する必要があります」と実際に回答しているので使える

## #524 紹介状などに含まれるリソースのID（identifier）の書き方（エーシーエス様・2回目）

### まず押さえること（説明の前提）

**IDは2種類ある**
- **Bundle.identifier**：送るデータの「まとまり全体」に付けるID。紹介状1通、臨床情報の1回分の報告などのまとまりを見分けるために使う（技術解説書P.120「機能3：Bundle.identifierの付与」）
- **各リソースのidentifier**：まとまりの中に入っている「1件1件のデータ」（傷病名1件、アレルギー1件など）に付けるID（JP-CLINS実装ガイド「５情報送信仕様」2.4）
- 形はどちらも同じで、3つの値を「^」（半角ハット記号）でつなぐ：**保険医療機関番号（10桁）^発行年（4桁）^施設内で重ならない識別子**
  - 施設内の識別子は、Bundleは「半角英数字1〜36文字」（技術解説書P.120）、リソースは「半角英数字と半角ハイフン36文字以内」（実装ガイド2.4）。ハイフンの違いは前回（9/16）「Bundleもハイフン可、技術解説書は次回更新で修正を検討」と回答済み（外部への約束P001）

**5情報と2文書**
- **5情報**（臨床情報）：傷病名・感染症（5項目）・検査（43項目）・薬剤アレルギー等・その他アレルギー等（技術解説書P.73 表17）
- **2文書**：診療情報提供書（紹介状）と退院時サマリー。文書の中にも傷病名やアレルギーなどが書かれる
- 2文書の中に書かれた5情報は、本サービスが取り出して5情報として管理する（実装ガイド）。だから、2文書の中でも5情報と同じ書き方にする必要がある

**データの組み立てで見るとこうなる**
```
臨床情報（5情報）を送るとき             診療情報提供書を送るとき
Bundle（ID：Bundle.identifier）          Bundle（ID：Bundle.identifier）
├ Patient（患者）                        ├ Composition（文書本体）
├ Condition（傷病名）   ← ID：形式あり   ├ Patient（患者）
├ AllergyIntolerance    ← ID：形式あり   ├ Condition（傷病名）   ← 5情報に当たる：同じ形式（今回の論点）
└ Observation（検査）   ← ID：形式あり   └ CarePlan（診療方針）  ← 5情報以外：それぞれの仕様に従う
```

**どこに書いてあるか（資料の地図）**

| 2文書の中の5情報も同じ仕様で書くこと／5情報以外は各仕様でよいこと | 同上 | 2.1.2.2の後の「2文書に含まれる５情報に該当する情報の記述方法」「2文書に含まれる５情報以外の情報の記載と取り扱い」（手元PDFの2ページ目） |

### どんな質問か
前回、「5情報のリソースのIDは『保険医療機関番号^発行年^施設内ID』の形で設定してください」と回答した。今回は次の2点。
- **1点目**：この形にするのは、5情報を送るときに組み込むリソースだけか。紹介状など、ほかの送信用のまとまり（Bundle）に組み込むリソースのIDには、特に決まりがないのか
- **2点目**：BundleのIDとリソースのIDは、今の仕様では同じルールで、それぞれ重ならないように付ければよいか

### 回答の考え方
- **1点目**：「5情報を送るときだけ」ではない。紹介状・退院時サマリーの中に入っている5情報のリソースも、本サービスが取り出して5情報として管理するので、同じ形式にする（実装ガイド）。5情報以外のリソース（CarePlanなど）は、それぞれのFHIR仕様やJP-Core仕様に従ってよい（実装ガイドの次の段落）。具体的な書き方は共通表で見てもらう。例のCarePlanは、identifierは任意だが、入れる場合はsystemに決まった値を入れる（valueの形式に指定はない）
- 「特に決まりがないのか」という問いに「指定はない」とだけ答えると、systemの固定値まで不要と読まれるので、CarePlanの例で「任意だが入れるなら決まりがある」ことを示す
- **2点目**：BundleのIDもリソースのIDも、3つの値を^でつなぐ同じ形で、それぞれの範囲で重ならないように付ける（技術解説書P.120、実装ガイド2.4）。「ご認識のとおり」と答える
- 機構の仮案（紹介状の中のリソースは特に指定なし）とは、1点目の結論が逆。実装ガイドの記載が根拠

### まず押さえること（説明の前提）

**退院時サマリーの送り方**
- 退院時サマリーは、紹介状（診療情報提供書）の**添付文書**として、紹介状と一緒に送るのが基本（技術解説書P.41、運用マニュアル4.00版P.208）
- ただ、紹介状を送る時点で退院時サマリーがまだできていないこともある。そのため、紹介状を送ったあとや患者の退院後に、退院時サマリーを**追加で送る（追加送付）**ことができる
- 追加送付の方法は3つ（技術解説書P.41）

| 方式 | やり方 | 受け取る側から見ると | 注意 |
|---|---|---|---|
| ① 更新 | 先に送った紹介状を更新し、退院時サマリーを添付して登録し直す | 紹介状が新しい内容に置き換わる | 紹介先がすでに紹介状を取得していたら使えない |
| ② コピーして新規 | 先に送った紹介状をコピーして新しい紹介状を作り、退院時サマリーを添付して新しい文書として登録する | **同じ内容の紹介状が2通届く**（今回の論点） | ― |
| ③ 頭紙（送付票） | 必要最低限の項目だけの頭紙（送付票）を作り、退院時サマリーを添付して新しい文書として登録する | 送付票＋退院時サマリーが届く | 実装は任意。前に送った紹介状と、システムで関連づける必要はない（P.50） |

- 技術解説書は「追加送付が起きるかや、紹介先との連絡方法を確認したうえで方式を選んでください」としている（P.41）。つまり、受け取る側の混乱は、システムではなく医療機関どうしの連絡で防ぐ前提

### 回答の考え方
- 後から退院時サマリーを送るときに相手の病院へ一報入れることは、今の（電カル共有を使わない）退院時サマリーのやり取りでも行われていると考えられる。「追加送付」という仕組みは電カル共有ならではだが、連絡そのものは**従来の運用を踏襲**する形で答える
- ベンダの認識とは一致しない点があるので、「ご認識のとおり」とは書かない

| | ベンダの認識 | 回答の考え方 |
|---|---|---|
| 誰に連絡するか | 相手の病院の**システム担当者** | 紹介先の医療機関（医師・医療事務どうしのやり取り） |
| 位置づけ | 電カル共有のための**追加の対応** | 従来の退院時サマリーのやり取りの**踏襲** |
| システムの外で対応するか | 外で対応 | 外で対応（ここだけ一致） |

## #530 健診結果を取り消す・変更する前に、保存されているかの照会は必須か（エクセル・クリエイツ様・1回目）

### まず押さえること（説明の前提）

**健診文書に対する操作**（インターフェイスIDは機能IF一覧・技術解説書P.184 表46）

| 操作 | 何をするか | インターフェイス |
|---|---|---|
| 登録 | 健診結果を本サービスに送る | CIS-IF-120／121 |
| 取消 | 登録した健診結果を消す（誤って登録したとき） | CIS-IF-122／123 |
| 変更 | 登録した健診結果を正しい内容に置き換える | CIS-IF-124／125 |
| 登録情報の履歴照会 | 自分の医療機関が登録した健診結果が、今も本サービスに保存されているかを確認する | TKK-IF-004／005 |

- どのデータを消す・変えるかは、登録したときのID（Bundle.identifier）で指定する（技術解説書P.155）
- **保存期間**：健診文書は登録後5年間保存され（技術解説書P.58）、過ぎると本サービスから消える
- **変更は、実質的に「取消＋正しい内容での新規登録」と同じ処理**（技術解説書P.155）。そのため、変更の機能を作らず、取消と新規登録の組み合わせで代えてもよい（P.184 表46）
- **保存期間を過ぎたデータに対する操作**
  - 取消：データがないのでエラーになる（技術解説書P.156）
  - 変更：臨床情報は「新規登録」として扱われる（技術解説書P.155）。**健診は、エラーになる**（NTTデータ・富士通の回答、9/18。技術解説書には書かれていない）
- なぜ取消の前に照会が要るか：「期限切れでデータがない」エラーと、「IDの間違いなど別の原因」のエラーを、システムが区別して返せない。そのため、期限切れのデータに取消を何度繰り返してもエラーが出続けてしまう（機構の9/7の仮案の説明）

**どこに書いてあるか（資料の地図）**

| 知りたいこと | 資料 | 場所 |
|---|---|---|
| 取消の前に照会すること | 技術解説書2.1.0版 | P.156「取消要求の取扱い」 |
| 照会の機能は実装必須であること | 技術解説書2.1.0版 | P.154「本機能および対応する外部インターフェイスの実装要否について」 |
| 変更＝取消＋新規登録、臨床情報の期限切れの変更 | 技術解説書2.1.0版 | P.155「機能15：登録情報の削除・更新」 |
| 健診文書の保存期間（5年） | 技術解説書2.1.0版 | P.58 |
| 変更の機能は省略できること | 技術解説書2.1.0版 | P.184 表46 |
| 健診の期限切れの変更がエラーになること | 台帳 #530 K列 | NTTデータ・富士通の回答（9/18） |

### どんな質問か
健診結果を取り消す、または変更する前に、「登録情報の履歴照会」を行う必要があるか、という質問。ベンダの理解は次のとおりで、その理解でよいかの確認。
- **(1) 取消**：技術解説書P.156に「保存されているかを照会で確認し、データがある場合だけ取消を行ってください」とあるので、取消の前の照会は必須
- **(2) 変更**：P.155には、同じIDで登録し直すこと、変更は「取消＋新規登録」と同じであること、期限切れの臨床情報の変更は新規登録になることは書いてあるが、変更の前に照会するとは書いていない。だから、変更の前の照会は必須ではない（任意）

### 回答の考え方
- **(1)**：P.156のとおりで「ご認識のとおり」。あわせて、その照会のために照会の機能は電子カルテ側で必ず作ることになっている（P.154）ことを添える
- **(2)**：問いは「必須ではない（任意）という理解でよいか」。技術解説書は変更前の照会を必須とはしていないので、まずそこに答える。ただし、
  - 変更は実質的に取消＋新規登録と同じ（P.155）
  - 健診は、期限切れのデータを変更するとエラーになる（臨床情報のように新規登録にはならない。NTTデータ・富士通の回答）
  - そのため、取消と同じく、照会で確認してから変更していただくようお願いする。技術解説書に書いていないので「行ってください」ではなく「お願いいたします」にとどめる
- 本田さんの指示（技術解説書を書いたときに機構へ説明した内容を、機構にコメントで返す）に沿って、機構の9/24のコメントに1つずつ答えるコメントを台帳K列に付ける

## #537 臨床情報の登録タイミングを、システムで管理する機能は必要か（SBS情報システム様・1回目）

### まず押さえること（説明の前提）

**臨床情報とは**（技術解説書P.73 表17）

| 情報 | 中身 | 保存期間（通常） |
|---|---|---|
| 傷病名 | 診断をつけた傷病名 | 登録日から5年間 |
| 感染症 | 梅毒STS・梅毒TP抗体・HBs・HCV・HIVの5項目の検査結果 | 登録日から5年間 |
| 検査 | 救急・生活習慣病に関わる43項目の検査結果 | 登録日から1年間、または直近3回分 |
| 薬剤アレルギー等 | 薬剤のアレルギー等 | 登録日から5年間 |
| その他アレルギー等 | 食品・飲料・環境などのアレルギー等 | 登録日から5年間 |

- 医療機関が電子カルテから本サービスに登録すると、ほかの医療機関・薬局や、患者本人（マイナポータル）が見られるようになる（P.73・P.74）

**登録するタイミングの決まり**（技術解説書P.74）
- **基本**：いつ登録するかは、各医療機関の判断に委ねる
- **外来**：タイミングの「目安」が示されている
  - 傷病名：病名リストを登録・更新したとき
  - アレルギー：アレルギーの入力欄を登録・更新したとき
  - 検査・感染症：検査結果が電子カルテに入ったとき
  - その場ですぐ登録（リアルタイム処理）を「推奨」。夜間にまとめて登録してもよい
- **入院**：入院中に発生した臨床情報は「**退院日当日中（夜間も可）までに登録してください**」（ここは推奨ではなく決まり）。ただし、退院日までに結果が出ない検査は、結果が出たときに登録する
- **自動登録**：「カルテを閉じたときに自動で登録する仕組みなどが考えられます」という例として書かれている。あわせて「医師等の判断で手動登録を選べるようにすることも可能」とある

**技術解説書2.1.0版の位置づけ**（P.2、P.6〜7）
- 2.1.0版は「モデル事業で検証するための内容」で、まだ最終確定ではない
- 全国で運用を始めるための確定版は、別に公開する（令和8年度冬頃に次版を公表予定）

**SBS様の状況**
- モデル事業に参加している電子カルテのベンダ。今は電子カルテとは別のアプリ（送受信アプリ）から、医師が中身を確認して手で登録している

**どこに書いてあるか（資料の地図）**

| 知りたいこと | 資料 | 場所 |
|---|---|---|
| 登録タイミングの決まり | 技術解説書2.1.0版 | P.74「臨床情報の登録タイミングおよび留意事項」 |
| 臨床情報の種類と保存期間 | 技術解説書2.1.0版 | P.73 表17 |
| 2.1.0版の位置づけ（検証用・次版の予定） | 技術解説書2.1.0版 | P.2「改版の経緯」、P.6〜7「1.2 本書の前提」 |

### どんな質問か
SBS様は、モデル事業の間は、登録タイミングを管理する機能（電子カルテの登録・更新をきっかけにした自動登録、退院日までの登録を促す機能など）は作らず、運用で対応したいと考えている（外来は同じ日のうちに、入院は退院日当日中に、アプリから手で登録する）。そのうえで4点の質問。
- **(1)** P.74の登録タイミング（外来の目安・リアルタイム処理）は推奨で、タイミングを管理する機能を備えることは必須ではない、という理解でよいか
- **(2)** 退院日当日中の登録は、モデル事業の間は、機能ではなく医療機関の運用（手動登録）で守ればよいか
- **(3)** (1)(2)の扱いがモデル事業中と本格運用で違うなら、それぞれ教えてほしい
- **(4)** 機能が必要な場合、最低限どこまで作ればよいか（登録漏れの通知でよいか、自動登録が必要か）

### 回答の考え方
