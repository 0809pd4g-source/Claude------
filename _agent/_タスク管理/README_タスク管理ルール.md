# タスク管理ルール

> 作成: 2026-10-01

## タスクの分類

| 分類 | 定義 | 例 |
|---|---|---|
| **定常** | 毎週・毎月のルーティンで発生するもの | WBS Todoスライド更新、議事要旨確認、ONS台帳更新 |
| **アドホック** | 特定のアウトプットを作るために発生するもの。WBS向けの個別資料は「WBS向け個別資料作成（アドホック）」の子項目として整理するが、WBS向けでないものは独立したタスクとして記載 | 血液型資料（WBS向け）、JFAGYコード周知文案、FHIRパス確認 |
| **業務外** | 社内手続きなど業務プロジェクトに直接関係しないもの | 勤務記録申請 |

## タスクのステータス

| ステータス | 意味 |
|---|---|
| **未着手** | まだ手をつけていない |
| **着手中** | 作業中 |
| **要相談** | 方針・形式・スコープが未確定で着手できない |
| **レビュー中（〇〇さん）** | 自分の作業は完了し、他者のレビュー待ち。必ず誰のRv中かを明記する（例：レビュー中（向井さん）） |
| **相手待ち** | 他者のアクション（回答・連携・承認）待ち |

## ファイル構成

| ファイル | 用途 |
|---|---|
| `tasks_current.md` | 現在のタスクリスト（締切カレンダー含む） |
| `daily/YYYYMMDD.md` | 日次メモ（その日の作業記録・残論点・翌日やること） |
| `README_タスク管理ルール.md` | 本ファイル（分類・ステータスの定義） |

## タスク表示フォーマット（セッション開始時・確認時）

| 列 | 内容 |
|---|---|
| **優先順位** | P1（今日中）/ P2（明日まで）/ P3（それ以降・超過）|
| **タイトル** | 一目で内容が分かる短い名前。文書・IF・領域・マスタが重要な文脈は必ず含める |
| **ゴール** | 2段階で記載。①本田さんRv依頼まで（中間ゴール）→ ②最終アウトカム（厚労省連携・基金回答・上位者RvOK等）。本田さんRvが不要なタスクは①を省略してよい。②が未確定の場合は「②TBD」と書き、分かり次第更新する |
| **期限** | 絶対日時で記載。「実質今日中」は理由も添える |
| **ステータス** | 未着手 / 着手中 / 要相談 / レビュー中（〇〇さん） / 相手待ち |

### セクション見出しのルール

- **定常（本日対応推奨）**：今日の曜日に発生する定常業務。期限が今日とは限らないが、今日着手・対応すべきもの
- **アドホック（全件）**：期限問わず全アドホックを表示。⚡マークは早期着手推奨
- **繰り越し**：期限が過去日のもの

### 早期着手推奨（⚡）の運用

- 翌日以降が期限でも、以下の条件を満たす場合は **⚡早期着手推奨** とタイトルの先頭に付ける
  - 他者のRv時間が必要（本田さん・向井さん等にRv依頼が必要なもの）
  - 前工程が別タスクに依存する
  - 不確定要素が多くバッファが必要
- タスク一覧の出力時は、⚡タスクを「明日締切」より前に目立つ位置に表示する

## tasks_current.md の更新ルール

- 「〇〇完了」「〇〇追加：内容（締切）」と伝えればClaudeが更新する
- WBS向け個別資料は「WBS向け個別資料作成（アドホック）」の子項目として記載する
- 業務外タスクは業務タスクとは別セクションに記載し、セッション開始時のタスク宣言にも表示する
- 完了したタスクは `完了` セクションへ移動する（削除しない）

## タスク拾い漏れ防止ルール（必須）

タスクの拾い漏れは業務崩壊につながる。以下を必ず守る。

### ルール1：情報を受け取ったらその場でtasks_current.mdに追加する
- ユーザーから作業内容・依頼・メモを受け取った瞬間に、daily memoだけでなく **tasks_current.mdにも同時に追加する**
- 「daily memoに書いたからOK」は禁止。tasks_current.mdが唯一のタスク管理台帳

### ルール2：daily memoの「確認待ち・要対応」は必ずtasks_current.mdと突き合わせる
- セッション開始時に直近のdailyファイルを読んだとき、「確認待ち・要対応」セクションの内容がtasks_current.mdに存在するか確認する
- 存在しなければ即座に追加する

### ルール3：セッション開始時の3点チェック（順番通りに実施）
1. `tasks_current.md` を読む
2. 今日の曜日 × 週次カレンダー表を照合 → 定常業務の漏れがないか確認
3. 直近のdailyファイルの「確認待ち・要対応」 × tasks_current.md を突き合わせ → 漏れがあれば追加

### ルール4：タスクには必ずゴール（完了条件）を明記する
- 「何をすればこのタスクが終わりか」が一目でわかるように書く
- 例：「厚労省のコメントを確認し、基金に回答する」「本田さんのRvOKが出る」

## セッション開始時の曜日別定常業務チェック（必須）

`tasks_current.md` の内容に加え、**今日の曜日と下表を照合**して定常業務を漏れなく拾う。  
詳細手順は `_agent/01_定常業務/20260831_電カル調査研究_定常業務マニュアル/02_output/20260831_定常業務マニュアル_vN.md` を参照。

| 曜日 | 定常業務 | 参照セクション |
|---|---|---|
| 月 | 三者定例ラップアップ（10:30）・昼会・開発進捗連絡会議（13:30）・開発課題検討会（14:00）・夕会（17:00）・会議後：議事要旨コメント作成〜返送（週次定常・複数日跨ぎ） | Section 2, 3-2, 4, 5 |
| 火 | 昼会・ONS問合せ会議（14:15）・ONS共有会（15:00）・夕会（17:00） | Section 2, 7 |
| 水 | 昼会（ONS返送日）・夕会（ONS受領日・17:00）・夕会前にWBS当てTodo事前ピックアップ | Section 2 |
| 木 | **三者定例 事前連携（13:30刈り取り・14:00格納）** | Section 3-3 |
| 金 | WBS確認会（10:00）・昼会・三者定例（15:00）・夕会（16:30）・WBS Todoスライド更新・課題・Todo台帳更新（本田さんRv依頼）・三者定例後の翌週リマインド投稿予約・次週ファイル作成 | Section 3-1, 6 |
| 月次（第2週） | ONS月次報告アジェンダ対応 | Section 7注記 |
| 月次（不定） | マスタ更新スケジュールスライド作成（次週開発進捗連絡会議向け） | 詳細は9/30午後メモ参照（要取込み） |

> **運用ルール**：セッション開始時に「今日は〇曜 → 上表の定常業務がある → tasks_current.md に未記載なら追加」という流れで処理する。ユーザーから新しいマニュアル・作業メモを受け取ったら、週次カレンダーに該当する業務を抽出して本表を更新する。
